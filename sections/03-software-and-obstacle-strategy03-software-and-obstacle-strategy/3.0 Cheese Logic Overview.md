Cheese v4 uses a software structure based on **separate testing codes** for the Open Challenge and the Obstacle Challenge. Both codes follow the same general idea: the robot reads its sensors, chooses the most important behavior for that moment, and sends commands to the drive and steering motors.

The Open Challenge code is the most developed mode. It focuses on completing three laps, counting curves correctly, avoiding walls, and parking at the end. The Obstacle Challenge code builds on the same navigation structure but adds the **HuskyLens + Arduino Nano** system for red and green pillar detection.

The current software is in a **near-final calibration phase**. The main logic is already defined, but values and behavior may still be adjusted based on testing.

---

## ❀ 3.0.1 Software Purpose ────୨ৎ────────୨ৎ────

The software has one main goal:

<p align="center">
  <strong>Use sensor information to move Cheese through the track safely, count progress, react to walls, detect obstacles, and finish in the correct parking area.</strong>
</p>

The robot does not simply drive forward blindly. Each loop of the program checks the robot’s surroundings and decides what action should take control.

<div align="center">

| Software Job | What It Means |
| :--- | :--- |
| **Read sensors** | Collect wall distance, front distance, floor color, and camera data. |
| **Validate readings** | Reject impossible or unsafe sensor values before using them. |
| **Count progress** | Use floor colors to count curves and track lap progress. |
| **Correct movement** | Use PID and wall logic to avoid collisions and handle curves. |
| **Detect obstacles** | Use HuskyLens and Arduino Nano to detect red and green pillars. |
| **Avoid pillars** | Add a camera-based steering bias when an obstacle is detected. |
| **Recover position** | Return to normal steering after curves or obstacle movement. |
| **Park** | Stop after the required number of curves/laps using saved distance references. |

</div>

## ❀ 3.0.3 Platform and Hardware Map ────୨ৎ────────୨ৎ────

The main robot code runs on the LEGO EV3 Brick using **Python 3** and the **ev3dev2** framework. The Arduino Nano is used as a bridge between the EV3 and the HuskyLens camera.

<div align="center">

| Property | Current Cheese v4 Setup |
| :--- | :--- |
| **Main language** | Python 3 |
| **Main framework** | ev3dev2 |
| **Main controller** | LEGO EV3 Brick |
| **Vision helper controller** | Arduino Nano |
| **Camera** | HuskyLens |
| **Drive motor** | EV3 Large Motor |
| **Steering motor** | EV3 Medium Motor |
| **Color sensor mode** | `COL-COLOR` |
| **Ultrasonic mode** | `US-DIST-CM` |
| **Main loop delay** | 0.01 s / 10 ms |

</div>

## ❀ 3.0.5 Main Software Architecture ────୨ৎ────────୨ৎ────

Cheese v4 uses a **priority-based control structure**. This means the robot does not give every behavior the same importance at the same time.

For example, if the robot is extremely close to a front wall, safety should take priority before normal steering. If the robot is detecting a valid curve, curve behavior matters more than tiny straight-line corrections. If the camera detects a pillar, the obstacle steering should influence the robot, but not if that would force the robot into a wall.

<p align="center">
  <a href="https://quesovamos2662.github.io/WRO2026_FE_Go-Cheese/embeds/v4_software_priority_chain.html">
    <img src="https://img.shields.io/badge/Open_v4_Software_Priority_Chain-FF9CEE?style=for-the-badge">
  </a>
</p>

<div align="center">

| Priority Layer | What It Does | Why It Matters |
| :---: | :--- | :--- |
| **1. Front wall safety** | Uses the front ultrasonic sensor to detect dangerous front-wall distance. | Prevents direct front collisions. |
| **2. Curve / line counting** | Uses the color sensor to detect blue and orange floor events. | Tracks the robot’s progress through the required laps. |
| **3. Wall and curve correction** | Uses ultrasonic sensors and PID logic to correct movement only when needed. | Avoids overcorrecting on straights. |
| **4. Obstacle detection** | Uses HuskyLens/Nano data to detect red and green pillars. | Allows the robot to react to obstacles. |
| **5. Recovery and parking** | Clears old steering commands, aligns after movement, and stops after the required progress. | Prevents one action from affecting the next part of the run. |

</div>

## ❀ 3.0.6 Sensor Roles in Software ────୨ৎ────────୨ৎ────

Each sensor has a specific job. The software becomes more reliable when each sensor is used for the task it is best at.

<p align="center">
  <a href="https://quesovamos2662.github.io/WRO2026_FE_Go-Cheese/embeds/v4_sensor_configuration.html">
    <img src="https://img.shields.io/badge/Open_v4_Sensor_Configuration-C77DFF?style=for-the-badge">
  </a>
</p>

<div align="center">

| Sensor | What the Software Uses It For |
| :--- | :--- |
| **Left ultrasonic** | Detects the left wall and helps identify if the robot is too close to that side. |
| **Right ultrasonic** | Detects the right wall and helps identify if the robot is too close to that side. |
| **Front ultrasonic** | Detects the wall in front and can trigger front collision recovery. |
| **Color sensor** | Detects blue and orange floor colors for curve counting. |
| **HuskyLens** | Detects red and green obstacle pillars. |
| **Arduino Nano** | Converts HuskyLens information into simple serial packets that the EV3 can read. |

</div>

The software does not use the color sensor in RGB-RAW mode in the current v4 logic. Instead, it uses **COL-COLOR mode**, where the EV3 color sensor returns a built-in color classification.

## ❀ 3.0.7 Open Challenge Logic Summary ────୨ৎ────────୨ৎ────

The Open Challenge code focuses on completing the required path without obstacles. Its main tasks are:

<div align="center">

| Open Challenge Task | Current Logic |
| :--- | :--- |
| **Drive through the track** | The Large Motor moves the robot while the Medium Motor controls steering. |
| **Detect curves** | The color sensor detects blue and orange floor color transitions. |
| **Count progress** | A valid opposite-color transition counts as one curve. |
| **Avoid walls** | Ultrasonic sensors activate correction when the robot is too close or entering a curve. |
| **Recover from front wall danger** | Front ultrasonic safety can reverse the robot away from a front wall. |
| **Finish after required progress** | The robot uses curve count and stored start-distance references for parking. |

</div>

### Curve counting idea

Cheese uses the floor colors to know when it has reached important parts of the track. The current Open logic is based on **BLUE** and **ORANGE** detections.

A valid curve is based on opposite-color progress, such as:

<div align="center">

| Valid Curve Sequence |
| :---: |
| **BLUE → ORANGE** |
| **ORANGE → BLUE** |

</div>

The Open code also includes timing protection so the two colors must happen within a limited time window. This helps prevent random or old detections from being counted as a real curve.

## ❀ 3.0.8 Minimum-Correction PID Logic ────୨ৎ────────୨ৎ────

The current software does not try to constantly steer between the walls every moment. Instead, Cheese uses a **minimum-correction controller**.

This means:

<p align="center">
  <strong>The robot normally tries to drive straight. PID correction activates when a correction is genuinely necessary.</strong>
</p>

<div align="center">

| Situation | Software Response |
| :--- | :--- |
| **Path is safe and open** | Drive straight with minimal steering. |
| **Side wall is too close** | Activate PID correction away from the wall. |
| **Curve is detected by front + side sensor pattern** | Use PID-based curve assistance. |
| **Sensor reading is invalid** | Avoid trusting impossible distance values. |
| **Correction direction changes** | Reduce stored steering influence so the robot does not carry old correction into the next section. |

</div>

This approach was chosen because constant steering corrections can make the robot oscillate, especially when ultrasonic readings are noisy or when the robot exits a curve.

The PID values are still calibration values, so the detailed constants belong in **Section 3.6 Tuning Process**. This overview focuses on the role of the controller rather than treating every value as final.

## ❀ 3.0.9 Front Wall Safety and Recovery ────୨ৎ────────୨ৎ────

The front ultrasonic sensor has an important safety role. It detects when Cheese is too close to a wall in front.

If the front wall distance becomes too small, the robot can:

<div align="center">

| Step | Action |
| :---: | :--- |
| **1** | Stop trusting normal forward movement for that moment. |
| **2** | Reset PID influence. |
| **3** | Center the steering. |
| **4** | Reverse straight away from the wall. |
| **5** | Resume normal navigation when the front distance is safe again. |

</div>

This behavior prevents the robot from continuing to push into a wall when the front sensor sees a dangerous distance.

## ❀ 3.0.10 Obstacle Challenge Logic Summary ────୨ৎ────────୨ৎ────

The Obstacle Challenge code adds the HuskyLens and Arduino Nano system to the navigation base.

Current obstacle rule:

<div align="center">

| Obstacle | HuskyLens ID | Required Behavior |
| :--- | :---: | :--- |
| **Red pillar** | **ID 1** | Pass on the right. |
| **Green pillar** | **ID 2** | Pass on the left. |

</div>

The HuskyLens detects the obstacle color, and the Arduino Nano sends simplified data to the EV3.

The serial packet format is:

<div align="center">

| Packet | Meaning |
| :--- | :--- |
| `R,xCenter,width` | Red pillar detected. |
| `G,xCenter,width` | Green pillar detected. |
| `N,0,0` | No valid pillar detected. |

</div>

The EV3 does not only receive the color. It also receives:

<div align="center">

| Value | Purpose |
| :--- | :--- |
| **Color code** | Tells whether the obstacle is red or green. |
| **xCenter** | Tells where the block appears horizontally in the camera image. |
| **width** | Estimates how large/close/confident the detection is. |

</div>

## ❀ 3.0.11 Camera-Based Steering Bias ────୨ৎ────────୨ৎ────

When the Obstacle Challenge code receives a fresh pillar detection, the software calculates a **camera steering bias**.

This bias is not a completely separate driving system. It is added to the normal steering logic so the robot can avoid the pillar while still respecting wall safety.

<div align="center">

| Camera Logic Part | Purpose |
| :--- | :--- |
| **Minimum width** | Ignores very small or noisy detections. |
| **xCenter position** | Helps decide how the robot should move relative to the pillar. |
| **Color-specific target** | Red and green use different desired passing positions. |
| **Bias smoothing** | Prevents the steering from snapping too harshly. |
| **Approach speed** | Slows the robot when approaching a detected pillar. |
| **Wall clearance limit** | Reduces camera steering if the requested side is too close to a wall. |
| **Lost-pillar reset** | Clears camera steering when the pillar leaves view. |

</div>

This is important because obstacle avoidance must not fight the wall safety system. If the robot is already too close to a wall, wall protection has priority over a camera command that would make the situation worse.

## ❀ 3.0.13 Reliability Layer ────୨ৎ────────୨ৎ────

Cheese uses multiple reliability protections because real sensor data is not always perfect.

<div align="center">

| Reliability Protection | Purpose |
| :--- | :--- |
| **Distance validation** | Rejects ultrasonic readings outside the realistic range. |
| **Sensor filtering** | Reduces sudden ultrasonic jumps and derivative spikes. |
| **Cooldown after curve count** | Prevents one floor event from being counted multiple times. |
| **Fresh camera packet check** | Prevents old HuskyLens detections from controlling the robot. |
| **Minimum pillar width** | Rejects tiny/noisy obstacle detections. |
| **PID reset when not needed** | Prevents old steering corrections from staying active. |
| **Camera steering reset when pillar is lost** | Prevents the robot from keeping an old obstacle turn. |
| **Parking mode camera suppression** | Prevents obstacle steering from interfering with final parking. |

</div>

This reliability layer is important because Cheese has to work on a real field, not in a perfect simulation. Lighting, distance readings, camera angle, steering friction, battery level, and sensor placement can all affect the software.

## ❀ 3.0.14 Main Loop Overview ────୨ৎ────────୨ৎ────

At a high level, the robot repeats the same decision cycle many times per second.

<div align="center">

| Loop Step | Action |
| :---: | :--- |
| **1** | Check if the stop button was pressed. |
| **2** | Read the front ultrasonic sensor. |
| **3** | Run front collision safety if needed. |
| **4** | Read the floor color and update curve counter. |
| **5** | Read left and right ultrasonic sensors. |
| **6** | Check if the finish/parking position has been reached. |
| **7** | Run PID, wall correction, curve assistance, and camera bias. |
| **8** | Send speed and steering commands to the motors. |
| **9** | Wait for the next loop cycle. |

</div>

This loop structure makes the software easier to debug because each behavior has a clear place in the decision cycle.

## ✦ Final Software Overview Note ─── ⋆⋅☆⋅⋆ ───

Cheese v4's software is designed around priority, not randomness. The robot reads sensors, validates data, counts track progress, avoids walls, responds to obstacles, and parks using a structured decision loop.

The Open Challenge logic is mostly developed and continues to be tuned for consistency. The Obstacle Challenge logic is already connected to movement, but it is still being calibrated for camera angle, late detection, recovery after avoidance, and obstacle parking.
