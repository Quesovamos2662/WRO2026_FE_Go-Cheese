Cheese v4 does not operate using one isolated command such as:

```text
DRIVE FORWARD
```

Instead, the robot continuously observes its environment and decides which behavior should control the motors at each moment.

The general control idea is:

```text
READ ENVIRONMENT
       ↓
VALIDATE SENSOR DATA
       ↓
IDENTIFY CURRENT SITUATION
       ↓
CHOOSE HIGHEST-PRIORITY RESPONSE
       ↓
CALCULATE STEERING + SPEED
       ↓
MOVE
       ↓
READ AGAIN
```

The robot currently uses **separate Open Challenge and Obstacle Challenge programs**.

The Open Challenge system is the most mature and is capable of completing three laps with curve counting and final parking.

The Obstacle Challenge adds the HuskyLens + Arduino Nano vision architecture for detecting and avoiding the red and green pillars.

---

# ❀ 3.0.1 Software Purpose ────୨ৎ────────୨ৎ────

The software has one main engineering goal:

<p align="center">
  <strong>
    Convert information from the real track into controlled,
    repeatable movement.
  </strong>
</p>

This requires several software responsibilities.

<div align="center">

| Software Job | What It Means |
| :--- | :--- |
| **Read sensors** | Collect wall distance, front distance, floor color, and camera data |
| **Validate readings** | Prevent unrealistic or outdated sensor information from controlling the robot |
| **Track progress** | Use floor colors to count completed curves |
| **Control steering** | Use PID and protective steering logic to maintain a useful path |
| **Protect from walls** | React before Cheese becomes trapped against a wall |
| **Detect obstacles** | Use HuskyLens data to identify red and green pillars |
| **Avoid pillars** | Modify steering according to obstacle color and position |
| **Recover** | Return Cheese to a useful trajectory after a correction or avoidance |
| **Park** | Finish after the required Open Challenge progress |

</div>

The important idea is that these behaviors are **connected**.

A correct sensor reading is useful only if the robot reacts correctly to it.

The programs are intentionally kept separate during development because the two challenges require different priorities.

```text
OPEN
 ↓
NAVIGATION
CURVES
WALL SAFETY
PARKING
```

while:

```text
OBSTACLE

NAVIGATION
    +
CAMERA
    +
PILLAR AVOIDANCE
    +
RECOVERY
```

Keeping them separate makes testing easier because a problem introduced during obstacle development does not need to destabilize the already more reliable Open Challenge system.

# ❀ 3.0.6 Priority-Based Control ────୨ৎ────────୨ৎ────

Cheese v4 uses a **priority-based software architecture**.

Not every behavior should have equal authority at the same time.

For example:

- avoiding a dangerous front wall is more important than maintaining normal forward speed,
- a strong wall-safety correction should not be ignored because of a minor PID correction,
- obstacle steering should not force Cheese directly into a wall,
- and parking logic should take control when the run is complete.

A simplified priority chain is:

```text
1. SAFETY
      ↓
2. VALID TRACK EVENTS
      ↓
3. WALL / PID CONTROL
      ↓
4. OBSTACLE RESPONSE
      ↓
5. NORMAL FORWARD MOVEMENT
      ↓
6. FINISH / PARKING WHEN REQUIRED
```

  <a href="https://quesovamos2662.github.io/WRO2026_FE_Go-Cheese/embeds/v4_software_priority_chain.html">
    <img src="https://img.shields.io/badge/Open_v4_Software_Priority_Chain-FF9CEE?style=for-the-badge">
  </a>
</p>

<div align="center">

| Priority Layer | Purpose |
| :--- | :--- |
| **Front safety** | Prevent dangerous frontal proximity |
| **Curve validation** | Keep correct run progress |
| **Wall protection** | Prevent wall contact |
| **PID navigation** | Maintain useful positioning |
| **Camera influence** | Avoid obstacles in Obstacle Challenge |
| **Recovery** | Remove old steering behavior |
| **Parking** | Stop correctly after required progress |

</div>

# ❀ 3.0.7 Main Control Loop ────୨ৎ────────୨ৎ────

The program repeats a decision cycle many times per second.

A simplified version is:

```text
START LOOP
    ↓
READ FRONT DISTANCE
    ↓
DANGER?
 ┌──┴──┐
YES    NO
 │      │
RECOVER │
        ↓
READ FLOOR COLOR
        ↓
UPDATE CURVE COUNTER
        ↓
READ SIDE DISTANCES
        ↓
CALCULATE WALL / PID RESPONSE
        ↓
READ CAMERA DATA
(IF OBSTACLE MODE)
        ↓
COMBINE ALLOWED STEERING INFLUENCES
        ↓
SET STEERING
        ↓
SET DRIVE SPEED
        ↓
CHECK FINISH / PARKING
        ↓
REPEAT
```

<div align="center">

| Loop Step | Action |
| :---: | :--- |
| **1** | Read front ultrasonic |
| **2** | Apply front-wall protection if required |
| **3** | Read floor color |
| **4** | Validate curve progress |
| **5** | Read lateral ultrasonics |
| **6** | Calculate PID / wall response |
| **7** | Read camera data in Obstacle mode |
| **8** | Calculate final steering request |
| **9** | Set motor speed |
| **10** | Check parking / completion |
| **11** | Repeat |

</div>

This structure helps isolate failures because each decision has a defined place in the loop.

# ❀ 3.0.8 Open Challenge Logic ────୨ৎ────────୨ৎ────

The Open Challenge is currently Cheese's most reliable software mode.

Its goal is to:

```text
START
  ↓
DRIVE
  ↓
DETECT CURVES
  ↓
COUNT 12 CURVES
  ↓
COMPLETE 3 LAPS
  ↓
RETURN TO PARKING REGION
  ↓
STOP
```

The system combines:

- color sensing,
- lateral ultrasonic navigation,
- front-wall protection,
- PID,
- steering control,
- curve validation,
- and parking logic.

# ❀ 3.0.10 Curve Counting Logic ────୨ৎ────────୨ৎ────

Cheese does not count every color reading as a corner.

A valid curve requires a meaningful transition.

```text
BLUE → ORANGE
```

or:

```text
ORANGE → BLUE
```

The current system also includes:

- a color-change time window,
- steering confirmation,
- minimum steering time,
- post-color steering validation,
- and cooldown.

This prevents one physical curve from being counted multiple times.

Current important values include:

<div align="center">

| Curve Parameter | Current Value |
| :--- | :---: |
| **Required curves** | **12** |
| **Color-change window** | **3.0 s** |
| **Curve cooldown** | **1.5 s** |
| **Minimum steering confirmation** | **0.1°** |
| **Minimum steering time** | **0.03 s** |
| **Post-color steering window** | **0.9 s** |

</div>

For three laps:

```text
4 CURVES
   ×
3 LAPS
   =
12 VALIDATED CURVES
```

The curve count is important because parking depends on the robot correctly understanding its progress through the run.

---

# ❀ 3.0.11 Minimum-Correction PID ────୨ৎ────────୨ৎ────

Cheese does not constantly steer aggressively between both walls.

The current Open controller follows a **minimum-correction philosophy**.

<p align="center">
  <strong>
    Drive straight whenever possible.
    Correct only when the sensor information shows that correction is useful.
  </strong>
</p>

A simplified controller behavior is:

```text
SAFE POSITION
    ↓
MINIMAL STEERING


SMALL ERROR
    ↓
PID CORRECTION


CLOSE TO WALL
    ↓
GENTLE PROTECTION


TOO CLOSE
    ↓
STRONG PROTECTION
```

Current PID values include:

<div align="center">

| Constant | Current Value |
| :--- | :---: |
| **KP** | **0.28** |
| **KI** | **0.001** |
| **KD** | **0.08** |
| **Integral limit** | **20** |
| **Center deadband** | **1.5** |
| **Maximum PID angle** | **32°** |

</div>

Filtering is also used to reduce unstable reactions to short ultrasonic fluctuations.

The goal is not perfectly constant distance.

The goal is a **stable and repeatable trajectory**.

# ❀ 3.0.14 Reverse Recovery ────୨ৎ────────୨ৎ────

If Cheese becomes dangerously close to a front wall, continuing to steer forward may no longer be useful.

The software can instead create physical space.

```text
FRONT WALL TOO CLOSE
        ↓
CONFIRM READING
        ↓
REDUCE / RESET NORMAL CONTROL
        ↓
REVERSE
        ↓
CREATE SPACE
        ↓
RETURN TO NAVIGATION
```

This is important because:

> **A steering system needs physical space to steer.**

If the robot is already pressed against a wall, stronger steering alone may not solve the problem.

Recovery therefore becomes part of navigation rather than only an emergency behavior.

# ❀ 3.0.15 Open Parking Logic ────୨ৎ────────୨ৎ────

Parking begins after the Open Challenge progress is complete.

The current system combines:

- curve count,
- starting distance information,
- ultrasonic readings,
- slower final movement,
- and final alignment checks.

The basic idea is:

```text
START
 ↓
SAVE REFERENCE DISTANCES
 ↓
RUN 3 LAPS
 ↓
REACH CURVE 12
 ↓
RETURN TOWARD START REGION
 ↓
COMPARE DISTANCES
 ↓
SLOW DOWN
 ↓
ENTER PARKING AREA
 ↓
STOP
```

Current Open parking is functional.

Cheese normally stops inside the correct region, although final alignment may still be slightly angled.

The largest remaining parking sensitivity is the curve counter:

```text
MISSED CURVE
    ↓
WRONG PROGRESS
    ↓
PARKING TOO LATE


EXTRA CURVE
    ↓
WRONG PROGRESS
    ↓
PARKING TOO EARLY
```

# ❀ 3.0.18 Nano Communication ────୨ৎ────────୨ৎ────

The Arduino Nano simplifies the camera data before the EV3 uses it.

Current communication packets use a structure such as:

```text
R,xCenter,width
```

for red,

```text
G,xCenter,width
```

for green,

and:

```text
N,0,0
```

when no useful pillar is available.

<div align="center">

| Data | Meaning |
| :--- | :--- |
| **R / G** | Obstacle color |
| **xCenter** | Horizontal position in camera image |
| **width** | Apparent pillar width / visual size |
| **N** | No valid detection |

</div>

This means the EV3 receives more than only:

```text
RED
```

or:

```text
GREEN
```

It also receives information about **where the pillar appears in the camera image**.

# ❀ 3.0.19 Camera Field of View ────୨ৎ────────୨ৎ────

Camera placement directly affects software behavior.

<p align="center">
  <img src="../../v-photos/v4/huskylens_angle_side_v4.jpg"

</p>

<p align="center">
  <em>
    Current HuskyLens viewing angle during obstacle testing.

</p>

The software cannot avoid a pillar that the camera never sees.

Therefore:

```text
ROBOT POSITION
      ↓
CAMERA ANGLE
      ↓
PILLAR ENTERS FOV
      ↓
DETECTION
      ↓
EV3 RECEIVES DATA
      ↓

```

This explains why a missed pillar is not always a camera-classification failure.

It can also result from:

- a poor curve exit,
- pillar angle,
- insufficient field of view,
- late visibility,
- excessive approach speed,
- or poor robot position.

# ❀ 3.0.20 Camera Steering Influence ────୨ৎ────────୨ৎ────

When a fresh obstacle detection is received, the Obstacle Challenge code generates a steering influence.

This camera influence is combined with the navigation system rather than replacing every other behavior.

Conceptually:

```text
NORMAL PID / WALL STEERING
            +
CAMERA OBSTACLE INFLUENCE
            ↓
FINAL STEERING REQUEST
```

However:

```text
CAMERA REQUEST
      ↓
WOULD IT CREATE WALL DANGER?
       ┌────┴────┐
      YES        NO
       ↓          ↓
LIMIT IT       ALLOW IT
```

This prevents obstacle avoidance from blindly forcing Cheese into a nearby wall.

```text
      ↓
CHEESE PASSES LEFT
```

# ❀ 3.0.22 Detection ≠ Successful Avoidance ────୨ৎ────────୨ৎ────

One of the most important lessons from obstacle testing is:

<p align="center">
  <strong>
    Seeing the pillar and successfully passing the pillar are two different engineering problems.
  </strong>
</p>

A successful sequence requires:

```text
SEE PILLAR
    ↓
IDENTIFY COLOR
    ↓
DETECT EARLY ENOUGH
    ↓
CALCULATE USEFUL STEERING
    ↓
MOVE AROUND PILLAR
    ↓
CLEAR PILLAR
    ↓
RECOVER POSITION
    ↓
PREPARE FOR NEXT PILLAR
```

Failure at any stage affects the next one.

---

# ❀ 3.0.23 Obstacle Recovery ────୨ৎ────────୨ৎ────

Recovery after avoidance is currently one of the largest development challenges.

Passing one pillar is not enough.

After avoidance, Cheese should return to a trajectory where:

- the robot is stable,
- the steering is not carrying an old avoidance request,
- ultrasonic wall information remains useful,
- and the camera can see the next pillar.

The desired behavior is:

```text
AVOID PILLAR
     ↓
CLEAR PILLAR
     ↓
REDUCE CAMERA BIAS
     ↓
RETURN TO NORMAL NAVIGATION
     ↓
STABILIZE
     ↓
DETECT NEXT PILLAR
```

A poor recovery can instead create:

```text
AVOID PILLAR
     ↓
BAD EXIT ANGLE
     ↓
NEXT PILLAR OUTSIDE CAMERA FOV
     ↓
LATE DETECTION
     ↓
FAILED NEXT AVOIDANCE
```

This makes recovery a **systems problem**, not merely a steering adjustment.

# ❀ 3.0.24 Current Obstacle Failure Modes ────୨ৎ────────୨ৎ────

<div align="center">

| Failure | Current Observation |
| :--- | :--- |
| **Pillar enters camera late** | Avoidance starts with less available distance |
| **Poor approach angle** | Detection may become unreliable |
| **Weak avoidance** | Cheese may contact the pillar |
| **Obstacle carried** | Can occur when detection/reaction is insufficient |
| **Poor recovery** | Robot can leave avoidance at a bad angle |
| **Next pillar not visible soon enough** | Often connected to previous recovery |
| **Wall contact** | Can occur during poor avoidance/recovery combinations |
| **Obstacle parking** | Still pending final stabilization |

</div>

The largest remaining challenge is currently:

> **Reliable post-obstacle recovery.**

# ❀ 3.0.25 Reliability Protections ────୨ৎ────────୨ৎ────

Real sensors are not perfect.

Cheese therefore uses several software protections.

<div align="center">

| Protection | Purpose |
| :--- | :--- |
| **Ultrasonic filtering** | Reduce short distance fluctuations |
| **Derivative filtering** | Reduce unstable PID reaction |
| **Color grouping** | Make orange detection more tolerant |
| **Curve cooldown** | Prevent duplicate counts |
| **Steering confirmation** | Help validate physical curve behavior |
| **Front confirmations** | Prevent one bad reading from instantly triggering recovery |
| **Camera freshness logic** | Prevent old obstacle data from controlling steering |
| **Lost-pillar handling** | Remove stale camera influence |
| **Wall protection** | Limit dangerous steering directions |
| **Parking suppression** | Prevent unrelated behaviors from interfering with finish logic |

</div>

These protections follow one important principle:

```text
RAW SENSOR DATA
      ↓
VALIDATION
      ↓
FILTERING
      ↓
INTERPRETATION
      ↓
ACTION
```

# ❀ 3.0.26 Speed as Part of the Software Strategy ────୨ৎ────────୨ৎ────

Speed is not treated independently from sensing.

A faster robot:

```text
COVERS MORE DISTANCE
BETWEEN DETECTIONS
```

which means:

```text
LESS TIME
FOR CAMERA + ULTRASONICS + STEERING
TO REACT
```

Therefore the software uses different speeds for different situations.

The target is not maximum speed.

# ❀ 3.0.28 Software + Mechanical Interaction ────୨ৎ────────୨ৎ────

Software performance depends on the mechanical robot.

For example:

```text
SOFTWARE REQUESTS STEERING
        ↓
MEDIUM MOTOR MOVES
        ↓
LINKAGE MOVES
        ↓
FRONT WHEELS TURN
        ↓
ROBOT CHANGES TRAJECTORY
```

If the linkage has play, friction or limited movement, the same software command may produce a different physical result.

The reverse is also true.

Mechanical improvements such as:

- reduced v4 mass,
- improved front-wheel configuration,
- lower EV3 placement,
- more compact steering,
- and better sensor placement

made software tuning easier because the robot became more predictable.

# ❀ 3.0.29 Battery as a Software Variable ────୨ৎ────────୨ৎ────

Battery condition also influences robot behavior.

The numerical software values may remain identical while:

- motor response changes,
- acceleration changes,
- steering becomes weaker,
- or recovery becomes less consistent.

Therefore:

```text
FAILED RUN
   ≠
AUTOMATICALLY BAD CODE
```

A failure may originate from:

```text
CODE
SENSOR
MECHANICS
BATTERY
CAMERA ANGLE
TRACK POSITION
TIMING
```

This is why software testing is always performed as part of the complete physical system.

# ❀ 3.0.30 Current Development Strategy ────୨ৎ────────୨ৎ────

The development process follows:

```text
TEST
 ↓
OBSERVE
 ↓
IDENTIFY FAILURE
 ↓
ISOLATE POSSIBLE CAUSE
 ↓
CHANGE ONE IMPORTANT VARIABLE
 ↓
TEST AGAIN
 ↓
COMPARE
```

The team avoids changing many unrelated variables simultaneously whenever possible because that makes it difficult to identify which change actually improved the robot.

The current tuning order has generally been:

```text
MECHANICAL RELIABILITY
        ↓
COLOR DETECTION
        ↓
PID
        ↓
CURVES
        ↓
OPEN PARKING
        ↓
OBSTACLE DETECTION
        ↓
OBSTACLE AVOIDANCE
        ↓
OBSTACLE RECOVERY
        ↓
OBSTACLE PARKING
```

# ❀ 3.0.31 Failure → Cause → Fix Philosophy ────୨ৎ────────୨ৎ────

Software changes are documented as engineering decisions rather than random parameter edits.

<div align="center">

| Failure | Likely Cause | Adjustment |
| :--- | :--- | :--- |
| Zig-zag on straights | Excessive steering correction | Minimum-correction PID |
| Duplicate curve count | Repeated floor detection | Cooldown + validation |
| Missed orange | Built-in color variation | Warm-color grouping |
| Front collision risk | Insufficient forward protection | Front ultrasonic recovery |
| Wide curve | Steering/timing mismatch | Curve calibration |
| Pillar detected late | FOV / approach / speed | Camera and path tuning |
| Pillar contacted | Avoidance insufficient | Stronger/earlier useful response |
| Bad obstacle exit | Recovery insufficient | Recovery tuning |
| Parking timing wrong | Incorrect progress count | Improve curve-count reliability |

</div>

The objective is always:

```text
FAILURE
   ↓
CAUSE
   ↓
RISK
   ↓
CHANGE
   ↓
RESULT
   ↓
LEARNING
```

# ✦ Engineering Lessons ─── ⋆⋅☆⋅⋆ ───

### 1. Software cannot be separated from the physical robot

A correct algorithm can still fail if the sensor geometry or mechanical response is poor.

### 2. More correction is not always better

Minimal useful correction often produces a more stable path than constant aggressive steering.

### 3. Detection is only the beginning

Seeing a wall, line or pillar is useful only if Cheese reacts correctly afterward.

### 4. Recovery matters

Every maneuver must leave the robot ready for the next one.

### 5. Reliability requires repetition

One successful run proves that the code can work.

Repeated successful runs show that the complete system is becoming reliable.

### 6. Every failure should produce information

The goal of testing is not only to succeed.

It is to understand **why** Cheese succeeds or fails.

# ✦ 3.0 Final Software Overview ─── ⋆⋅☆⋅⋆ ───

Cheese v4 uses a structured, sensor-driven software system built around **priority, validation, progressive correction and recovery**.

In the Open Challenge, the EV3 combines:

- three ultrasonic sensors,
- the EV3 Color Sensor,
- PID navigation,
- progressive wall protection,
- front-distance recovery,
- validated curve counting,
- and parking logic.

This system currently allows Cheese to complete its three-lap Open run with relatively stable behavior.

For the Obstacle Challenge, the architecture adds:

- HuskyLens obstacle recognition,
- Arduino Nano communication,
- red/green passing rules,
- camera-based steering influence,
- wall-aware avoidance,
- and post-obstacle recovery.

The obstacle system already detects pillars and influences physical movement, but avoidance and especially recovery remain active development areas.

The most important software principle behind Cheese is:

<p align="center">
  <strong>
    Sense → Validate → Decide → Act → Recover → Repeat
  </strong>
</p>
