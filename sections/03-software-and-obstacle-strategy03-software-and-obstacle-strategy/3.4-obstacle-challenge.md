The Obstacle Challenge requires Cheese to continue navigating the field while also reacting to colored pillars.

The robot must do more than detect an obstacle.

A complete successful maneuver requires:

```text
SEE PILLAR
    ↓
IDENTIFY COLOR
    ↓
DETECT EARLY ENOUGH
    ↓
CHOOSE REQUIRED PASSING SIDE
    ↓
CREATE CLEARANCE
    ↓
PASS PILLAR
    ↓
RECOVER
    ↓
PREPARE FOR NEXT EVENT
```

The current vision system already affects physical steering.

The main remaining challenge is making the complete sequence repeatable.

# ❀ 3.4.2 Obstacle Challenge Objective ────୨ৎ────────୨ৎ────

The Obstacle Challenge combines normal navigation with vision-based decision-making.

<div align="center">

| Objective | Meaning |
| :--- | :--- |
| **Keep normal navigation active** | Cheese must continue moving through the field |
| **Detect pillars** | HuskyLens identifies green and red |
| **Send usable camera data** | Nano transfers simplified information to EV3 |
| **Choose correct passing side** | Each color has a fixed rule |
| **Avoid without contact** | Robot should clear the pillar rather than push it |
| **Respect walls** | Camera steering must not create wall danger |
| **Recover** | Robot should stabilize after each avoidance |
| **Prepare for next pillar** | Recovery should return the next obstacle to useful camera view |
| **Finish later** | Obstacle parking will be finalized after avoidance becomes reliable |

</div>

The real engineering challenge is combining:

```text
VISION
   +
WALL SAFETY
   +
STEERING
   +
SPEED
   +
RECOVERY
```

without letting one system destroy another.

# ❀ 3.4.6 Obstacle System Architecture ────୨ৎ────────୨ৎ────

The obstacle system has three main layers.

<div align="center">

| Layer | Components | Main Role |
| :--- | :--- | :--- |
| **Navigation layer** | EV3, motors, ultrasonics, color sensor | Normal field navigation |
| **Vision layer** | HuskyLens + Arduino Nano | Detect and transmit pillar information |
| **Reaction layer** | EV3 steering / speed logic | Turn camera information into obstacle movement |

</div>

The architecture is:

```text
ENVIRONMENT
    ↓
HUSKYLENS
    ↓
ARDUINO NANO
    ↓
EV3
    ↓
NAVIGATION + VISION LOGIC
    ↓
STEERING + DRIVE
    ↓
ROBOT MOVEMENT
```

The camera therefore provides information.

It does not independently control the motors.

# ❀ 3.4.12 Simplified Vision Packets ────୨ৎ────────୨ৎ────

The Nano sends compact packets.

For red:

```text
R,xCenter,width
```

For green:

```text
G,xCenter,width
```

If there is no useful obstacle:

```text
N,0,0
```

<div align="center">

| Packet Value | Meaning |
| :--- | :--- |
| **R / G** | Pillar color |
| **xCenter** | Horizontal image position |
| **width** | Apparent detected width |
| **N** | No valid current pillar |

</div>

The EV3 therefore receives:

```text
WHAT IS IT?
+
WHERE IS IT?
+
HOW LARGE DOES IT APPEAR?
```

# ❀ 3.4.14 Camera Data Freshness ────୨ৎ────────୨ৎ────

Old vision information should not continue steering Cheese.

Example:

```text
PILLAR DETECTED
      ↓
STEERING BEGINS
      ↓
PILLAR LEAVES VIEW
```

If the previous command is never cleared:

```text
OLD CAMERA COMMAND
      ↓
CONTINUED TURN
      ↓
BAD RECOVERY
      ↓
WALL / NEXT-PILLAR PROBLEM
```

Therefore the controller checks whether the latest packet is still valid.

---

# ❀ 3.4.15 Camera Steering Bias ────୨ৎ────────୨ৎ────

Camera information becomes a steering **influence**, not an unlimited command.

```text
NORMAL NAVIGATION
        +
CAMERA BIAS
        ↓
SAFETY LIMIT
        ↓
FINAL STEERING
```

Important mechanisms include:

<div align="center">

| Feature | Purpose |
| :--- | :--- |
| **Fresh packet check** | Reject outdated camera commands |
| **Minimum detection size** | Ignore weak / tiny detections |
| **Color rule** | Choose correct passing side |
| **xCenter response** | React to horizontal pillar location |
| **Width response** | Increase reaction as pillar becomes more relevant |
| **Bias smoothing** | Avoid sudden steering snaps |
| **Approach-speed reduction** | Increase reaction time |
| **Wall limiter** | Prevent camera steering toward danger |
| **Lost-pillar reset** | Remove old obstacle influence |

</div>

# ❀ 3.4.18 Approach Phase ────୨ৎ────────୨ৎ────

The ideal obstacle approach begins while Cheese still has enough physical distance to react.

```text
PILLAR ENTERS VIEW
       ↓
DETECTION BECOMES VALID
       ↓
STEERING BEGINS EARLY
       ↓
LATERAL CLEARANCE BUILDS
```

Late detection instead creates:

```text
PILLAR APPEARS LATE
       ↓
LESS AVAILABLE DISTANCE
       ↓
STRONGER LAST-SECOND TURN REQUIRED
       ↓
GREATER CONTACT RISK
```

This is why camera angle and speed matter.

---

# ❀ 3.4.19 Speed During Approach ────୨ৎ────────୨ৎ────

A faster robot reduces available reaction time.

```text
MORE SPEED
   ↓
MORE DISTANCE TRAVELED
WHILE THE CAMERA + EV3 + STEERING REACT
```

Controlled speed gives:

```text
MORE TIME
   ↓
EARLIER EFFECTIVE STEERING
   ↓
MORE CLEARANCE
```

The goal is not to drive slowly everywhere.

It is to slow down where obstacle control requires precision.

# ❀ 3.4.22 Detection ≠ Successful Avoidance ────୨ৎ────────୨ৎ────

One of the most important obstacle-development lessons is:

<p align="center">
  <strong>
    Correct recognition does not automatically mean successful avoidance.
  </strong>
</p>

A complete maneuver requires:

```text
CORRECT DETECTION
       ↓
EARLY ENOUGH DETECTION
       ↓
USEFUL STEERING
       ↓
ENOUGH PHYSICAL SPACE
       ↓
PILLAR CLEARANCE
       ↓
RECOVERY
```

Any one of those stages can fail.

---

# ❀ 3.4.23 Avoidance Strength ────୨ৎ────────୨ৎ────

Too little obstacle response can produce:

```text
DETECT
 ↓
WEAK TURN
 ↓
INSUFFICIENT CLEARANCE
 ↓
CONTACT
```

Too much response can produce:

```text
DETECT
 ↓
AGGRESSIVE TURN
 ↓
PILLAR CLEARED
 ↓
WALL DANGER
```

The desired response is:

> **Strong enough to clear the pillar, but controlled enough to preserve a recoverable trajectory.**

---

# ❀ 3.4.24 Pillar-Carrying Failure ────୨ৎ────────୨ৎ────

One important field failure is Cheese carrying the pillar.

A typical chain is:

```text
PILLAR DETECTED LATE
      ↓
AVOIDANCE BEGINS LATE
      ↓
NOT ENOUGH LATERAL SPACE
      ↓
ROBOT CONTACTS PILLAR
      ↓
PILLAR MOVES WITH ROBOT
```

Possible contributors include:

- camera geometry,
- late field-of-view entry,
- excessive approach speed,
- weak avoidance,
- poor starting trajectory.

---

# ❀ 3.4.25 Recovery Phase ────୨ৎ────────୨ৎ────

Recovery is currently one of the largest obstacle-development priorities.

The desired transition is:

```text
PILLAR CLEARED
      ↓
CAMERA BIAS REDUCES
      ↓
STEERING RETURNS
      ↓
NORMAL NAVIGATION REGAINS AUTHORITY
      ↓
ROBOT STABILIZES
```

The robot should not continue carrying an old obstacle steering command after the obstacle is already behind it.

---

# ❀ 3.4.26 Recovery Affects Future Vision ────୨ৎ────────୨ৎ────

Poor recovery can create a failure several seconds later.

```text
PILLAR 1 CLEARED
      ↓
BAD EXIT ANGLE
      ↓
CAMERA POINTS AWAY
      ↓
PILLAR 2 ENTERS VIEW LATE
      ↓
LATE DETECTION
      ↓
PILLAR 2 FAILURE
```

This is one of the most important systems-level observations in the obstacle strategy.

A problem that looks like a camera failure may actually begin in the previous steering maneuver.

# ❀ 3.4.29 Obstacle Control Priority ────୨ৎ────────୨ৎ────

Different behaviors need different levels of authority.

A practical priority structure is:

```text
FRONT SAFETY
      ↓
SEVERE WALL PROTECTION
      ↓
VALID OBSTACLE RESPONSE
      ↓
NORMAL NAVIGATION
      ↓
RECOVERY / STABILIZATION
```

Parking becomes relevant once obstacle navigation itself is sufficiently stable.

The central rule is:

<p align="center">
  <strong>
    Vision may influence the robot strongly,
    but it should not blindly override safety.
  </strong>
</p>

# ❀ 3.4.30 Main Current Failure Modes ────୨ৎ────────୨ৎ────

<div align="center">

| Failure | How It Appears | Likely Cause | Current Direction |
| :--- | :--- | :--- | :--- |
| **Late detection** | Robot reacts too close | FOV / approach geometry | Earlier useful visibility |
| **Weak avoidance** | Pillar still contacted | Insufficient response | Strengthen controlled bias |
| **Pillar carried** | Robot pushes obstacle | Late reaction / low clearance | Earlier response + speed tuning |
| **Poor recovery** | Robot exits misaligned | Transition unstable | Recovery tuning |
| **Next pillar appears late** | Camera cannot see it soon enough | Previous recovery angle | Improve exit geometry |
| **Wall contact** | Robot clears pillar but reaches wall | Avoidance too aggressive | Better wall interaction |
| **Obstacle parking unfinished** | Full finish sequence incomplete | Avoidance not stable enough | Parking later |

</div>

The current obstacle system is not mainly failing because it confuses colors.

The main difficulties are **timing, physical clearance and recovery**. :contentReference[oaicite:1]{index=1}

# ❀ 3.4.31 Failure Chains ────୨ৎ────────୨ৎ────

Obstacle failures often form chains.

### Chain A — Late detection

```text
BAD APPROACH
      ↓
PILLAR ENTERS FOV LATE
      ↓
LATE CAMERA DATA
      ↓
LATE STEERING
      ↓
CONTACT
```

### Chain B — Poor recovery

```text
PILLAR 1 CLEARED
      ↓
BAD RECOVERY
      ↓
BAD ROBOT HEADING
      ↓
PILLAR 2 OUTSIDE FOV
      ↓
NEXT FAILURE
```

### Chain C — Over-aggressive avoidance

```text
STRONG CAMERA RESPONSE
      ↓
PILLAR CLEARED
      ↓
ROBOT TOO CLOSE TO WALL
      ↓
WALL CONTACT
```

These show why obstacle development cannot be reduced to adjusting only one steering number.

Parking should remain later because any major change to obstacle movement can change the final trajectory of the run.

# ❀ 3.4.34 Software + Mechanics + Vision Feedback ────୨ৎ────────୨ৎ────

Obstacle navigation forms a closed feedback loop.

```text
CAMERA SEES PILLAR
      ↓
SOFTWARE CALCULATES
      ↓
MEDIUM MOTOR TURNS
      ↓
ROBOT CHANGES HEADING
      ↓
CAMERA VIEW CHANGES
      ↓
NEW DETECTION
```

This means the previous steering command directly changes the next camera input.

Vision and movement therefore cannot be tuned independently.

---

# ❀ 3.4.35 Why One Successful Pillar Is Not Enough ────୨ৎ────────୨ৎ────

A complete obstacle run requires repeated success.

```text
PILLAR 1
 ↓
AVOID
 ↓
RECOVER
 ↓
PILLAR 2
 ↓
AVOID
 ↓
RECOVER
 ↓
PILLAR 3
 ↓
...
```

A single successful avoidance proves:

```text
THE SYSTEM CAN WORK
```

Repeated successful sequences prove:

```text
THE SYSTEM IS BECOMING RELIABLE
```

# ✦ Engineering Lessons ─── ⋆⋅☆⋅⋆ ───

### 1. Recognition and avoidance are different problems

The camera can correctly identify the obstacle while the physical maneuver still fails.

---

### 2. Camera geometry is part of navigation

Where Cheese points determines what the HuskyLens can see.

---

### 3. Speed affects perception

Higher speed reduces the time available between useful detection and obstacle contact.

---

### 4. Vision should not blindly override safety

The correct pillar rule is useless if following it directly sends Cheese into a wall.

---

### 5. Recovery is part of obstacle avoidance

A maneuver is not complete when the pillar is merely behind the robot.

It is complete when Cheese is ready for what comes next.

---

### 6. A failure may begin one obstacle earlier

Poor recovery from Pillar 1 can cause late detection of Pillar 2.

---

### 7. Physical evidence should define documentation

Current HuskyLens testing visibly confirms:

```text
GREEN = ID 1
RED   = ID 2
```

The repository should use this current mapping consistently.

# ✦ 3.4 Obstacle Challenge Summary ─── ⋆⋅☆⋅⋆ ───

Cheese v4's Obstacle Challenge combines the normal navigation architecture with a dedicated vision system.

The current obstacle system uses:

- HuskyLens recognition,
- Arduino Nano communication,
- **Green = ID 1**,
- **Red = ID 2**,
- Green → pass left,
- Red → pass right,
- camera position information,
- obstacle-size information,
- camera steering influence,
- wall-safety limitation,
- approach-speed control,
- lost-pillar handling,
- and post-obstacle recovery.

Current physical evidence confirms both trained color classes, and real obstacle-field testing confirms that the system is already being tested as a complete physical navigation problem.

The main remaining development target is:

```text
EARLY USEFUL DETECTION
        ↓
CONTROLLED AVOIDANCE
        ↓
CLEAN CLEARANCE
        ↓
STABLE RECOVERY
        ↓
NEXT PILLAR READY
```

  </strong>
