The Obstacle Challenge is more complex than the Open Challenge because Cheese must still drive around the field while also reacting to colored pillars. The robot must not only detect an obstacle; it must detect it early enough, classify it correctly, move around it without carrying it, and recover before the next wall, curve, or obstacle.

The current Obstacle Challenge code is:

<div align="center">

| Current File | Recommended Clean Repository Name |
| :--- | :--- |
| `GOODYIPEE (1)(3) (21).py` | `obstacle_challenge_v4_testing.py` |

</div>

This code is the current official obstacle testing version. It already connects camera detection to robot movement, but the system is still being calibrated for detection timing, camera angle, avoidance strength, recovery after the obstacle, and obstacle parking.

## ❀ 3.4.1 Obstacle Challenge Objective ────୨ৎ────────୨ৎ────

In the Obstacle Challenge, Cheese must complete the same general field navigation while reacting to red and green pillars.

<div align="center">

| Objective | Meaning |
| :--- | :--- |
| **Keep normal navigation active** | The robot still needs wall sensing, curve counting, and safe movement. |
| **Detect obstacles** | HuskyLens identifies red and green pillars. |
| **Receive camera data** | Arduino Nano sends simplified detection data to the EV3. |
| **Choose the correct side** | Red and green pillars require different passing behavior. |
| **Avoid without carrying the pillar** | The robot must steer early enough to go around the obstacle. |
| **Recover after avoidance** | Cheese must return to a stable path after passing the pillar. |
| **Adapt parking later** | Obstacle parking is still pending in the current v4 calibration. |

</div>

The main obstacle challenge is not only color recognition. The hardest part is combining vision, steering, wall protection, speed control, and recovery without causing one behavior to fight another.

## ❀ 3.4.4 Obstacle System Architecture ────୨ৎ────────୨ৎ────

Cheese v4 divides the obstacle system into three layers.

<div align="center">

| Layer | Components Used | Main Role |
| :--- | :--- | :--- |
| **Navigation layer** | EV3, Large Motor, Medium Motor, ultrasonic sensors, color sensor | Keeps the robot moving, avoids walls, counts curves, and manages parking logic. |
| **Vision layer** | HuskyLens camera and Arduino Nano | Detects red and green pillars and sends simplified data to the EV3. |
| **Reaction layer** | EV3 steering logic, drive motor, wall safety, camera bias | Adjusts speed and steering so Cheese can pass the pillar safely. |

</div>

This separation is important because the camera should not control the robot alone. The EV3 still handles movement stability, wall safety, steering limits, and recovery.

## ❀ 3.4.5 Hardware and Communication Path ────୨ৎ────────୨ৎ────

The obstacle system uses the HuskyLens as the camera and the Arduino Nano as the communication bridge.

<div align="center">

| Step | System | Function |
| :---: | :--- | :--- |
| **1** | HuskyLens | Detects trained red and green pillars. |
| **2** | Arduino Nano | Reads HuskyLens data and simplifies it. |
| **3** | EV3 USB serial | Receives the simplified packet from the Nano. |
| **4** | EV3 Python code | Converts the packet into camera steering bias. |
| **5** | Motors | Apply the final steering and speed command. |

</div>

<p align="center">
  <img src="../../img/HuskyLens_to_Arduino_Nano_Wiring.png" alt="HuskyLens to Arduino Nano wiring diagram" width="80%">
</p>

<p align="center">
  <em>HuskyLens to Arduino Nano wiring diagram used for the obstacle vision communication system.</em>
</p>

The Arduino Nano is useful because it allows the vision system to be tested separately from EV3 driving. This makes debugging easier: the team can check whether the camera/Nano sends correct data before tuning steering behavior.

## ❀ 3.4.6 Pillar Identification Rules ────୨ৎ────────୨ৎ────

The HuskyLens is trained with fixed IDs for obstacle colors.

<div align="center">

| Pillar | HuskyLens ID | Required Behavior |
| :--- | :---: | :--- |
| **Red pillar** | **ID 1** | Pass on the right. |
| **Green pillar** | **ID 2** | Pass on the left. |

</div>

This rule must stay consistent in the code, camera training, and testing notes. If the ID mapping or the steering convention changes, the robot may avoid the correct color in the wrong direction.

---

## ❀ 3.4.7 Nano to EV3 Data Packet ────୨ৎ────────୨ৎ────

The Arduino Nano does not send a large amount of camera data to the EV3. Instead, it sends a simplified packet.

<div align="center">

| Packet | Meaning |
| :--- | :--- |
| `R,xCenter,width` | Red pillar detected. |
| `G,xCenter,width` | Green pillar detected. |
| `N,0,0` | No valid pillar detected. |

</div>

The EV3 uses three parts of the packet:

<div align="center">

| Packet Part | Why It Matters |
| :--- | :--- |
| **Color code** | Tells the robot whether the pillar is red or green. |
| **`xCenter`** | Shows where the pillar appears horizontally in the camera view. |
| **`width`** | Helps estimate detection strength, size, and reaction intensity. |

</div>

This design makes the EV3 code simpler because it does not need to process raw camera vision. It only needs to interpret a small obstacle message.

---

## ❀ 3.4.8 Camera Placement and Detection Timing ────୨ৎ────────୨ৎ────

Camera placement is one of the biggest tuning factors in the Obstacle Challenge. Cheese v4 places the HuskyLens lower and closer to the front area than the older v3 design.

<p align="center">
  <img src="../../v-photos/v4/sensor_placement_cam_v4.jpg" alt="Cheese v4 HuskyLens camera placement" width="75%">
</p>

<p align="center">
  <em>Cheese v4 HuskyLens camera placement used for obstacle recognition and current angle calibration.</em>
</p>

The camera angle matters because the obstacle must enter the field of view early enough. If the pillar appears too late, Cheese may not have enough distance to steer around it, even if the color is detected correctly.

<div align="center">

| Camera Issue | Effect on Robot |
| :--- | :--- |
| **Obstacle appears late** | The robot reacts too close to the pillar. |
| **Obstacle enters at a bad angle** | The detection may not be stable or centered enough. |
| **Pillar is visible but too small** | The robot may not react strongly enough. |
| **Pillar is lost during approach** | Camera bias may clear before avoidance finishes. |

</div>

The current obstacle problem is mostly timing and geometry, not color confusion.

## ❀ 3.4.9 Normal Navigation Still Runs ────୨ৎ────────୨ৎ────

The Obstacle Challenge still depends on the Open Challenge navigation base. Cheese cannot focus only on pillars because it must also stay inside the track and continue counting progress.

<div align="center">

| Open Navigation System | Role During Obstacle Challenge |
| :--- | :--- |
| **Side ultrasonic sensors** | Help avoid left/right walls. |
| **Front ultrasonic sensor** | Protects against front-wall danger. |
| **Color sensor** | Tracks curve progress. |
| **Sensor-fusion PID** | Provides steering correction and wall control. |
| **Parking logic** | Still needed after the required progress, but obstacle parking is currently pending. |

</div>

When no valid obstacle is detected, Cheese should continue normal navigation. When an obstacle is detected, the camera branch adds steering influence, but wall safety can still limit unsafe commands.

---

## ❀ 3.4.10 Camera Steering Bias ────୨ৎ────────୨ৎ────

The obstacle code uses camera data as a **steering bias**. This means the camera does not completely take over the robot. Instead, the code adds a camera-based influence to the normal steering decision.

<div align="center">

| Camera Bias Feature | Purpose |
| :--- | :--- |
| **Fresh packet check** | Prevents old obstacle data from controlling the robot. |
| **Minimum width check** | Ignores tiny or weak detections. |
| **Color-specific target** | Uses different desired passing behavior for red and green. |
| **`xCenter` correction** | Uses the horizontal obstacle position to decide steering influence. |
| **Width / proximity response** | Reacts more strongly when the pillar appears larger. |
| **Bias smoothing** | Prevents harsh steering jumps. |
| **Speed reduction** | Gives the steering system more time to avoid the pillar. |
| **Wall-safety limit** | Reduces camera influence if the requested side is too close to a wall. |
| **Lost-pillar reset** | Clears camera steering when the obstacle is no longer valid. |

</div>

This approach is important because obstacle avoidance and wall protection can conflict. For example, the camera may request movement to one side, but the ultrasonic sensors may show that this side is already too close to a wall. In that case, wall safety must protect the robot.

---

## ❀ 3.4.11 Obstacle Avoidance Phases ────୨ৎ────────୨ৎ────

The obstacle behavior can be divided into three main phases.

<div align="center">

| Phase | What Happens | Current Issue |
| :--- | :--- | :--- |
| **Approach phase** | HuskyLens sees the pillar and Nano sends the packet to EV3. | Detection can happen late depending on camera angle. |
| **Avoidance phase** | EV3 adds camera steering bias and may slow the robot. | Avoidance can be too weak or too late, causing the robot to carry the pillar. |
| **Recovery phase** | Camera bias clears and robot returns to normal navigation. | Recovery sometimes leaves the robot poorly aligned. |

</div>

The recovery phase is very important. If Cheese avoids the obstacle but exits at a bad angle, the robot may struggle with the next wall, curve, or obstacle.

---

## ❀ 3.4.12 Current Failure Analysis ────୨ৎ────────୨ৎ────

The obstacle system currently fails for understandable reasons. These failures are useful because they show what still needs to be tuned.

<div align="center">

| Failure | How It Looks on the Field | Likely Cause | Current Response |
| :--- | :--- | :--- | :--- |
| **Late detection** | Cheese reacts when it is already close to the pillar. | Camera angle, field of view, or detection threshold. | Adjust camera angle and reduce approach speed. |
| **Weak avoidance** | Cheese sees the pillar but still clips or carries it. | Camera bias not strong or early enough. | Increase response carefully without creating wall crashes. |
| **Obstacle carried by robot** | Cheese pushes the pillar instead of passing it. | Reaction starts too late or steering is not enough. | Tune detection timing, bias strength, and speed reduction. |
| **Poor recovery** | Cheese passes the obstacle but exits misaligned. | Camera bias clears before path is stable or PID returns too early/late. | Tune recovery and transition back to normal navigation. |
| **Wall contact after avoidance** | Cheese avoids the pillar but later touches wall. | Exit angle after avoidance is not controlled enough. | Improve recovery and wall-safety interaction. |
| **Obstacle parking unfinished** | Robot may not finish the obstacle round parking reliably. | Current v4 parking has not been fully adapted to obstacle behavior. | Keep obstacle parking as a future calibration stage. |

</div>

The most common failure is that Cheese detects or reacts too late and can carry the obstacle. Wall crashes after avoidance happen less often, and color confusion is not the main current problem.

---

## ❀ 3.4.13 Speed Control During Obstacles ────୨ৎ────────୨ৎ────

Obstacle avoidance needs controlled speed. If the robot approaches too fast, the steering motor does not have enough time to move the chassis around the pillar.

<div align="center">

| Situation | Speed Behavior | Reason |
| :--- | :--- | :--- |
| **No obstacle detected** | Normal navigation speed. | Maintains efficiency when the path is clear. |
| **Obstacle detected** | Controlled approach speed. | Gives the robot more time to react. |
| **Avoidance active** | Reduced or stable speed. | Prevents the robot from overshooting the avoidance path. |
| **Pillar lost** | Return carefully to normal navigation. | Avoids keeping old camera steering after the obstacle leaves view. |
| **Recovery needed** | Maintain controlled correction before full speed. | Helps the robot re-enter stable navigation. |

</div>

The goal is not to make the robot slow forever. The goal is to slow down only when obstacle behavior needs more control.

---

## ❀ 3.4.14 Behavior Priority in Obstacle Challenge ────୨ৎ────────୨ৎ────

Obstacle behavior must be priority-based. Without priorities, PID, wall protection, and camera steering could fight each other.

<div align="center">

| Priority | Behavior | Reason |
| :---: | :--- | :--- |
| **1** | Manual stop / safe shutdown | The robot must always be stoppable. |
| **2** | Front-wall safety | A front collision can stop the run immediately. |
| **3** | Finish / parking mode | After required progress, finishing becomes the goal. |
| **4** | Valid obstacle camera bias | A confirmed pillar needs path adjustment. |
| **5** | Severe wall protection | Wall safety can limit unsafe obstacle steering. |
| **6** | Curve and progress tracking | The robot must keep track of the course. |
| **7** | Normal sensor-fusion PID | Handles movement when no higher-priority event needs control. |

</div>

The key idea is that obstacle avoidance should influence steering, but it should not blindly override safety. A good obstacle system must avoid the pillar and still respect the walls.

---

## ❀ 3.4.15 Testing Plan for Obstacle Challenge ────୨ৎ────────୨ৎ────

The obstacle system should be tested in stages because many variables affect the result.

<div align="center">

| Test Stage | What to Test | Success Condition |
| :---: | :--- | :--- |
| **1** | HuskyLens red detection | Red pillar is detected consistently as ID 1. |
| **2** | HuskyLens green detection | Green pillar is detected consistently as ID 2. |
| **3** | Nano to EV3 packet | EV3 receives `R`, `G`, or `N` packets correctly. |
| **4** | Camera angle | Pillar appears early enough for reaction. |
| **5** | Single red obstacle | Robot passes red on the right without carrying it. |
| **6** | Single green obstacle | Robot passes green on the left without carrying it. |
| **7** | Avoidance strength | Steering is strong enough to clear the pillar but not so strong that it hits a wall. |
| **8** | Recovery after obstacle | Robot returns to stable navigation after passing the pillar. |
| **9** | Obstacle + curve interaction | Robot does not lose the next curve or wall after avoidance. |
| **10** | Multiple obstacle sequence | Robot handles more than one obstacle in a run. |
| **11** | Obstacle parking adaptation | Parking is adapted after avoidance behavior becomes stable. |
| **12** | Repeatability | Several runs behave similarly under the same setup. |

</div>

Testing should start slowly. If detection fails, camera angle and training should be checked before changing steering. If the robot carries the obstacle, the team should check detection timing, speed, and camera bias before changing parking.

## ❀ 3.4.16 Current Tuning Priorities ────୨ৎ────────୨ৎ────

The current obstacle priorities are:

<div align="center">

| Priority | Tuning Area | Why It Comes First |
| :---: | :--- | :--- |
| **1** | Camera angle and field of view | The robot cannot avoid what it does not see early enough. |
| **2** | Detection timing | Late detection causes late steering and obstacle contact. |
| **3** | Avoidance strength | Weak avoidance can make the robot carry the obstacle. |
| **4** | Recovery after avoidance | Bad recovery can ruin the next curve or next obstacle. |
| **5** | Speed during obstacle approach | Speed must give steering enough time to work. |
| **6** | Obstacle parking | Parking should be finalized after obstacle movement is reliable. |

</div>

This order avoids tuning the wrong subsystem first. For example, obstacle parking should not be finalized until obstacle avoidance and recovery are stable.

## ❀ Obstacle Challenge Summary ────୨ৎ────────୨ৎ────

Cheese v4's Obstacle Challenge strategy adds vision-based decision-making to the Open Challenge navigation base. The robot still uses ultrasonic sensors for wall safety, the color sensor for curve progress, and EV3 motor control for steering and drive movement. The HuskyLens and Arduino Nano add an extra layer that allows the robot to detect red and green pillars.

The system already detects obstacles and can influence movement, but it is still being calibrated. The main current problems are late detection, camera angle sensitivity, weak/late avoidance, obstacle contact, recovery after passing the pillar, and pending obstacle parking.

<p align="center">
  <strong>Final interpretation:</strong><br>
  Cheese's obstacle strategy is strongest when camera detection, wall safety, speed control, and recovery work together instead of competing for steering control.
</p>
