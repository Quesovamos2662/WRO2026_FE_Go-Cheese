Cheese v4's software architecture is based on one central idea:

<p align="center">
  <strong>
    The robot should not constantly correct its movement.
    It should drive naturally whenever possible and intervene only
    when sensor information shows that correction is useful.
  </strong>
</p>

This led to a **minimum-correction, priority-based architecture**.

Instead of allowing every sensor to continuously command the steering system, Cheese separates sensing from decision-making.

```text
SENSORS
   ↓
VALIDATE INFORMATION
   ↓
INTERPRET CURRENT SITUATION
   ↓
SELECT RELEVANT CONTROL BEHAVIOR
   ↓
CALCULATE FINAL STEERING + SPEED
   ↓
MOVE
   ↓
READ AGAIN
```

The result is a controller where different behaviors cooperate instead of constantly fighting each other.

      +

      +

This separation also protects the more stable Open Challenge logic from experimental obstacle changes.

# ❀ 3.1.4 Program Structure ────୨ৎ────────୨ৎ────

The current code follows a modular organization.

<div align="center">

| Program Block | Function |
| :--- | :--- |
| **Imports** | Loads EV3 motors, sensors, timing and communication libraries |
| **Hardware initialization** | Assigns motors and sensors to physical ports |
| **Constants** | Stores speed, steering, PID, wall, timing and recovery parameters |
| **State variables** | Stores information that must survive between loop cycles |
| **Sensor functions** | Read and validate hardware values |
| **Steering functions** | Convert desired angles into controlled motor movement |
| **PID functions** | Calculate minimum-correction navigation |
| **Curve functions** | Detect and validate progress |
| **Safety functions** | Detect dangerous front-wall situations |
| **Parking functions** | Detect return to the starting region |
| **Vision functions** | Parse Nano/HuskyLens information |
| **Main loop** | Coordinates the complete control cycle |
| **Shutdown logic** | Safely stops the motors if the program exits |

</div>

This makes debugging easier than placing every behavior inside one giant loop.

A failure can be investigated inside the subsystem responsible for it.

# ❀ 3.1.5 Main Control Cycle ────୨ৎ────────୨ৎ────

The main program runs continuously while Cheese is moving.

<p align="center">

       width="82%">
</p>

<p align="center">
  <em>
    Current Cheese v4 software control cycle.
  </em>
</p>

A simplified execution order is:

```text
START LOOP
    ↓
CHECK STOP CONDITION
    ↓
READ FRONT SENSOR
    ↓
FRONT DANGER?
    ↓
RUN SAFETY IF REQUIRED
    ↓
READ COLOR SENSOR
    ↓
UPDATE CURVE STATE
    ↓
READ SIDE ULTRASONICS
    ↓
FILTER / VALIDATE DISTANCES
    ↓
CALCULATE NAVIGATION
    ↓
READ CAMERA DATA
(Obstacle mode)
    ↓

    ↓
COMMAND STEERING + DRIVE
    ↓
CHECK FINISH / PARKING
    ↓
REPEAT
```

The Open controller currently uses a loop delay of approximately:

```text
0.01 s
```

This allows Cheese to update decisions many times every second.

# ❀ 3.1.6 Priority-Based Control ────୨ৎ────────୨ৎ────

Cheese does not allow every control system to have unlimited authority.

The current architecture uses **behavior priority**.

A simplified priority concept is:

```text
CRITICAL SAFETY
      ↓
TRACK PROGRESS
      ↓
WALL PROTECTION
      ↓
PID / CURVE RESPONSE
      ↓
CAMERA AVOIDANCE
      ↓
NORMAL MOVEMENT
```

Parking becomes the dominant finishing behavior once the required progress has been completed.

<div align="center">

| Control Layer | Trigger | Response |
| :--- | :--- | :--- |
| **Front safety** | Dangerous front distance | Reverse / create space |
| **Curve validation** | Valid floor-color progression | Update curve counter |
| **Wall protection** | Side distance becomes unsafe | Increase steering protection |
| **PID navigation** | Useful wall/curve error exists | Apply proportional correction |
| **Obstacle response** | Fresh pillar detection exists | Add camera steering influence |
| **Normal movement** | No important correction exists | Drive with minimal steering |
| **Parking** | Full run progress reached | Enter final parking behavior |

</div>

<p align="center">
  <a href="https://quesovamos2662.github.io/WRO2026_FE_Go-Cheese/embeds/v4_software_priority_chain.html">
    <img src="https://img.shields.io/badge/Open_v4_Software_Priority_Chain-FF9CEE?style=for-the-badge">
  </a>
</p>

The architecture is designed to prevent situations such as:

```text
CAMERA SAYS TURN LEFT
        +
WALL SENSOR SAYS LEFT SIDE IS DANGEROUS
        ↓
UNCONTROLLED CONFLICT
```

Instead, wall safety can limit the camera request.

# ❀ 3.1.7 Sensor Validation Layer ────୨ৎ────────୨ৎ────

Sensor readings are not used blindly.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/07_v4_sensor_validation_reliability.png"
       alt="Cheese v4 sensor validation and reliability flowchart"
       width="78%">
</p>

<p align="center">
  <em>
    Validation and reliability checks applied before sensor information is allowed to influence movement.
  </em>
</p>

The general architecture is:

```text
RAW READING
     ↓
VALID?
 ┌───┴───┐
NO      YES
│         │
IGNORE   FILTER
          ↓
     INTERPRET
          ↓
       CONTROL
```

Reliability mechanisms include:

- ultrasonic range validation,
- ultrasonic filtering,
- derivative filtering,
- color sequence validation,
- curve cooldown,
- steering confirmation,
- repeated front-distance confirmations,
- camera freshness checks,
- minimum obstacle-size checks,
- and reset of outdated control states.

This prevents one incorrect sensor sample from instantly changing the robot's trajectory.

# ❀ 3.1.8 Software State and Memory ────୨ৎ────────୨ৎ────

A control loop sees only the present moment.

Cheese also needs memory.

State variables allow the program to remember what happened during previous cycles.

### Navigation State

<div align="center">

| State | Purpose |
| :--- | :--- |
| `last_error` | Previous PID error |
| `integral` | Accumulated PID error |
| filtered derivative | Smooths error-rate changes |
| filtered distances | Stores smoothed ultrasonic measurements |

</div>

### Curve State

<div align="center">

| State | Purpose |
| :--- | :--- |
| first detected color | Beginning of possible curve sequence |
| first-color time | Used for sequence timeout |
| completed curves | Tracks total progress |
| last curve time | Supports cooldown |
| steering confirmation | Confirms physical turning activity |
| pending second color | Holds a candidate transition while validation completes |

</div>

### Parking State

<div align="center">

| State | Purpose |
| :--- | :--- |
| starting side distances | Records initial geometry |
| starting front distance | Main finish reference |
| finish confirmations | Prevents one noisy reading from stopping the robot |
| previous finish distance | Helps detect target crossing |
| parking state | Indicates final-run behavior |

</div>

### Vision State

<div align="center">

| State | Purpose |
| :--- | :--- |
| latest pillar color | Red / green / none |
| pillar x-position | Horizontal camera position |
| pillar width | Apparent size |
| latest packet time | Determines whether data is fresh |
| camera steering influence | Current obstacle correction |
| lost-pillar state | Helps clear old avoidance commands |

</div>

Without state memory, Cheese could not reliably determine:

```text
WHAT HAPPENED BEFORE
        +
WHAT IS HAPPENING NOW
        ↓
WHAT SHOULD HAPPEN NEXT
```

# ❀ 3.1.9 Minimum-Correction PID Architecture ────୨ৎ────────୨ৎ────

The PID system is one of the most important architectural decisions in the Open Challenge.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/03_v4_minimum_correction_pid_controller.png"
       alt="Cheese v4 minimum correction PID controller"
       width="80%">
</p>

<p align="center">
  <em>
    Minimum-correction PID architecture used to reduce unnecessary steering on safe sections of the track.
  </em>
</p>

Cheese does **not** constantly try to sit exactly in the mathematical center of the lane.

Instead:

```text
SAFE PATH
    ↓
DRIVE STRAIGHT


USEFUL ERROR
    ↓
PID CORRECTION


DANGER
    ↓
STRONGER PROTECTION
```

Current Open PID constants are:

<div align="center">

| Constant | Current Value |
| :--- | :---: |
| **KP** | **0.28** |
| **KI** | **0.001** |
| **KD** | **0.08** |
| **Integral limit** | **20** |
| **Center deadband** | **1.5** |
| **Maximum PID angle** | **32°** |

</div>

The architecture follows:

```text
ERROR
 ↓
PROPORTIONAL RESPONSE
 +
LIMITED INTEGRAL MEMORY
 +
FILTERED DERIVATIVE RESPONSE
 ↓
STEERING CORRECTION
 ↓
ANGLE LIMIT
 ↓
STEERING MOTOR
```

The steering correction is limited because unlimited mathematical PID output would not make physical sense for the Ackermann system.

---

# ❀ 3.1.10 Why Minimum Correction Was Chosen ────୨ৎ────────୨ৎ────

Earlier behavior showed that excessive continuous correction can create:

```text
SMALL SENSOR DIFFERENCE
        ↓
STEER
        ↓
CROSS TARGET
        ↓
OPPOSITE STEER
        ↓
CROSS TARGET AGAIN
        ↓
ZIG-ZAG
```

The current architecture instead tries to create:

```text
SAFE
 ↓
STRAIGHT

DRIFT
 ↓
SMALL CORRECTION

SAFE AGAIN
 ↓
RETURN TO STRAIGHT
```

This reduced the need for Cheese to continuously fight its own previous steering commands.

Current steering calibration includes:

<div align="center">

| Parameter | Value |
| :--- | :---: |
| **Steering speed** | **60** |
| **Steering deadband** | **0.8°** |
| **Turn step** | **3.0°** |
| **Return step** | **5.0°** |
| **Soft steering start** | **10°** |
| **Full steering authority** | **24°** |
| **Maximum PID steering** | **32°** |

</div>

This creates a controlled command chain:

```text
REQUESTED ANGLE
      ↓
LIMIT ANGLE
      ↓
COMPARE WITH CURRENT STEERING
      ↓
MOVE BY CONTROLLED STEP
      ↓
MEDIUM MOTOR
      ↓
ACKERMANN LINKAGE
```

The software therefore considers the fact that steering is a **physical mechanical process**, not an instantaneous variable.

# ❀ 3.1.17 Vision Packet Architecture ────୨ৎ────────୨ৎ────

The Nano converts camera information into a compact packet.

```text
R,xCenter,width
```

means red.

```text
G,xCenter,width
```

means green.

```text
N,0,0
```

means no useful pillar.

The EV3 therefore receives:

<div align="center">

| Value | Software Meaning |
| :--- | :--- |
| **Color** | Which passing rule to apply |
| **xCenter** | Where the pillar appears horizontally |
| **width** | Approximate apparent size / proximity information |
| **packet age** | Whether the detection is still fresh |

</div>

This is more useful than simply receiving:

```text
RED
```

because obstacle movement depends on both **what** the pillar is and **where** it appears.

# ❀ 3.1.18 Camera Steering Bias ────୨ৎ────────୨ৎ────

The camera does not completely replace wall navigation.

Instead, it creates a steering influence.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/05_v4_obstacle_detection_camera_bias.png"
       alt="Cheese v4 obstacle detection and camera bias flowchart"
       width="82%">
</p>

<p align="center">
  <em>
    Obstacle-detection architecture showing how camera information becomes steering influence.
  </em>
</p>

Conceptually:

```text
NORMAL NAVIGATION
       +
CAMERA BIAS
       ↓
WALL SAFETY CHECK
       ↓
FINAL STEERING
```

Important camera-control concepts include:

- reject tiny detections,
- reject stale detections,
- use pillar position,
- use pillar width,
- choose direction according to color,
- smooth steering influence,
- reduce speed during approach,
- limit camera commands near dangerous walls,
- clear bias after losing the pillar.

This prevents the camera from behaving like an uncontrolled second steering system.

# ❀ 3.1.20 Obstacle Avoidance and Recovery ────୨ৎ────────୨ৎ────

Detection is only the first half of obstacle navigation.

The desired architecture is:

```text
DETECT PILLAR
      ↓
IDENTIFY COLOR
      ↓
GENERATE AVOIDANCE
      ↓
CLEAR PILLAR
      ↓
REMOVE OLD CAMERA INFLUENCE
      ↓
RECOVER TRAJECTORY
      ↓
PREPARE FOR NEXT PILLAR
```

The current system already performs detection and influences steering.

The main remaining difficulty is reliable recovery.

Current failure chain:

```text
PILLAR AVOIDED
      ↓
BAD EXIT ANGLE
      ↓
ROBOT NOT STABLE
      ↓
NEXT PILLAR ENTERS FOV LATE
      ↓
NEXT AVOIDANCE BECOMES HARDER
```

Therefore obstacle recovery is not treated as an optional cosmetic centering step.

It is part of preparing the perception system for the next obstacle.

# ❀ 3.1.21 Speed Architecture ────୨ৎ────────୨ৎ────

Speed is also state-dependent.

The robot does not need the same speed in every situation.

Current Open values include:

<div align="center">

| State | Speed |
| :--- | :---: |
| **Normal drive** | **-62** |
| **Gentle wall response** | **-44** |
| **Severe wall response** | **-24** |
| **Parking** | **-28** |
| **Parking medium** | **-18** |
| **Parking creep** | **-10** |
| **Emergency reverse** | **28** |

</div>

This creates:

```text
NORMAL TRACK
    ↓
FASTER


INCREASED RISK
    ↓
SLOWER


PARKING
    ↓
PRECISE


EMERGENCY
    ↓
REVERSE
```

The target is not simply the maximum possible motor speed.

It is the maximum speed that still gives the sensing and steering architecture enough time to react reliably.

# ❀ 3.1.22 Systems Interaction ────୨ৎ────────୨ৎ────

The algorithm cannot be evaluated separately from the physical robot.

For example:

```text
SOFTWARE ANGLE REQUEST
        ↓
MEDIUM MOTOR
        ↓
STEERING LINKAGE
        ↓
FRONT WHEELS
        ↓
ROBOT TRAJECTORY
        ↓
NEW SENSOR READINGS
        ↓
SOFTWARE AGAIN
```

This forms a **closed physical control loop**.

If the linkage is loose, the motor is weak, the battery is low or a sensor is badly positioned, the same software command may create a different result.

That is why tuning Cheese always involves:

```text
SOFTWARE
   +
SENSORS
   +
MECHANICS
   +
POWER
   +
TRACK GEOMETRY
```

# ❀ 3.1.23 Why Battery Condition Matters ────୨ৎ────────୨ৎ────

Battery condition can change how the same algorithm behaves.

The constants may remain identical while:

- propulsion becomes weaker,
- steering response changes,
- reverse recovery takes longer,
- or obstacle avoidance becomes less aggressive.

Therefore:

```text
FAILED TEST
    ≠
AUTOMATICALLY A SOFTWARE FAILURE
```

The team checks several possible causes:

```text
CODE?
SENSOR?
MECHANICS?
BATTERY?
CAMERA ANGLE?
TRACK POSITION?
TIMING?
```

This prevents the team from changing a correct software parameter to compensate for a hardware problem.

# ❀ 3.1.25 Architecture Failure → Fix Examples ────୨ৎ────────୨ৎ────

The current architecture was created through repeated failures and corrections.

<div align="center">

| Failure / Observation | Architectural Cause | Change | Result |
| :--- | :--- | :--- | :--- |
| Zig-zag on straights | Too much constant steering | Minimum-correction architecture | Straighter default movement |
| Wall approached too closely | PID alone was not enough in severe cases | Progressive wall protection | Earlier safety response |
| Front collision could trap steering | Turning while already too close | Reverse recovery | Creates physical steering space |
| Duplicate curve counts | Raw color events were trusted too easily | Sequence + timing + steering confirmation | Better progress reliability |
| Orange read inconsistently | Built-in color output varied | Warm-color grouping | More tolerant detection |
| Camera steering conflicted with walls | Independent steering influences | Wall-limited camera bias | Safer obstacle response |
| Old obstacle turn remained active | Camera influence lasted too long | Lost-pillar / freshness resets | Cleaner transition |
| Next obstacle became harder after avoidance | Recovery not treated as part of architecture | Explicit recovery focus | Current obstacle priority |

</div>

This represents the team's preferred engineering chain:

```text
FAILURE
   ↓
CAUSE
   ↓
RISK
   ↓
ARCHITECTURE CHANGE
   ↓
TEST
   ↓
RESULT
   ↓
LEARNING
```

# ✦ Engineering Lessons ─── ⋆⋅☆⋅⋆ ───

### 1. Clear priorities reduce conflicts

Two individually good control behaviors can still produce bad movement if both try to control the robot simultaneously.

---

### 2. Sensor validation belongs before action

A robot should not immediately trust every value it receives.

---

### 3. Straight driving is also a control decision

Not steering is sometimes better than adding another correction.

---

### 4. Safety needs its own layer

When Cheese is physically trapped near a wall, normal PID may no longer be the correct response.

---

### 5. Perception and movement are connected

Camera recognition is only useful when robot geometry allows the obstacle to enter the field of view.

---

### 6. Recovery prepares the next decision

A maneuver is not truly successful if Cheese finishes it in a position that makes the next maneuver fail.

---

### 7. Architecture should make failures understandable

A modular system allows the team to ask:

```text
WAS IT:
SENSING?
VALIDATION?
DECISION?
STEERING?
RECOVERY?
PARKING?
```

instead of treating every failed run as one unknown software problem.

# ✦ 3.1 Final Algorithm Architecture Summary ─── ⋆⋅☆⋅⋆ ───

Cheese v4 uses a **priority-based minimum-correction architecture** designed to reduce unnecessary steering and prevent different behaviors from fighting each other.

The Open Challenge architecture currently combines:

- three ultrasonic sensors,
- color-based progress detection,
- sensor filtering,
- PID navigation,
- progressive wall protection,
- front reverse recovery,
- validated curve counting,
- stored starting references,
- and final parking logic.

The Obstacle Challenge extends this architecture with:

- HuskyLens recognition,
- Arduino Nano communication,
- red/green passing rules,
- camera-based steering influence,
- wall-aware obstacle movement,
- and post-obstacle recovery.

The system can therefore be summarized as:

<p align="center">
  <strong>
    Sense → Validate → Remember → Prioritize → Correct → Recover → Repeat
  </strong>
</p>
