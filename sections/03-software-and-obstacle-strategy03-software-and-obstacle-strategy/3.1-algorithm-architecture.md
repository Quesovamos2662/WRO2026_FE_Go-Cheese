<p align="center">
  <em>This section explains the internal architecture of Cheese v4's current software. It focuses mainly on the present Open Challenge and Obstacle Challenge testing codes, while preserving a small legacy note about the previous v3 structure for engineering continuity.</em>
</p>

<p align="center">
  ✦ ─── ⋆⋅☆⋅⋆ ─── 🧀🤖 ─── ⋆⋅☆⋅⋆ ─── ✦
</p>

Cheese v4's algorithm is designed around one central idea:

<p align="center">
  <strong>The robot should not correct all the time. It should drive straight by default and only correct when the sensors show that correction is necessary.</strong>
</p>

This is why the current code is based on a **minimum-correction control architecture**. Instead of constantly forcing the robot toward the center of the track, the program waits for useful evidence: a close wall, a front wall, a confirmed curve situation, a detected floor-color transition, or a detected obstacle.

The Open Challenge and Obstacle Challenge codes are kept in separate files because they have different goals. The Open code focuses on navigation, curve counting, front safety, and parking. The Obstacle code uses the same navigation foundation but adds camera-based pillar avoidance through the HuskyLens and Arduino Nano.

## ❀ 3.1.2 Architecture Goal ────୨ৎ────────୨ৎ────

The software architecture has to organize several robot behaviors without letting them fight each other.

<div align="center">

| Behavior | Why It Needs Control |
| :--- | :--- |
| **Normal driving** | The robot must keep moving smoothly through the track. |
| **Wall correction** | The robot must avoid drifting into the side walls. |
| **Front-wall safety** | The robot must stop or reverse before pushing into a front wall. |
| **Curve counting** | The robot must know how many curves/laps have been completed. |
| **Parking** | The robot must stop after the correct track progress. |
| **Obstacle detection** | The robot must recognize red and green pillars. |
| **Obstacle avoidance** | The robot must pass each pillar on the correct side. |
| **Recovery** | The robot must return to normal driving after a curve or obstacle. |

</div>

The architecture solves this by separating the code into modules. Each module has one clear job, and the main loop decides when each job should influence the robot.

## ❀ 3.1.3 Program Structure ────୨ৎ────────୨ৎ────

The current Cheese v4 software follows a repeated structure.

<div align="center">

| Program Block | Role in the Robot |
| :--- | :--- |
| **Imports** | Loads ev3dev2 motor, sensor, button, display, sound, timing, serial, and threading tools. |
| **Hardware setup** | Assigns motors and sensors to EV3 ports and sets sensor modes. |
| **Movement settings** | Stores speed, steering, wall, PID, and timing constants. |
| **Obstacle settings** | In the obstacle code, stores HuskyLens/Nano and pillar avoidance constants. |
| **State variables** | Stores memory between loop cycles: curve count, PID state, filtered values, parking references, and camera data. |
| **Helper functions** | Reads sensors, validates data, clamps values, resets PID, sets steering, and stops the robot. |
| **Control functions** | Handles curve counting, front recovery, minimum-correction PID, camera bias, and parking detection. |
| **Main loop** | Runs the robot repeatedly until the stop button is pressed or the finish condition is reached. |
| **Finally block** | Stops motors and shows the stopped message even if the program exits unexpectedly. |

</div>

This structure keeps the code readable. Instead of placing all decisions directly inside the main loop, the loop calls functions that each handle one specific responsibility.

## ❀ 3.1.5 Main Loop Execution Order ────୨ৎ────────୨ৎ────

The main loop is the heart of the program. It repeats the same decision cycle until the robot stops.

<div align="center">

| Order | Loop Action | Why It Happens There |
| :---: | :--- | :--- |
| **1** | Check the back button | Allows an emergency stop before any new action. |
| **2** | Read the front ultrasonic sensor | Front safety has the highest priority. |
| **3** | Run front collision recovery if needed | Prevents the robot from pushing into a front wall. |
| **4** | Read floor color and update curve counter | Tracks progress through the course. |
| **5** | Read left and right ultrasonic sensors | Provides wall data for correction and curve detection. |
| **6** | Check finish / parking condition | Stops the robot after the required progress. |
| **7** | Run minimum-correction PID and camera bias | Decides steering and speed for the current moment. |
| **8** | Sleep for the loop delay | Keeps the loop timing stable. |

</div>

The loop delay is currently **0.01 s**, which means the program can update sensor readings and steering decisions many times per second.

## ❀ 3.1.6 Priority-Based Control Model ────୨ৎ────────୨ৎ────

Cheese v4 does not let every behavior control the robot at the same time. The algorithm uses priorities so the most important behavior wins each cycle.

<div align="center">

| Priority | Control Layer | Main Trigger | Main Result |
| :---: | :--- | :--- | :--- |
| **1** | **Front wall safety** | Front ultrasonic is too close to a wall. | Steering is centered and the robot reverses straight. |
| **2** | **Curve counting** | Color sensor detects blue/orange sequence. | Curve counter updates, but does not directly command steering. |
| **3** | **Wall danger correction** | A side wall is inside the correction distance. | PID activates to steer away from the close wall. |
| **4** | **Curve assistance** | Front wall plus side opening indicates a curve. | PID produces a stronger curve-related correction. |
| **5** | **Obstacle camera bias** | Fresh HuskyLens/Nano pillar packet is available. | A steering bias is added to pass the pillar correctly. |
| **6** | **Straight alignment / normal drive** | No urgent correction is needed. | Robot drives straight or makes only small alignment corrections. |
| **7** | **Parking mode** | Required curve count is reached. | Robot suppresses unnecessary camera influence and searches for finish position. |

</div>

The priority system reduces conflict. For example, camera steering should not force the robot into a wall, and PID correction should not keep old steering after the situation has changed.

## ❀ 3.1.7 State Variables ────୨ৎ────────୨ৎ────

State variables are the robot’s memory. One loop cycle only knows what sensors see right now, but the robot needs memory to count curves, smooth sensor readings, handle PID, and stop at the correct place.

### PID State

<div align="center">

| Variable | Purpose |
| :--- | :--- |
| `integral` | Stores accumulated error. In the current calibration, the integral is effectively disabled to avoid old steering influence. |
| `last_error` | Stores the previous PID error for derivative calculation. |
| `filtered_derivative` | Smooths sudden derivative changes. |

</div>

### Sensor Filtering State

<div align="center">

| Variable | Purpose |
| :--- | :--- |
| `filtered_left` | Stores filtered left ultrasonic distance. |
| `filtered_right` | Stores filtered right ultrasonic distance. |
| `filtered_front` | Stores filtered front ultrasonic distance. |

</div>

### Curve Counting State

<div align="center">

| Variable | Purpose |
| :--- | :--- |
| `first_curve_color` | Stores the first color detected in a possible curve sequence. |
| `first_curve_color_time` | Stores when the first color was detected. |
| `last_curve_count_time` | Stores when the last curve was accepted. |
| `completed_curves` | Counts the number of completed curves. |
| `steering_seen_between_colors` | In the Open code, confirms that steering happened during the color sequence. |
| `waiting_for_post_color_steering` | Allows a short window for steering to occur after the second color. |
| `pending_second_color` | Stores the second color while waiting for steering confirmation. |

</div>

### Parking and Start Memory

<div align="center">

| Variable | Purpose |
| :--- | :--- |
| `start_left_distance` | Left distance measured at the start of the run. |
| `start_right_distance` | Right distance measured at the start of the run. |
| `start_front_distance` | Front distance measured at the start of the run. |
| `finish_match_count` | Counts repeated finish matches to avoid stopping on one noisy reading. |
| `previous_finish_front` | Helps detect when the robot crosses the saved front-distance target. |
| `parking_mode_announced` | Tracks whether parking mode has already been reported. |

</div>

### Obstacle / Camera State

<div align="center">

| Variable | Purpose |
| :--- | :--- |
| `husky_color` | Stores the latest detected pillar color. |
| `husky_x_center` | Stores the horizontal position of the detected block in the camera image. |
| `husky_width` | Stores the detected block width. |
| `husky_last_update` | Stores when the latest camera packet arrived. |
| `husky_lock` | Protects camera data shared between the serial thread and navigation loop. |
| `pillar_bias` | Stores the current smoothed camera steering bias. |
| `pillar_speed_ramp` | Stores the current camera-based speed reduction. |
| `pillar_just_lost` | Marks when the robot just lost the pillar from view. |
| `navigation_phase` | Helps prevent straight alignment from fighting curve behavior. |

</div>

## ❀ 3.1.8 Curve Counting Architecture ────୨ৎ────────୨ৎ────

Cheese v4 uses the floor color sensor to count progress around the track. The current logic uses **blue** and **orange** as the meaningful floor events.

<div align="center">

| Color Event | Meaning in Code |
| :--- | :--- |
| **Blue** | Accepted as `BLUE`. |
| **Orange strip** | Treated as `ORANGE`. Depending on lighting, the sensor may classify it as red, yellow, or brown in some code versions. |

</div>

A curve is based on an opposite-color sequence:

<div align="center">

| Valid Sequence |
| :---: |
| `BLUE → ORANGE` |
| `ORANGE → BLUE` |

</div>

The current Open code makes this more reliable by adding timing and steering confirmation.

<div align="center">

| Rule | Purpose |
| :--- | :--- |
| **Opposite colors only** | Prevents repeated detection of the same color from counting twice. |
| **3.0 s color window** | Prevents old color readings from combining into a false curve. |
| **Steering confirmation** | Confirms that the robot actually performed a turn-related movement. |
| **0.9 s post-color window** | Allows the steering confirmation to happen slightly after the second color. |
| **Cooldown after count** | Prevents one curve from being counted repeatedly. |
| **Movement continues during cooldown** | The counter pauses, but the robot does not stop driving. |

</div>

The color sensor’s job is mainly to update the curve count. It does not directly choose a steering angle. Steering is handled by ultrasonic-based correction and, in the obstacle code, by camera bias.

## ❀ 3.1.9 Minimum-Correction PID Architecture ────୨ৎ────────୨ৎ────

The current controller is not a classic “always-center” PID. Instead, it is a **minimum-correction PID**.

<p align="center">
  <strong>Default behavior: drive straight. Correction only activates when there is a reason.</strong>
</p>

This prevents Cheese from overreacting to every tiny ultrasonic difference. That matters because small sensor noise can create unnecessary steering if the robot is constantly trying to center itself.

<div align="center">

| Situation | Controller Response |
| :--- | :--- |
| **Safe/open path** | Reset PID memory and drive straight. |
| **Side wall too close** | Build a wall-error value and steer away from the close wall. |
| **Curve detected by sensor pattern** | Build a curve-error value using front distance and side opening. |
| **No valid correction needed** | Do not force steering. |
| **Correction direction changes** | Reduce stored influence so the robot does not carry old steering into the next section. |

</div>

### Current PID behavior

The current PID calculation is mostly **`correction = KP * error + KD * filtered_derivative`**.

The integral term is currently set to zero in the main calibration direction. This is intentional because stored integral correction can make the robot keep turning after the original problem is gone.

<div align="center">

| PID Part | Current Role |
| :--- | :--- |
| **P / proportional** | Responds to the size of the current error. |
| **I / integral** | Disabled or minimized in the current testing logic. |
| **D / derivative** | Uses a filtered derivative to reduce sudden changes and overshoot. |

</div>

The final steering command is clamped so the PID does not create unlimited steering. This makes the robot safer and easier to tune.

## ❀ 3.1.10 Front Wall Safety Architecture ────୨ৎ────────୨ৎ────

The front ultrasonic sensor has the highest safety priority in the current loop. This is important because a front collision is more dangerous than a small side alignment error.

When the front sensor reports that Cheese is too close to a wall, the code can run a straight reverse recovery.

<div align="center">

| Recovery Step | Action |
| :---: | :--- |
| **1** | Read front distance. |
| **2** | If the robot is too close, activate recovery. |
| **3** | Reset PID memory. |
| **4** | Center steering immediately. |
| **5** | Reverse straight away from the wall. |
| **6** | Stop recovery when front distance is safe or timeout is reached. |
| **7** | Return to the normal loop. |

</div>

This layer is intentionally placed before curve counting, PID, obstacle response, and parking checks. If the robot is about to hit a front wall, it should not continue with normal driving decisions.

## ❀ 3.1.11 Obstacle Challenge Architecture ────୨ৎ────────୨ৎ────

The Obstacle Challenge code adds a vision layer to the navigation base.

<p align="center">
  <strong>HuskyLens detects the pillar. Arduino Nano simplifies the data. EV3 uses the data to adjust steering.</strong>
</p>

### Data path

<div align="center">

| Step | System | Role |
| :---: | :--- | :--- |
| **1** | HuskyLens | Detects trained red and green obstacle pillars. |
| **2** | Arduino Nano | Reads HuskyLens output and converts it into a simple serial packet. |
| **3** | EV3 USB serial | Receives the packet from the Nano. |
| **4** | EV3 Python code | Converts the packet into camera steering bias and speed adjustment. |
| **5** | Motors | Apply the final drive speed and steering angle. |

</div>

### Pillar identification

<div align="center">

| Pillar | HuskyLens ID | Required Behavior |
| :--- | :---: | :--- |
| **Red pillar** | **ID 1** | Pass on the right. |
| **Green pillar** | **ID 2** | Pass on the left. |

</div>

### Serial packets

The Nano sends one packet at a time:

<div align="center">

| Packet | Meaning |
| :--- | :--- |
| `R,xCenter,width` | Red pillar detected. |
| `G,xCenter,width` | Green pillar detected. |
| `N,0,0` | No valid pillar detected. |

</div>

The EV3 uses three parts of each packet:

<div align="center">

| Packet Value | Why It Matters |
| :--- | :--- |
| **Color code** | Chooses the red or green passing rule. |
| **xCenter** | Shows where the obstacle appears horizontally in the image. |
| **width** | Helps reject tiny/noisy detections and estimate how strongly to react. |

</div>

## ❀ 3.1.12 Camera Steering Bias ────୨ৎ────────୨ৎ────

The camera does not replace the entire driving system. Instead, it adds a **camera bias** to the normal steering decision.

This makes the obstacle logic easier to combine with wall safety.

<div align="center">

| Camera Logic Feature | Purpose |
| :--- | :--- |
| **Minimum block width** | Ignores tiny detections that are likely too far away or noisy. |
| **Fresh packet timeout** | Prevents old camera data from steering the robot. |
| **Color-specific target** | Red and green use different desired camera positions so the robot passes on the correct side. |
| **Proximity ramp** | Gives an early response and increases reaction as the block appears larger. |
| **Bias smoothing** | Prevents steering from snapping instantly to a harsh angle. |
| **Approach speed** | Slows the robot while reacting to a detected pillar. |
| **Wall clearance limiter** | Reduces camera influence if the desired side is too close to a wall. |
| **Lost-pillar reset** | Clears camera steering when the pillar leaves view. |
| **Parking suppression** | Removes camera influence once parking mode begins. |

</div>

This is one of the most important design choices in the obstacle code. It helps avoid a conflict where the camera wants to pass a pillar on one side, but the wall sensors show that the robot is already too close to that wall.

## ❀ 3.1.13 Parking Architecture ────୨ৎ────────୨ৎ────

Parking depends on the curve counter and the starting-position memory.

At the beginning of the run, the robot samples its starting distances. Later, after enough curves are counted, the robot compares current readings against those saved references to decide when it has returned to the correct area.

<div align="center">

| Parking Element | Role |
| :--- | :--- |
| **`TOTAL_CURVES = 12`** | Represents three laps with four curves per lap. |
| **Starting left distance** | Stored as a side reference. |
| **Starting right distance** | Stored as a side reference. |
| **Starting front distance** | Used as the main parking reference. |
| **Front-dominant finish check** | Stops when the front distance matches the saved front reference. |
| **Side sanity check** | Supports backup stopping but does not dominate the normal parking stop. |
| **Parking speed** | Slows the robot during final parking behavior. |

</div>

The front sensor is the dominant parking reference because it gives the robot a clearer stopping point when returning to the start area. Side sensors are still useful, but they are treated more carefully because side readings can change during curves or because of angle.

## ❀ 3.1.14 Reliability Protections ────୨ৎ────────୨ৎ────

Cheese v4 includes several protections to prevent one bad reading from controlling the whole robot.

<div align="center">

| Protection | What It Prevents |
| :--- | :--- |
| **`valid_distance()`** | Rejects impossible ultrasonic readings outside the physical range. |
| **Sensor filtering** | Reduces sudden jumps in ultrasonic values. |
| **Derivative filtering** | Prevents one sharp sensor change from creating a harsh steering command. |
| **Curve cooldown** | Prevents one color event from counting multiple times. |
| **Color timing window** | Prevents old colors from forming a false curve sequence. |
| **Steering confirmation** | Helps confirm that a counted curve corresponds to real movement. |
| **Fresh camera packet check** | Prevents stale HuskyLens data from affecting steering. |
| **Minimum pillar width** | Ignores tiny or noisy obstacle detections. |
| **PID reset** | Clears old correction memory when it should not continue. |
| **`finally` shutdown** | Stops both motors even if the program exits unexpectedly. |

</div>

Reliability protections matter because Cheese runs in a real environment. Lighting, distance readings, camera visibility, battery level, sensor position, and steering friction can all affect the robot.

## ❀ 3.1.16 Current vs Legacy v3 Architecture ────୨ৎ────────୨ৎ────

Most of this section documents the current Cheese v4 code. However, the previous v3 architecture is still important because it explains why the team changed the code structure.

<div align="center">

| Area | Legacy v3 Direction | Current v4 Direction |
| :--- | :--- | :--- |
| **General logic** | More layers and more special-case behavior. | Cleaner minimum-correction architecture. |
| **Steering behavior** | More continuous correction and stronger software compensation. | Drive straight by default; correct only when needed. |
| **Color handling** | Earlier documentation included RGB-style explanations and older function names. | Current code uses `COL-COLOR` and blue/orange curve logic. |
| **Sensors** | Older documentation did not fully match the current three-ultrasonic setup. | Current v4 uses left, right, and front ultrasonic sensors. |
| **Obstacle system** | Camera logic was less integrated in earlier documentation. | Current obstacle code uses HuskyLens/Nano data to influence steering. |
| **Documentation role** | v3 explains the engineering path and previous attempts. | v4 is the current reference for building and tuning Cheese. |

</div>

The v3 material is kept as **legacy evidence**, not as the current algorithm reference. It shows the design evolution: the team simplified the robot, reduced weight, improved sensor placement, and moved toward a control structure that creates fewer conflicts between behaviors.

## ✦ Final Algorithm Architecture Note ─── ⋆⋅☆⋅⋆ ───

Cheese v4's algorithm is built to reduce conflict between behaviors. The robot does not try to do everything at once. It checks safety, updates progress, reads walls, verifies parking, and then applies only the correction that makes sense for the current situation.

The Open Challenge code is the most stable part of the current software. The Obstacle Challenge code already connects HuskyLens/Nano detection to movement, but it is still being calibrated for camera angle, late detection, recovery, and obstacle parking.

<p align="center">
  <strong>
    The main architectural decision is simple: clear priorities create more reliable behavior than many uncontrolled corrections fighting each other.
  </strong>
</p>
