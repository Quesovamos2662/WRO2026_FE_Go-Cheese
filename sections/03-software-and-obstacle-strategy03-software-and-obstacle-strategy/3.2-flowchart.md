Cheese v4 uses a **priority-based software structure**. This means the robot does not allow every behavior to control movement at the same time. Instead, the program checks the most important conditions first, such as front-wall safety, then continues into color detection, curve counting, obstacle logic, wall correction, and final parking.

The main flowchart gives the complete overview. The sub-flowcharts explain each important branch in more detail.

## ❀ Main Loop Control Cycle ────୨ৎ────────୨ৎ────

The main loop is the repeated decision cycle of the robot. It is where Cheese reads the environment, updates its internal state, and decides what movement should happen next.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/01_v4_main_loop_control_cycle.png" alt="Cheese v4 main loop control cycle flowchart" width="92%">
</p>

<p align="center">
  <em>Main loop flowchart showing the repeated order of safety checks, sensor readings, curve counting, parking checks, control decisions, motor commands, and loop delay.</em>
</p>

The main loop is important because Cheese does not follow a fixed movement script. It reacts continuously to sensor input.

<div align="center">

| Loop Step | Purpose |
| :---: | :--- |
| **1** | Check whether the robot should stop. |
| **2** | Read the front ultrasonic sensor for safety. |
| **3** | Run front-wall recovery if the robot is too close. |
| **4** | Read floor color in `COL-COLOR` mode. |
| **5** | Update the curve counter using BLUE/ORANGE transitions. |
| **6** | Read left and right ultrasonic sensors. |
| **7** | Check whether parking or finish logic should activate. |
| **8** | Run navigation control, PID correction, and obstacle extension if active. |
| **9** | Send motor commands and repeat the loop. |

</div>

## ❀ Color Detection and Curve Counting ────୨ৎ────────୨ৎ────

The color sensor is used to track progress around the field. Cheese v4 uses the color sensor in **COL-COLOR mode**, not RGB-RAW mode.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/02_v4_color_detection_curve_counting.png" alt="Cheese v4 color detection and curve counting flowchart" width="92%">
</p>

<p align="center">
  <em>Color detection and curve counting flowchart showing how BLUE and ORANGE floor events become valid curve counts.</em>
</p>

The current logic focuses on the two meaningful floor events:

<div align="center">

| Color Event | Meaning |
| :--- | :--- |
| **BLUE** | One side of the curve sequence. |
| **ORANGE** | The opposite side of the curve sequence. |

</div>

A valid curve is counted when Cheese detects an opposite-color sequence:

<div align="center">

| Valid Curve Sequence |
| :---: |
| **BLUE → ORANGE** |
| **ORANGE → BLUE** |

</div>

The counter includes protection against false readings.

<div align="center">

| Protection | Why It Matters |
| :--- | :--- |
| **Color window** | Prevents old color readings from combining into a fake curve. |
| **Cooldown** | Prevents one curve from being counted more than once. |
| **Steering confirmation** | Helps confirm that the robot was actually performing a curve-related movement. |
| **Movement continues during cooldown** | The counter pauses, but the robot keeps driving. |

</div>

## ❀ Minimum-Correction PID Controller ────୨ৎ────────୨ৎ────

Cheese v4 does not constantly chase the exact center of the track. Instead, it uses a **minimum-correction PID controller**.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/03_v4_minimum_correction_pid_controller.png" alt="Cheese v4 minimum-correction PID controller flowchart" width="92%">
</p>

<p align="center">
  <em>Minimum-correction PID flowchart showing how Cheese decides whether steering correction is necessary.</em>
</p>

The key idea is:

<p align="center">
  <strong>Drive straight by default. Correct only when the sensors show that correction is needed.</strong>
</p>

This reduces overreaction and helps prevent oscillation caused by noisy ultrasonic readings.

<div align="center">

| Condition | Response |
| :--- | :--- |
| **Path is safe** | Reset PID memory and drive straight. |
| **Side wall is too close** | Build a wall error and steer away from the close wall. |
| **Curve geometry is detected** | Use front distance and side opening to assist the curve. |
| **No correction is needed** | Avoid unnecessary steering. |
| **Correction is calculated** | Use proportional response and filtered derivative response. |

</div>

The current controller behaves mostly as a **P + filtered D** controller, while the integral term is disabled or minimized during calibration to avoid old steering influence carrying into later sections.

## ❀ Front Wall Safety and Reverse Recovery ────୨ৎ────────୨ৎ────

The front ultrasonic sensor has the highest safety priority. This branch exists to prevent the robot from pushing into a wall when it is too close in front.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/04_v4_front_wall_safety_reverse_recovery.png" alt="Cheese v4 front wall safety and reverse recovery flowchart" width="92%">
</p>

<p align="center">
  <em>Front-wall safety flowchart showing front distance reading, trigger check, reverse recovery, steering reset, and return to the main loop.</em>
</p>

This branch is checked before normal navigation because front collisions are more dangerous than small side-position errors.

<div align="center">

| Safety Step | Purpose |
| :---: | :--- |
| **1** | Read front ultrasonic distance. |
| **2** | Check whether the front wall is inside the trigger threshold. |
| **3** | Enter safety routine immediately if needed. |
| **4** | Reset PID and steering influence. |
| **5** | Reverse to create space. |
| **6** | Stop recovery when clearance is restored. |
| **7** | Return to the main loop. |

</div>

## ❀ Obstacle Detection and Camera Bias ────୨ৎ────────୨ৎ────

The Obstacle Challenge code adds the HuskyLens and Arduino Nano system to the normal navigation base.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/05_v4_obstacle_detection_camera_bias.png" alt="Cheese v4 obstacle detection and camera bias flowchart" width="92%">
</p>

<p align="center">
  <em>Obstacle detection flowchart showing HuskyLens/Nano data flow, packet validation, red/green ID rules, camera bias, and wall-safety limitation.</em>
</p>

The obstacle branch uses this data path:

<div align="center">

| Step | System | Role |
| :---: | :--- | :--- |
| **1** | HuskyLens | Detects trained red and green pillars. |
| **2** | Arduino Nano | Converts camera data into a simplified packet. |
| **3** | EV3 serial reader | Reads the newest packet. |
| **4** | EV3 navigation logic | Uses the packet to create camera steering bias. |
| **5** | Motors | Apply the final allowed steering and speed. |

</div>

Current obstacle rule:

<div align="center">

| Pillar | HuskyLens ID | Required Behavior |
| :--- | :---: | :--- |
| **Red pillar** | **ID 1** | Pass on the right. |
| **Green pillar** | **ID 2** | Pass on the left. |

</div>

The Arduino Nano sends simplified packets such as:

<div align="center">

| Packet | Meaning |
| :--- | :--- |
| `R,xCenter,width` | Red pillar detected. |
| `G,xCenter,width` | Green pillar detected. |
| `N,0,0` | No valid pillar detected. |

</div>

This branch is still being calibrated. The main current issues are camera angle, delayed detection, recovery after avoidance, and obstacle parking.

## ❀ Parking and Finish Logic ────୨ৎ────────୨ৎ────

Parking is treated as its own software branch because the robot must not simply stop randomly after driving three laps. It must stop after completing the required progress and return to the correct final area.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/06_v4_parking_finish_logic.png" alt="Cheese v4 parking and finish logic flowchart" width="92%">
</p>

<p align="center">
  <em>Parking and finish flowchart showing completion check, parking mode, starting-distance reference, final section check, and controlled stop.</em>
</p>

Parking depends on the curve counter and starting-distance references.

<div align="center">

| Parking Element | Role |
| :--- | :--- |
| **Completed curves** | Confirms that the required progress has been reached. |
| **`TOTAL_CURVES = 12`** | Represents the full three-lap target. |
| **Starting front distance** | Main reference for detecting the finish area. |
| **Side distances** | Optional sanity check for alignment. |
| **Parking speed** | Keeps the final approach controlled. |
| **Stop and hold** | Ends the run inside the final section. |

</div>

The main remaining parking challenge is final alignment. The robot can finish inside the correct area, but if earlier curve counting is inaccurate, parking may activate too early or too late.

## ❀ Sensor Validation and Reliability Protections ────୨ৎ────────୨ৎ────

Real sensor readings are not perfect. Because of this, Cheese v4 includes validation and reliability logic before sensor data is allowed to influence movement.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/07_v4_sensor_validation_reliability.png" alt="Cheese v4 sensor validation and reliability flowchart" width="92%">
</p>

<p align="center">
  <em>Reliability flowchart showing ultrasonic validation, fallback behavior, stale camera packet rejection, PID reset, and safe degraded operation.</em>
</p>

The purpose of this layer is not to make every sensor reading perfect. The purpose is to keep Cheese safe when readings are imperfect.

<div align="center">

| Reliability Protection | Why It Matters |
| :--- | :--- |
| **Ultrasonic range validation** | Rejects readings outside the usable physical range. |
| **Sensor filtering** | Reduces sudden jumps in wall distance. |
| **Color stability logic** | Prevents random color flashes from being accepted too easily. |
| **Cooldown after curve count** | Prevents duplicate curve counts. |
| **Fresh camera packet check** | Prevents old obstacle data from steering the robot. |
| **Minimum obstacle width** | Rejects tiny or weak detections. |
| **Fallback behavior** | Allows safer behavior when one or more readings are unreliable. |
| **PID reset after major events** | Prevents old correction memory from affecting the next section. |

</div>

This reliability layer supports the engineering goal of making Cheese predictable under real field conditions.

## ❀ How These Flowcharts Support Debugging ────୨ৎ────────୨ৎ────

The flowcharts are not only decorative. They are used as debugging maps.

<div align="center">

| If Cheese Fails During... | Team Should Check... |
| :--- | :--- |
| **Straight driving** | Main loop, PID controller, ultrasonic validation, side-wall readings. |
| **Curve counting** | Color detection, BLUE/ORANGE sequence, cooldown, steering confirmation. |
| **Front-wall approach** | Front wall safety threshold and reverse recovery behavior. |
| **Obstacle avoidance** | HuskyLens/Nano packets, ID rule, camera bias, wall safety limit. |
| **Parking** | Completed curve count, starting-distance memory, front reference, final alignment. |
| **Random steering behavior** | PID reset, stale camera packet rejection, sensor filtering. |

</div>

This makes the flowchart section an engineering tool. Each diagram connects a real behavior on the mat to a specific part of the code.
