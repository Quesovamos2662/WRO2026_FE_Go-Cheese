The Open Challenge is currently one of Cheese v4's most developed software modes.

The objective is not simply to drive around the field for a fixed amount of time.

Cheese must understand its own progress, maintain a safe trajectory, recover when necessary, complete **three laps**, and return to the parking region.

The current Open logic can be summarized as:

```text
START
  ↓
SAVE STARTING DISTANCES
  ↓
DRIVE
  ↓
READ ULTRASONICS + COLOR
  ↓
CORRECT ONLY WHEN NEEDED
  ↓
DETECT VALID CURVES
  ↓
COUNT PROGRESS
  ↓
12 CURVES REACHED
  ↓
ENTER PARKING MODE
  ↓
MATCH STARTING REGION
  ↓
STOP
```

Current testing shows that Cheese can complete the three-lap Open run with relatively stable behavior.

The parking system normally finishes inside the correct area, although final alignment can still be slightly angled.

# ❀ 3.3.1 Open Challenge Objective ────୨ৎ────────୨ৎ────

The Open Challenge contains no red or green obstacle pillars.

This means the camera system is not needed for normal Open navigation.

The challenge therefore focuses on autonomous driving and progress tracking.

<div align="center">

| Objective | Meaning |
| :--- | :--- |
| **Complete three laps** | Cheese must complete the required full run |
| **Avoid side walls** | Lateral ultrasonic sensors help maintain safe clearance |
| **Avoid front collisions** | The front ultrasonic provides forward protection |
| **Count curves correctly** | Floor colors are used to track run progress |
| **Recover when necessary** | Cheese can reverse if forward space becomes unsafe |
| **Activate parking correctly** | Parking begins only after the required progress |
| **Stop inside the target area** | Final movement becomes slower and more precise |

</div>

The main design target is:

<p align="center">
  <strong>
    Repeatable completion before maximum speed.
  </strong>
</p>

# ❀ 3.3.6 Starting Procedure ────୨ৎ────────୨ৎ────

Before moving, Cheese waits for the start command.

This allows the robot to be positioned correctly before the run begins.

After starting, the robot samples its surrounding distances.

The starting references include:

<div align="center">

| Starting Reference | Purpose |
| :--- | :--- |
| **Left distance** | Side reference |
| **Right distance** | Side reference |
| **Front distance** | Main finish / parking reference |

</div>

Multiple readings are sampled instead of trusting only one measurement.

The objective is to reduce the influence of one noisy ultrasonic value.

Conceptually:

```text
READ
READ
READ
READ
READ
   ↓
REMOVE UNRELIABLE VALUES
   ↓
SELECT REPRESENTATIVE DISTANCE
   ↓
SAVE START REFERENCE
```

These stored values become important again after the three laps are complete.

# ❀ 3.3.10 Color Interpretation ────୨ৎ────────୨ৎ────

The physical track contains blue and orange curve markers.

However, the EV3's built-in classification may identify the physical orange marker as different warm colors.

The software therefore interprets:

<div align="center">

| EV3 Reading | Open Meaning |
| :--- | :--- |
| **Blue** | `BLUE` |
| **Red** | `ORANGE` |
| **Yellow** | `ORANGE` |
| **Brown** | `ORANGE` |
| Other | Ignored |

</div>

This creates a more tolerant interpretation:

```text
PHYSICAL ORANGE
      ↓
RED / YELLOW / BROWN
      ↓
SOFTWARE GROUP
      ↓
ORANGE
```

This allows the software to adapt to the real sensor rather than expecting perfect classification.

<p align="center">

<p align="center">

A curve is not counted from one isolated color.

The current system expects opposite-color progression:

```text

```


```text
FIRST COLOR
    ↓
STORE IT
    ↓
SECOND COLOR
    ↓
OPPOSITE?
    ↓
WITHIN TIME WINDOW?
    ↓
STEERING CONFIRMED?
    ↓
COUNT CURVE
    ↓
COOLDOWN
```

# ❀ 3.3.13 Why Curve Counting Needs Protection ────୨ৎ────────୨ৎ────

One incorrect count can affect the entire finish.

### Duplicate count

```text
ONE PHYSICAL CURVE
      ↓
COUNTED TWICE
      ↓
TOTAL REACHES 12 TOO EARLY
      ↓
PARKING ACTIVATES TOO EARLY
```

### Missed count

```text
ONE CURVE MISSED
      ↓
TOTAL STAYS TOO LOW
      ↓
ROBOT PASSES FINISH REGION
      ↓
PARKING ACTIVATES TOO LATE
```

The current protections reduce these risks.

<div align="center">

| Protection | Purpose |
| :--- | :--- |
| **Opposite-color requirement** | Reject repeated same-color events |
| **3.0 s window** | Prevent old events from pairing |
| **Steering confirmation** | Connect color sequence to physical turning |
| **Post-color window** | Allow slightly delayed steering confirmation |
| **Cooldown** | Prevent duplicate counts |

</div>

# ❀ 3.3.15 Ultrasonic Filtering ────୨ৎ────────୨ৎ────

Ultrasonic readings can fluctuate slightly.

Using every raw value directly could produce unstable steering.

Current filtering values include:

<div align="center">

| Parameter | Value |
| :--- | :---: |
| **Sensor filter alpha** | **0.65** |
| **Derivative filter** | **0.45** |
| **Loop delay** | **0.01 s** |

</div>

The control chain becomes:

```text
RAW DISTANCE
     ↓
VALIDATE
     ↓
FILTER
     ↓
CALCULATE ERROR
     ↓
PID
     ↓
STEERING
```

This makes the controller less sensitive to short sensor spikes.

# ❀ 3.3.20 Why Recovery Matters ────୨ৎ────────୨ৎ────

A successful safety event is not just:

```text

```

It should be:

```text
AVOID CRASH
     ↓
CREATE SPACE
     ↓
RESTORE USEFUL POSITION
     ↓
CONTINUE THE RUN
```

Recovery is therefore treated as part of navigation rather than only as an emergency stop.

# ❀ 3.3.24 Curve Count → Parking Dependency ────୨ৎ────────୨ৎ────

Parking and curve counting are strongly connected.

```text
COLOR SENSOR
      ↓
VALID CURVE
      ↓
COMPLETED_CURVES
      ↓
12?
      ↓
PARKING MODE
```

This creates a systems dependency.

If the count is wrong, even perfect parking distance logic may activate at the wrong time.

Therefore:

> **Parking reliability begins with curve-count reliability.**

# ❀ 3.3.25 Battery Condition ────୨ৎ────────୨ৎ────

Battery condition can affect Open behavior even if none of the constants change.

A lower battery can change:

- drive response,
- steering response,
- acceleration,
- recovery strength,
- and timing.

This means:

```text
SAME CODE
   +
DIFFERENT BATTERY CONDITION
   ↓
SLIGHTLY DIFFERENT PHYSICAL RESPONSE
```

Battery state is therefore considered during testing before deciding that a software value needs to be changed.

# ❀ 3.3.27 Failure → Cause → Fix Examples ────୨ৎ────────୨ৎ────

The Open Challenge evolved through repeated testing.

<div align="center">

| Observation | Likely Cause | Adjustment | Result |
| :--- | :--- | :--- | :--- |
| Robot zig-zagged | Too much constant correction | Minimum-correction PID | Straighter normal motion |
| Wall approached too closely | Normal PID reacted too late | Progressive wall protection | Earlier response |
| Front wall trapped robot | Steering had insufficient space | Reverse recovery | Physical room restored |
| Orange was inconsistent | EV3 warm-color classification varied | Red + Yellow + Brown grouped | More tolerant detection |
| Curves could count incorrectly | Raw color event was insufficient | Timing + sequence + steering confirmation | Better counting |
| Parking could activate incorrectly | Progress depended on curve count | Stronger validation | Better finish timing |
| Parking ended slightly angled | Final movement still had steering/speed influence | Slower creep + steering limit | Improved final approach |

</div>

This follows the engineering chain:

```text
FAILURE
   ↓
CAUSE
   ↓
RISK
   ↓
CHANGE
   ↓
TEST
   ↓
RESULT
```

# ✦ Engineering Lessons ─── ⋆⋅☆⋅⋆ ───

### 1. Progress and navigation should be separated

The color sensor tracks progress.

The ultrasonic sensors and PID control movement.

This prevents floor detection from directly determining steering.

---

### 2. More steering does not always improve navigation

Minimal useful correction produced more stable movement than constantly trying to correct every small sensor difference.

---

### 3. Safety should become stronger progressively

A robot should react before it reaches collision distance.

---

### 4. Sometimes recovery requires moving backward

When there is no physical space available for steering, reversing can be the correct navigation action.

---

### 5. Parking begins long before the parking area

A reliable final stop depends on correct curve counting throughout the entire run.

---

### 6. Repeatability matters more than one perfect test

A single successful run proves that Cheese **can** complete the Open Challenge.

Repeated successful runs show that the system is becoming reliable.

---

# ✦ 3.3 Open Challenge Summary ─── ⋆⋅☆⋅⋆ ───

Cheese v4 solves the Open Challenge using a combination of:

- three ultrasonic sensors,
- an EV3 Color Sensor,
- validated BLUE / ORANGE curve detection,
- minimum-correction PID,
- progressive wall protection,
- front-distance safety,
- reverse recovery,
- 12-curve progress tracking,
- stored starting-distance references,
- and progressive final parking.

The Open Challenge is currently one of the strongest parts of Cheese v4.

The robot is capable of completing the required three laps and returning to the parking region with relatively stable behavior.

The remaining improvements are mainly related to:

- curve-count consistency,
- final parking angle,
- and maintaining repeatability under changing battery and track conditions.

The central Open Challenge logic can be summarized as:

<p align="center">
  <strong>
    Navigate safely → Validate progress → Complete 12 curves → Return → Park
  </strong>
</p>
