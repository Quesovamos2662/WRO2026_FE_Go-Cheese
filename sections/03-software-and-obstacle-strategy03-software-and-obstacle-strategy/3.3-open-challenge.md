The Open Challenge is currently one of Cheese v4's most developed software modes.

The objective is not simply to drive around the field for a fixed amount of time.

Cheese must understand its own progress, maintain a safe trajectory, recover when necessary, complete **three laps**, and return to the parking region.

<p align="center">
  <strong>
    Navigate safely → Validate progress → Complete 12 curves → Return → Park
  </strong>
</p>

Current testing shows that Cheese can complete the three-lap Open run with relatively stable behavior.

The parking system normally finishes inside the correct area, although final alignment can still be slightly angled.

# ❀ 3.3.1 Open Challenge Objective ────୨ৎ────────୨ৎ────

The Open Challenge contains no red or green obstacle pillars.

This means the camera system is not required for normal Open navigation.

The challenge therefore focuses on autonomous driving, wall awareness, progress tracking, recovery, and final parking.

<div align="center">

| Objective | Meaning |
| :--- | :--- |
| **Complete three laps** | Cheese must complete the required full run |
| **Avoid side walls** | Lateral ultrasonic sensors help maintain safe clearance |
| **Avoid front collisions** | The front ultrasonic provides forward protection |
| **Count curves correctly** | Floor colors are used to track run progress |
| **Recover when necessary** | Cheese can reverse if forward space becomes unsafe |
| **Activate parking correctly** | Parking begins only after the required progress |
| **Stop inside the target area** | Final movement becomes slower and more precise |

</div>

The main design target is:

<p align="center">
  <strong>
    Repeatable completion before maximum speed.
  </strong>
</p>

# ❀ 3.3.6 Starting Procedure ────୨ৎ────────୨ৎ────

Before moving, Cheese waits for the start command.

This allows the robot to be positioned correctly before the run begins.

After starting, the robot samples its surrounding distances.

<div align="center">

| Starting Reference | Purpose |
| :--- | :--- |
| **Left distance** | Side reference |
| **Right distance** | Side reference |
| **Front distance** | Main finish / parking reference |

</div>

Multiple readings are sampled instead of trusting only one measurement.

The objective is to reduce the influence of a noisy ultrasonic value.

<p align="center">
  <strong>
    Multiple Readings → Reject Unreliable Values → Select Reference → Save
  </strong>
</p>

These stored values become important again after the three laps are complete.

# ❀ 3.3.10 Color Interpretation ────୨ৎ────────୨ৎ────

The physical track contains blue and orange curve markers.

However, the EV3 built-in classification may identify the physical orange marker as different warm colors.

The software therefore interprets:

<div align="center">

| EV3 Reading | Open Meaning |
| :--- | :--- |
| **Blue** | `BLUE` |
| **Red** | `ORANGE` |
| **Yellow** | `ORANGE` |
| **Brown** | `ORANGE` |
| Other | Ignored |

</div>

This creates a tolerant interpretation:

<p align="center">
  <strong>
    Physical Orange → Red / Yellow / Brown readings → Software ORANGE
  </strong>
</p>

The software therefore adapts to the real sensor instead of expecting perfect classification.

# ❀ 3.3.13 Why Curve Counting Needs Protection ────୨ৎ────────୨ৎ────

One incorrect count can affect the entire finish.

### Duplicate count

<p align="center">
  <strong>
    One Physical Curve → Counted Twice → 12 Reached Early → Parking Starts Early
  </strong>
</p>

### Missed count

<p align="center">
  <strong>
    Curve Missed → Count Too Low → Finish Region Passed → Parking Starts Late
  </strong>
</p>

The current protections reduce these risks.

<div align="center">

| Protection | Purpose |
| :--- | :--- |
| **Opposite-color requirement** | Reject repeated same-color events |
| **3.0 s window** | Prevent old events from pairing |
| **Steering confirmation** | Connect the color sequence to physical turning |
| **Post-color window** | Allow slightly delayed steering confirmation |
| **Cooldown** | Prevent duplicate counts |

</div>

# ❀ 3.3.14 Minimum-Correction PID ────୨ৎ────────୨ৎ────

Open navigation uses a minimum-correction PID philosophy.

<p align="center">
  <em>
    Minimum-correction PID logic used during Open navigation.

The key idea is:

<p align="center">
  <strong>
    If Cheese is already safe, do not create unnecessary steering.
  </strong>
</p>

<div align="center">

| Situation | Response |
| :--- | :--- |
| **Safe / centered enough** | Drive mostly straight |
| **Useful distance error** | Apply PID correction |
| **Wall risk** | Apply stronger protective correction |

</div>

Current PID values are:

<div align="center">

| Constant | Value |
| :--- | :---: |
| **KP** | **0.28** |
| **KI** | **0.001** |
| **KD** | **0.08** |

| **Maximum PID angle** | **32°** |

</div>

# ❀ 3.3.15 Ultrasonic Filtering ────୨ৎ────────୨ৎ────

Ultrasonic readings can fluctuate slightly.

Using every raw value directly could produce unstable steering.

Current filtering values include:

<div align="center">

| Parameter | Value |
| :--- | :---: |
| **Sensor filter alpha** | **0.65** |
| **Derivative filter** | **0.45** |
| **Loop delay** | **0.01 s** |

</div>

The control chain becomes:

<p align="center">
  <strong>
    Raw Distance → Validate → Filter → Calculate Error → PID → Steering
  </strong>
</p>

This makes the controller less sensitive to short sensor spikes.

# ❀ 3.3.18 Open Corner Handling ────୨ৎ────────୨ৎ────

Corners are one of the most important physical events in the Open Challenge.

A successful corner must allow Cheese to:

- enter without excessive steering,
- stay clear of the inner wall,
- avoid opening too far toward the outer wall,
- complete the turn,
- and return to stable navigation afterward.

<p align="center">
  <img src="../../v-photos/v4/curve_demonstration_v4.gif"
       alt="Cheese v4 Open Challenge curve demonstration"
       width="78%">
</p>

<p align="center">
  <em>
    Real Open Challenge corner demonstration showing Cheese physically entering,
    executing and leaving a curve.
  </em>
</p>

The current corner philosophy is:

<p align="center">
  <strong>
    Turn Only as Much as Needed → Clear Corner → Release Steering → Return to PID
  </strong>
</p>

Open corner recovery is not based on forcing a completely separate maneuver after every turn.

Instead, the robot normally returns to its **minimum-correction PID and wall-protection logic** once the corner geometry becomes safe again.

  <strong>

# ❀ 3.3.26 Battery Condition ────୨ৎ────────୨ৎ────

Battery condition can affect Open behavior even if none of the software constants change.

A lower battery can affect:

- drive response,
- steering response,
- acceleration,
- recovery strength,
- and timing.

<p align="center">
  <strong>
    Same Code + Different Battery Condition = Different Physical Response
  </strong>
</p>

Battery state is therefore considered during testing before deciding that a software value must be changed.

# ❀ 3.3.28 Failure → Cause → Fix ────୨ৎ────────୨ৎ────

The Open Challenge evolved through repeated testing.

<div align="center">

| Observation | Likely Cause | Adjustment | Result |
| :--- | :--- | :--- | :--- |
| Robot zig-zagged | Too much constant correction | Minimum-correction PID | Straighter normal motion |
| Wall approached too closely | Normal PID reacted too late | Progressive wall protection | Earlier response |
| Front wall trapped robot | Steering had insufficient physical space | Reverse recovery | Physical room restored |
| Orange was inconsistent | EV3 warm-color classification varied | Red + Yellow + Brown grouped | More tolerant detection |
| Curves could count incorrectly | Raw color event was insufficient | Timing + sequence + steering confirmation | Better counting |
| Parking could activate incorrectly | Progress depended on curve count | Stronger count validation | Better finish timing |
| Parking ended slightly angled | Final speed and steering still influenced pose | Slower creep + steering limit | Improved final approach |

</div>

The engineering process follows:

<p align="center">
  <strong>
    Failure → Cause → Risk → Change → Test → Result
  </strong>
</p>

Corner quality strongly affects the next part of the run.

A poor exit can leave Cheese:

- too close to the inner wall,
- too far toward the outer wall,
- at an incorrect heading,
- or requiring excessive PID correction afterward.

A better corner creates the opposite effect:

<p align="center">
  <strong>
    Clean Entry → Controlled Turn → Useful Exit Heading → Stable PID Recovery
  </strong>
</p>

This is why corner tuning is treated as a full navigation problem rather than only a steering-angle problem.

# ❀ 3.3.32 Testing Strategy ────୨ৎ────────୨ৎ────

Open Challenge testing is divided into stages.

<div align="center">

| Stage | Test | Success Condition |
| :---: | :--- | :--- |
| **1** | Straight movement | No major uncontrolled drift |
| **2** | Side ultrasonic response | Stable useful wall readings |
| **3** | Front safety | Correct reverse recovery |
| **4** | Color recognition | Reliable BLUE / ORANGE interpretation |
| **5** | One curve | Exactly one valid count |
| **6** | Four curves | One complete lap counted correctly |
| **7** | One complete lap | Stable navigation |
| **8** | Three laps | 12 valid curves |
| **9** | Parking | Stops inside region |
| **10** | Repeatability | Similar result across repeated runs |

</div>

Testing subsystems separately makes failures easier to diagnose.

The final stage is always real-field integration.

# ✦ Engineering Lessons ─── ⋆⋅☆⋅⋆ ───

### 1. Progress and navigation should be separated

The color sensor tracks progress.

The ultrasonic sensors and PID control movement.

This prevents floor detection from directly controlling steering.

---

### 2. More steering does not always improve navigation

Minimal useful correction produced more stable movement than constantly trying to correct every small sensor difference.

---

### 3. Safety should become stronger progressively

A robot should begin reacting before it reaches collision distance.

---

### 4. Sometimes recovery requires moving backward

When there is no physical space available for steering, reversing can be the correct navigation action.

---

### 5. Parking begins long before the parking area

A reliable final stop depends on correct curve counting throughout the entire run.

---

### 6. A corner affects more than the corner itself

The robot's exit heading determines the quality of the next straight section.

A poor corner can create unnecessary PID corrections or wall risk afterward.

---

### 7. Visual testing evidence matters

Flowcharts explain the intended architecture.

Real-track GIFs demonstrate how the physical system behaves when those algorithms interact with the actual field.

---

### 8. Repeatability matters more than one perfect test

A single successful run proves that Cheese **can** complete the Open Challenge.

Repeated successful runs show that the system is becoming reliable.

# ✦ 3.3 Open Challenge Summary ─── ⋆⋅☆⋅⋆ ───

Cheese v4 solves the Open Challenge using a combination of:

- three ultrasonic sensors,
- an EV3 Color Sensor,
- validated BLUE / ORANGE curve detection,
- minimum-correction PID,
- progressive wall protection,
- controlled Ackermann steering,
- front-distance safety,
- reverse recovery,
- 12-curve progress tracking,
- stored starting-distance references,
- and progressive final parking.

The Open Challenge is currently one of the strongest parts of Cheese v4.

The robot is capable of completing the required three laps and returning to the parking region with relatively stable behavior.

The addition of real Open Challenge GIFs strengthens the documentation by connecting the software architecture to the physical behavior of the robot on the field.

The remaining improvements are mainly related to:

- curve-count consistency,
- final parking angle,
- maintaining clean corner exits,
- and repeatability under changing battery and track conditions.
