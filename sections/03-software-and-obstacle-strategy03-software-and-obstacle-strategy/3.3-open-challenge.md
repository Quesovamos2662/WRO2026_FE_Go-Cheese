The current Open Challenge code is a **Cheese v4 calibration version** focused on progressive wall avoidance, curve-count reliability, reverse recovery, and finish positioning. In the source file, the program is identified as an Open Challenge test using Python 3.5.3 and ev3dev2. :contentReference[oaicite:0]{index=0}

The Open Challenge is currently one of Cheese’s strongest modes. In testing, the robot is able to complete the required **three laps** almost consistently. The parking system also stops inside the correct area, although the robot may sometimes finish slightly angled. The biggest current Open Challenge risks are wall contact during difficult sections and parking alignment depending on accurate curve counting and finish detection.

---

## ❀ 3.3.1 Open Challenge Objective ────୨ৎ────────୨ৎ────

The Open Challenge does not include red or green obstacle pillars. Because of this, the robot does not need to make obstacle-passing decisions. Instead, the software focuses on stable autonomous navigation.

The Open Challenge objectives for Cheese v4 are:

<div align="center">

| Objective | Meaning |
| :--- | :--- |
| **Complete three laps** | The robot must drive around the field for the required number of laps. |
| **Avoid wall collisions** | The robot must correct its path before touching side or front walls. |
| **Count curves correctly** | The robot uses floor-color events to track progress. |
| **Handle front-wall danger** | The front ultrasonic sensor can trigger reverse recovery. |
| **Enter parking mode after completion** | Parking begins only after the required curve count is reached. |
| **Stop inside the final area** | The robot should finish inside the correct section without passing the target. |

</div>

The main design goal is not only speed. The robot must be predictable, repeatable, and safe enough to finish the run.

## ❀ 3.3.4 Hardware Used in Open Challenge ────୨ৎ────────୨ৎ────

The Open Challenge code uses the EV3 Brick, two motors, three ultrasonic sensors, and one color sensor.

<div align="center">

| Component | Port | Role in Open Challenge |
| :--- | :---: | :--- |
| **Medium Motor** | `OUTPUT_A` | Controls Ackermann steering. |
| **Large Motor** | `OUTPUT_B` | Drives the robot forward through the rear drive system. |
| **Left Ultrasonic Sensor** | `INPUT_1` | Reads the left wall distance. |
| **Right Ultrasonic Sensor** | `INPUT_2` | Reads the right wall distance. |
| **Front Ultrasonic Sensor** | `INPUT_3` | Detects front-wall danger and supports front-distance logic. |
| **Color Sensor** | `INPUT_4` | Detects floor colors for curve counting. |

</div>

The code confirms this v4 hardware map and sets all three ultrasonic sensors to `US-DIST-CM`, while the color sensor uses `COL-COLOR`. :contentReference[oaicite:1]{index=1}

## ❀ 3.3.5 Open Challenge Flow Overview ────୨ৎ────────୨ৎ────

The Open Challenge logic follows a repeated sensor-based control loop. It does not simply drive for a fixed amount of time.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/08_v4_main_software_flowchart.png" alt="Cheese v4 main software flowchart" width="95%">
</p>

<p align="center">
  <em>Main Cheese v4 software flowchart showing the complete Open Challenge navigation base and finish logic.</em>
</p>

The Open Challenge flow can be summarized as:

<div align="center">

| Step | Action |
| :---: | :--- |
| **1** | Wait for the EV3 start button. |
| **2** | Memorize starting distances from the left, right, and front ultrasonic sensors. |
| **3** | Begin the main loop. |
| **4** | Read ultrasonic sensors and floor color. |
| **5** | Run front-wall recovery if the robot is too close to the front wall. |
| **6** | Update the curve counter using the color sensor. |
| **7** | Check whether parking mode should activate. |
| **8** | Run sensor-fusion PID and wall protection. |
| **9** | Repeat until the finish condition is reached. |
| **10** | Stop the robot safely. |

</div>

The actual loop follows this structure: it reads distances, checks front collision recovery, updates the curve counter, activates parking mode after enough curves, checks finish position, runs sensor-fusion PID, and sleeps for the loop delay. :contentReference[oaicite:2]{index=2}

## ❀ 3.3.6 Starting Procedure and Distance Memory ────୨ৎ────────୨ৎ────

Before driving, Cheese waits for the start button. This prevents the robot from starting before the team has placed it correctly on the mat.

After the start command, the robot memorizes its starting distances. This is important because the parking logic later uses these starting references to recognize the finish area.

<div align="center">

| Starting Reference | Purpose |
| :--- | :--- |
| **Starting left distance** | Stored as a side reference. |
| **Starting right distance** | Stored as a side reference. |
| **Starting front distance** | Used as the main finish reference. |
| **Median sampling** | Reduces the effect of one bad ultrasonic reading. |

</div>

The code samples left, right, and front ultrasonic distances multiple times, then stores median values as `start_left_distance`, `start_right_distance`, and `start_front_distance`. :contentReference[oaicite:3]{index=3}

This starting memory makes parking more reliable than using time alone.

## ❀ 3.3.7 Main Movement Speeds ────୨ৎ────────୨ৎ────

The Open Challenge code uses different speeds for different situations.

<div align="center">

| Speed Constant | Value | Use |
| :--- | :---: | :--- |
| `NORMAL_SPEED` | `-62` | Normal Open Challenge driving. |
| `GENTLE_WALL_SPEED` | `-44` | Slower speed during moderate wall correction. |
| `SEVERE_WALL_SPEED` | `-24` | Stronger slow-down when the robot is close to danger. |
| `PARKING_SPEED` | `-28` | Controlled speed during parking approach. |
| `PARKING_MEDIUM_SPEED` | `-18` | Slower parking speed near the saved finish reference. |
| `PARKING_CREEP_SPEED` | `-10` | Very slow final approach close to the target. |
| `EMERGENCY_REVERSE_SPEED` | `28` | Reverse speed during front-wall recovery. |

</div>

These values are defined in the Open Challenge code as movement and PID constants. :contentReference[oaicite:4]{index=4}

The use of multiple speeds is important because the robot should not move with the same aggressiveness in every situation. A clear straight section can be faster, but wall danger and final parking need slower motion.

## ❀ 3.3.8 Color-Based Curve Counting ────୨ৎ────────୨ৎ────

The Open Challenge depends heavily on curve counting. Cheese uses the floor color sensor to detect curve-related events.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/02_v4_color_detection_curve_counting.png" alt="Cheese v4 color detection and curve counting flowchart" width="92%">
</p>

<p align="center">
  <em>Color detection and curve counting flowchart showing how BLUE and ORANGE floor events become valid curve counts.</em>
</p>

The current code reads the EV3 color sensor in `COL-COLOR` mode. A blue reading becomes `BLUE`. Red, yellow, and brown readings are grouped as `ORANGE`, because the orange floor marker may be classified differently depending on lighting and sensor conditions. :contentReference[oaicite:5]{index=5}

<div align="center">

| Sensor Reading | Open Logic Meaning |
| :--- | :--- |
| **Blue** | `BLUE` |
| **Red** | `ORANGE` |
| **Yellow** | `ORANGE` |
| **Brown** | `ORANGE` |
| **Other / none** | ignored |

</div>

A valid curve sequence must use opposite colors:

<div align="center">

| Valid Sequence |
| :---: |
| **BLUE → ORANGE** |
| **ORANGE → BLUE** |

</div>

## ❀ 3.3.9 Curve Counter Protections ────୨ৎ────────୨ৎ────

The curve counter includes several protections because one wrong count can affect the entire run and parking timing.

<div align="center">

| Protection | Current Value / Behavior | Purpose |
| :--- | :---: | :--- |
| **Total curve target** | `12` | Represents the full Open Challenge progress target. |
| **Color-change window** | `3.0 s` | The opposite colors must appear close enough in time. |
| **Curve cooldown** | `1.5 s` | Prevents the same curve from being counted repeatedly. |
| **Post-color steering window** | `0.9 s` | Allows steering confirmation shortly after the second color. |
| **Minimum steering time** | `0.03 s` | Confirms that steering was not only a tiny accidental movement. |

</div>

These constants are defined in the curve counter section of the code. :contentReference[oaicite:6]{index=6}

The current counter does more than detect colors. It stores the first curve color, waits for an opposite color, checks whether the transition happened inside the allowed time window, and uses steering confirmation before registering the curve. :contentReference[oaicite:7]{index=7}

This prevents three common errors:

<div align="center">

| Possible Error | How the Code Reduces It |
| :--- | :--- |
| **False color flash** | The color must fit the sequence logic. |
| **Old color pairing** | The transition must happen within the `3.0 s` window. |
| **Duplicate curve count** | The cooldown blocks repeated counts from the same event. |

</div>

## ❀ 3.3.10 Sensor-Fusion PID and Wall Control ────୨ৎ────────୨ৎ────

The Open Challenge code does not rely on only one sensor. It combines side-wall readings and front-wall information into a sensor-fusion correction model.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/03_v4_minimum_correction_pid_controller.png" alt="Cheese v4 minimum correction PID controller flowchart" width="92%">
</p>

<p align="center">
  <em>Minimum-correction PID flowchart showing how Cheese decides when steering correction is necessary.</em>
</p>

The current Open code builds a fused error using left, right, and front ultrasonic readings. The left and right sensors are used to estimate side error, while the front sensor can add assist when the front wall is becoming relevant. :contentReference[oaicite:8]{index=8}

The PID calculation uses:

<div align="center">

| PID Constant | Value | Role |
| :--- | :---: | :--- |
| `KP` | `0.28` | Proportional response to present error. |
| `KI` | `0.001` | Small integral response, limited to avoid excessive stored correction. |
| `KD` | `0.08` | Derivative response to error change. |
| `MAX_PID_ANGLE` | `32` | Maximum normal PID steering angle. |

</div>

The PID and loop constants are defined in the movement section of the code. :contentReference[oaicite:9]{index=9}

Unlike a simple constant-centering system, this version also softens steering, slows down when the robot is near walls, and uses immediate raw-distance protection when a side wall becomes dangerous. :contentReference[oaicite:10]{index=10}

## ❀ 3.3.11 Progressive Wall Protection ────୨ৎ────────୨ৎ────

Wall protection is one of the most important parts of Open Challenge reliability. Cheese can sometimes approach a wall too closely after a curve or because of sensor and steering delay.

The current code uses progressive thresholds:

<div align="center">

| Wall Protection Value | Current Value | Meaning |
| :--- | :---: | :--- |
| `WALL_GENTLE_DISTANCE` | `28.0 cm` | Correction begins earlier. |
| `WALL_SEVERE_DISTANCE` | `22.0 cm` | Stronger wall protection becomes necessary. |
| `FULL_WALL_AVOIDANCE_CM` | `15.0 cm` | Full wall avoidance reference. |
| `GENTLE_WALL_ANGLE` | `14°` | Moderate protective steering. |
| `SEVERE_WALL_ANGLE` | `18°` | Stronger protective steering. |

</div>

This makes wall correction gradual instead of sudden. When the robot is only slightly close to a wall, it corrects gently. When the robot is dangerously close, the correction becomes stronger and the robot slows down.

The code also resets stored PID force during raw-distance wall danger so the robot does not keep turning after it leaves the wall. :contentReference[oaicite:11]{index=11}

## ❀ 3.3.12 Front Wall Safety and Reverse Recovery ────୨ৎ────────୨ৎ────

The front ultrasonic sensor is a safety system. It protects Cheese from driving directly into the front wall.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/04_v4_front_wall_safety_reverse_recovery.png" alt="Cheese v4 front wall safety and reverse recovery flowchart" width="92%">
</p>

<p align="center">
  <em>Front-wall safety and reverse recovery flowchart showing how the robot creates space before returning to normal movement.</em>
</p>

The current front recovery constants are:

<div align="center">

| Constant | Value | Purpose |
| :--- | :---: | :--- |
| `FRONT_TOO_CLOSE_CM` | `10.0 cm` | Trigger distance for front danger. |
| `FRONT_RECOVERY_DISTANCE_CM` | `30.0 cm` | Target safe distance after reversing. |
| `FRONT_RECOVERY_CONFIRMATIONS` | `3` | Requires repeated safe readings. |
| `FRONT_RECOVERY_TIMEOUT` | `1.8 s` | Prevents the robot from reversing forever. |
| `REVERSE_MAX_STEER` | `10.0°` | Limits steering angle during reverse recovery. |

</div>

These constants are defined in the front collision recovery section of the code. :contentReference[oaicite:12]{index=12}

When front recovery activates, the robot resets PID, keeps only a limited amount of previous steering, reverses, waits for safe front distance or timeout, then centers steering and resumes the loop. :contentReference[oaicite:13]{index=13}

This branch has high priority because a front collision can stop the entire run.

## ❀ 3.3.13 Parking and Finish Logic ────୨ৎ────────୨ৎ────

Parking is treated as its own final behavior. It is not just a timer at the end of the run.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/06_v4_parking_finish_logic.png" alt="Cheese v4 parking and finish logic flowchart" width="92%">
</p>

<p align="center">
  <em>Parking and finish logic flowchart showing completion check, parking mode, starting-distance reference, and controlled final stop.</em>
</p>

Parking begins when the curve counter reaches the full target:

<div align="center">

| Parking Trigger | Meaning |
| :--- | :--- |
| `completed_curves >= TOTAL_CURVES` | Cheese has reached the required Open Challenge progress. |
| `TOTAL_CURVES = 12` | Three laps with four main curve events per lap. |

</div>

After entering parking mode, Cheese compares its current front distance with the saved starting front distance. If the match is confirmed, or if the robot crosses the saved front target cleanly, the robot stops. :contentReference[oaicite:14]{index=14}

The parking approach is progressive:

<div align="center">

| Distance From Saved Front Reference | Behavior |
| :--- | :--- |
| **More than 12 cm away** | Approach at `PARKING_SPEED = -28`. |
| **Within 12 cm** | Slow to `PARKING_MEDIUM_SPEED = -18`. |
| **Within 6 cm** | Creep at `PARKING_CREEP_SPEED = -10`. |
| **Very close to target** | Limit steering to ±8° to reduce final rotation. |

</div>

This parking strategy is documented in the code comments and constants. :contentReference[oaicite:15]{index=15}

Current parking status:

<div align="center">

| Parking Area | Status |
| :--- | :--- |
| **Stops inside final area** | Working. |
| **Overshoots target** | Not currently the main issue. |
| **Stops too early** | Not currently the main issue. |
| **Final angle** | Sometimes slightly tilted. |
| **Main dependency** | Accurate curve counting and stable front-distance finish reference. |

</div>

## ❀ 3.3.14 Open Challenge Risks and Responses ────୨ৎ────────୨ৎ────

Even without obstacles, the Open Challenge can fail if sensor data or motion control becomes unreliable.

<div align="center">

| Risk | Possible Effect | Current Response |
| :--- | :--- | :--- |
| **Curve count is missed** | Parking may activate too late or not activate at the correct time. | Use opposite-color sequence, time window, steering confirmation, and cooldown. |
| **Curve count is duplicated** | Parking may activate too early. | Use cooldown and sequence reset logic. |
| **Wall contact during navigation** | Robot may lose alignment or crash. | Use progressive wall protection, speed reduction, and raw-distance override. |
| **Front wall too close** | Robot may push into the wall. | Use front ultrasonic reverse recovery. |
| **Parking alignment is tilted** | Robot finishes inside the area but not perfectly straight. | Use progressive parking speed and steering limitation near final target. |
| **Ultrasonic reading jumps** | PID may overcorrect. | Use distance validation and filtering. |

</div>

The most important current Open risks are **wall contact** and **final parking angle**, especially when earlier curve counting or sensor readings are not fully stable.

## ❀ 3.3.15 Open Challenge Testing Plan ────୨ৎ────────୨ৎ────

The Open Challenge should be tested in stages so the team can identify the correct cause of each failure.

<div align="center">

| Test Stage | What to Test | Success Condition |
| :---: | :--- | :--- |
| **1** | Straight movement | Cheese drives without strong drift. |
| **2** | Side ultrasonic readings | Left and right distances stay reasonable and stable. |
| **3** | Front ultrasonic safety | Robot reverses when too close and returns to normal movement. |
| **4** | Color detection | BLUE and ORANGE are detected consistently. |
| **5** | Curve counting | One valid opposite-color sequence counts one curve. |
| **6** | Wall protection | Robot avoids side walls without overcorrecting. |
| **7** | Full lap test | Robot completes one lap with correct curve count. |
| **8** | Full three-lap test | Robot completes all 12 curve events. |
| **9** | Parking test | Robot stops inside the correct final area. |
| **10** | Repeatability test | Multiple runs behave similarly. |

</div>

If a failure happens, the team should tune the related subsystem first. For example, if the robot misses curves, color logic should be checked before changing PID. If the robot touches a wall, wall thresholds and steering behavior should be checked before changing parking logic.

## ❀ 3.3.17 Current vs Legacy Open Strategy ────୨ৎ────────୨ৎ────

The previous Open Challenge documentation was useful during earlier development, but it described Cheese v3 more strongly. The current v4 strategy is different because it uses updated sensor placement, front-wall recovery, progressive wall protection, and starting-distance parking references.

<div align="center">

| Area | Previous / Legacy Explanation | Current v4 Explanation |
| :--- | :--- | :--- |
| **Robot version** | Cheese v3. | Cheese v4. |
| **Color mode** | Older explanations sometimes used candidate confirmation or RGB-style language. | Current code uses `COL-COLOR` and groups blue/orange events. |
| **Progress tracking** | Curve and lap counter described separately. | Current code mainly uses `completed_curves` with `TOTAL_CURVES = 12`. |
| **Parking** | Timing or motor-position references were emphasized. | Current code uses saved starting distances, especially front distance. |
| **Wall correction** | PID centering and protected wall logic. | Sensor-fusion PID, progressive wall protection, and front assist. |
| **Safety** | Side-wall protection emphasized. | Front-wall reverse recovery is also a major priority. |

</div>

The legacy version is still useful as engineering history, but this section should be read as the current Cheese v4 Open Challenge reference.

## ❀ Open Challenge Summary ────୨ৎ────────୨ৎ────

Cheese v4 solves the Open Challenge by combining floor-color progress tracking, three-ultrasonic wall sensing, sensor-fusion PID, progressive wall protection, front-wall reverse recovery, and starting-distance parking logic.

The current Open Challenge behavior is strong: Cheese can complete three laps and stop inside the correct area. The remaining improvements focus on reducing wall contact, keeping curve counts reliable, and improving final alignment so the robot finishes less tilted.

<p align="center">
  <strong>Final interpretation:</strong><br>
  Open Challenge success depends on separating movement control from progress tracking: ultrasonic sensors control safe movement, while the color sensor tracks curve completion so Cheese knows when to finish.
</p>
