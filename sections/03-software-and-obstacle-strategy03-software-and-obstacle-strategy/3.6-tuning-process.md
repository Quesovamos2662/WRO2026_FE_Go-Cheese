The current tuning status is:

<div align="center">

| Area | Current Status |
| :--- | :--- |
| **Open Challenge** | Almost final and mostly stable. |
| **Three-lap run** | Works well when battery and sensors are consistent. |

| **Three-lap time** | Around 80–90 seconds. |
| **Parking** | Stops inside the correct area, but can sometimes finish slightly angled. |
| **Obstacle Challenge** | Functional, but still experimental and in calibration. |
| **Main obstacle issue** | Recovery after avoiding a pillar is the biggest challenge. |
| **System sensitivity** | Battery level, sensor readings, camera angle, and speed still affect performance. |

## ❀ 3.6.1 Purpose of Tuning ────୨ৎ────────୨ৎ────

The purpose of tuning was to make Cheese v4 more stable, predictable, and repeatable during competition-style runs. Even after the main logic was planned, the robot still needed many adjustments because real performance depends on mechanical weight, wheel traction, steering response, sensor height, PID values, camera angle, battery level, and field conditions.

The main tuning goals were:

<div align="center">

| Tuning Goal | Why It Was Important |
| :--- | :--- |
| **Reduce crashes** | The robot needed to complete full laps without hitting the walls. |
| **Improve curve behavior** | Tighter curves helped Cheese return to the center faster. |
| **Improve color reliability** | Curve counting depends on the color sensor. |
| **Make parking more accurate** | Parking depends on curve count and finish reference detection. |
| **Improve obstacle avoidance** | The robot needed to detect pillars and avoid carrying them. |
| **Improve recovery** | After curves and obstacles, Cheese needed to become straight again. |
| **Keep speed proportional to reliability** | A faster robot is not useful if it becomes unstable. |

</div>

The main engineering idea was to tune for **consistency first**, then speed.

---

## ❀ 3.6.2 Real v4 Tuning Order ────୨ৎ────────୨ৎ────

The team followed a practical tuning order. We started with the robot’s physical structure before tuning software details.

<div align="center">

| Order | Tuning Stage | Main Focus |
| :---: | :--- | :--- |
| **1** | Mechanical tuning | Reduce weight, improve center of gravity, improve wheel behavior, and make the robot easier to control. |
| **2** | Color tuning | Make the color sensor detect blue and orange more reliably. |
| **3** | PID tuning | Calibrate the main navigation controller so Cheese could complete laps without crashing. |
| **4** | Curve tuning | Make curves more closed, centered, and useful for the next section. |
| **5** | Parking tuning | Use curve count and front-distance memory to stop inside the final area. |
| **6** | Obstacle tuning | Adjust camera angle, speed, obstacle response, and recovery after avoidance. |

</div>

This order was important because software cannot fully fix a robot that is mechanically unstable. Cheese v4 became easier to tune after the physical robot became lighter and better balanced.

---

## ❀ 3.6.3 Mechanical Tuning in v4 ────୨ৎ────────୨ৎ────

Mechanical tuning was one of the biggest improvements from v3 to v4. The team reduced unnecessary weight and reorganized the robot so the EV3 Brick sat in a better position.

<div align="center">

| Mechanical Change | Effect on Tuning |
| :--- | :--- |
| **Weight reduction** | Made Cheese easier to accelerate, turn, and recover. |
| **EV3 position improved** | Helped the center of gravity and improved weight distribution. |
| **Front wheel change** | Improved steering behavior and helped the robot respond better during curves. |
| **Removal of unnecessary parts** | Made the robot less bulky and easier to inspect or adjust. |
| **Removal of auxiliary lights** | Simplified wiring and reduced weight; the current v4 system does not depend on them. |
| **Lower / cleaner sensor area** | Helped with color detection and physical consistency. |

</div>

The most important mechanical improvements were lowering the effective weight, improving the EV3 Brick placement, and using the new front wheel setup. These changes helped the software tuning because the robot reacted more predictably.

## ❀ 3.6.4 Tuning Cycle ────୨ৎ────────୨ৎ────

The team used a repeated tuning cycle instead of changing random values.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/07_v4_sensor_validation_reliability.png" alt="Cheese v4 sensor validation and reliability flowchart" width="90%">
</p>

<p align="center">
  <em>Sensor validation and reliability flowchart showing how Cheese reduces the effect of unstable readings during tuning and testing.</em>
</p>

The tuning cycle followed this structure:

<div align="center">

| Step | Action | Why It Matters |
| :---: | :--- | :--- |
| **1** | Observe a failure on the field. | The team starts from real behavior, not guesses. |
| **2** | Identify the subsystem involved. | Prevents changing unrelated values. |
| **3** | Change one main variable or method. | Makes cause and effect easier to understand. |
| **4** | Test again. | Shows whether the adjustment helped or hurt. |
| **5** | Compare with the previous run. | Helps decide whether the change should stay. |
| **6** | Keep, reduce, or reverse the change. | Prevents the robot from becoming worse over time. |
| **7** | Repeat with the next problem. | Builds gradual improvement. |

</div>

This process was used for curve shape, PID behavior, color detection, parking accuracy, obstacle response, and recovery after obstacles.

## ❀ 3.6.5 Open Challenge Tuning Summary ────୨ৎ────────୨ৎ────

Open Challenge tuning focused on completing three laps, counting curves correctly, avoiding wall crashes, and parking inside the correct area.

<div align="center">

| Open System | What Was Tuned | Result |
| :--- | :--- | :--- |
| **Curve counter** | Two-color sequence, timing window, cooldown, and steering confirmation. | Helped improve lap precision. |
| **PID controller** | Wall response, steering strength, derivative behavior, and filtering. | Became the base of reliable Open navigation. |
| **Front reverse** | Front ultrasonic trigger and recovery distance. | Helped prevent crashes and reduce destabilization. |
| **Parking** | Saved front-distance reference and progressive parking speed. | Helped Cheese stop inside the final area. |
| **Speed** | Normal, wall-protection, and parking speeds. | Improved fluency while keeping the robot controllable. |

</div>

The Open Challenge is currently the most stable part of the project. It works well when the battery is charged and the setup is consistent. The main remaining issues are occasional parking angle and rare curve-count problems.

## ❀ 3.6.7 PID and Wall Control Tuning ────୨ৎ────────୨ৎ────

PID calibration was one of the most important parts of the project. It became the base of the Open Challenge code because Cheese needed to complete laps without drifting into walls.

<div align="center">

| PID / Control Value | Current Value | Purpose |
| :--- | :---: | :--- |
| `KP` | `0.28` | Main proportional response to wall error. |
| `KI` | `0.001` | Small integral correction for accumulated error. |
| `KD` | `0.08` | Derivative response to reduce unstable changes. |
| `MAX_PID_ANGLE` | `32°` | Limits normal steering correction. |
| `SENSOR_FILTER_ALPHA` | `0.65` | Smooths ultrasonic readings. |
| `DERIVATIVE_FILTER_ALPHA` | `0.45` | Smooths derivative response. |
| `PID_CENTER_ERROR_DEADBAND` | `1.5` | Prevents small harmless errors from causing steering. |
| `LOOP_DELAY` | `0.01 s` | Main loop timing. |

</div>

The PID tuning goal was not to force Cheese into the exact center at every moment. The goal was to make corrections strong enough to avoid walls, but smooth enough to prevent zig-zag movement.

## ❀ 3.6.8 Wall Protection Tuning ────୨ৎ────────୨ৎ────

Wall protection was tuned because normal PID alone was not always enough during curves, bad exits, or close-wall situations.

<div align="center">

| Wall Protection Value | Current Value | Why It Matters |
| :--- | :---: | :--- |
| `WALL_GENTLE_DISTANCE` | `28.0 cm` | Starts softer wall correction earlier. |
| `WALL_SEVERE_DISTANCE` | `22.0 cm` | Activates stronger wall danger behavior. |
| `FULL_WALL_AVOIDANCE_CM` | `15.0 cm` | Represents very close wall danger. |
| `GENTLE_WALL_ANGLE` | `14°` | Moderate steering away from wall. |
| `SEVERE_WALL_ANGLE` | `18°` | Stronger steering away from wall. |
| `WALL_OVERRIDE_MIN_ANGLE` | `8°` | Minimum raw-distance escape steering. |

</div>

The team tuned wall protection because a curve exit can place the robot close to the exterior wall. If wall correction is too weak, Cheese may hit the wall. If it is too strong, the robot may overcorrect and become unstable.

## ❀ 3.6.10 Color Sensor Tuning ────୨ৎ────────୨ৎ────

Color sensor tuning was essential because the robot uses color events to count curves. Earlier in development, the color sensor was affected by sunlight. It sometimes detected orange too strongly and had more difficulty with the blue line in certain directions.

In Cheese v4, the sensor is structurally in the same general position as before, but it is slightly lower. This helped it detect both colored lines more reliably. Because of this, external light-blocking solutions like mamparas are no longer part of the normal current operation.

<div align="center">

| Color Tuning Change | Result |
| :--- | :--- |
| **Lower color sensor position** | Improved detection of both blue and orange. |
| **Use of `COL-COLOR` mode** | Simplified the detection system. |
| **Grouping orange-like readings** | Helped classify the orange marker more reliably. |
| **Curve sequence logic** | Prevented one color from counting as a full curve. |
| **Cooldown** | Reduced double-count risk. |
| **Steering confirmation** | Connected curve counting to real turning movement. |

</div>

## ❀ 3.6.11 Curve Counter Tuning ────୨ৎ────────୨ৎ────

The curve counter was one of the most important software improvements because it affected both lap progress and parking.

<p align="center">
  <img src="../../img/software-flowcharts%20v4/02_v4_color_detection_curve_counting.png" alt="Cheese v4 color detection and curve counting flowchart" width="90%">
</p>

<p align="center">
  <em>Color detection and curve counting flowchart showing how Cheese turns floor colors into valid curve counts.</em>
</p>

<div align="center">

| Curve Counter Value | Current Value | Purpose |
| :--- | :---: | :--- |
| `TOTAL_CURVES` | `12` | Full three-lap Open Challenge target. |
| `COLOR_CHANGE_WINDOW` | `3.0 s` | Opposite colors must appear within this time. |
| `CURVE_COOLDOWN` | `1.5 s` | Prevents the same curve from being counted repeatedly. |
| `CORNER_TURN_MIN_ANGLE` | `0.1°` | Minimum steering activity needed for confirmation. |
| `CORNER_TURN_MIN_TIME` | `0.03 s` | Confirms steering was not just instant noise. |
| `POST_COLOR_STEERING_WINDOW` | `0.9 s` | Allows steering confirmation shortly after the second color. |

</div>

The valid curve sequences are:

<div align="center">

| Sequence | Result |
| :---: | :--- |
| **BLUE → ORANGE** | Counts one curve. |
| **ORANGE → BLUE** | Counts one curve. |

</div>

This method improved precision because Cheese does not count one color as one curve. It waits for the opposite color and verifies that the movement matches a real curve event.

## ❀ 3.6.12 Curve Shape Tuning ────୨ৎ────────୨ৎ────

Curve tuning focused on making Cheese turn more closed and recover better after the turn. Earlier, the robot sometimes took curves too wide or reacted too late. Wide curves made the robot harder to center before the next obstacle.

<div align="center">

| Curve Behavior | Tuning Direction |
| :--- | :--- |
| **Curve too wide** | Increase curve authority or make steering response earlier. |
| **Robot reacts too late** | Adjust speed and steering timing. |
| **Robot exits too far outward** | Make curves more closed so Cheese returns toward the center. |
| **Exterior wall becomes risky** | Improve curve exit and wall protection. |
| **Obstacle after curve becomes harder** | Improve centering so the camera sees the next pillar better. |

</div>

The current curves are more closed than before, and this helped the robot crash less and center better between obstacles. However, the team is still tuning corner handling because the robot can still turn late or too openly in some situations.

## ❀ 3.6.13 Parking Tuning ────୨ৎ────────୨ৎ────

Parking tuning depended on the rest of the run. If the curve count is wrong, parking can activate early, late, or behave strangely.

The current parking system is not based only on time. Cheese memorizes its starting distances and later uses the front distance as the main finish reference.

<div align="center">

| Parking Value | Current Value | Purpose |
| :--- | :---: | :--- |

| `FINISH_FRONT_TOLERANCE_CM` | `2.0 cm` | Allowed difference from saved front distance. |
| `FINISH_CONFIRMATIONS` | `2` | Confirms the finish match before stopping. |

| `PARKING_ALIGNMENT_CUTOFF_CM` | `6.0 cm` | Activates creep behavior and steering limit. |
| `PARKING_CLOSE_MAX_STEER` | `8.0°` | Prevents large steering corrections near the final stop. |

</div>

Current parking status:

<div align="center">

| Parking Observation | Current Result |
| :--- | :--- |
| **Stops inside the area** | Yes, working. |
| **Overshoots** | Not a main current issue. |
| **Stops too short** | Not a main current issue. |
| **Final angle** | Sometimes slightly angled. |
| **Main dependency** | Correct curve count and stable front-distance reading. |

</div>

## ❀ 3.6.15 Camera and Obstacle Calibration ────୨ৎ────────୨ৎ────

Camera tuning focused on the relationship between what HuskyLens sees and how the EV3 reacts.

<div align="center">

| Camera / Obstacle Issue | Effect | Tuning Direction |
| :--- | :--- | :--- |
| **Camera angle not ideal** | The pillar appears late or at a weak angle. | Adjust camera position and view direction. |
| **Pillar not detected early enough** | Robot has little time to avoid it. | Lower speed and improve camera view. |
| **Avoidance too weak** | Cheese may clip or carry the pillar. | Increase camera bias carefully. |
| **Recovery after avoidance fails** | Robot is not straight for the next section. | Tune return to PID and wall correction. |
| **Obstacle parking not adapted** | Robot may not finish obstacle run correctly. | Complete parking only after avoidance is reliable. |

</div>

The current priority is not only making the camera detect color. The priority is making detection happen early enough and making the robot recover after the dodge.

This shows that v4 was not just a rebuild. It was a response to specific problems found during testing.

## ❀ 3.6.20 Final Tuning Workflow ────୨ৎ────────୨ৎ────

The current recommended tuning workflow for Cheese v4 is:

<div align="center">

| Step | What to Check | Why It Comes in This Order |
| :---: | :--- | :--- |
| **1** | Mechanical alignment and wheel behavior | Mechanical problems can make software tuning unreliable. |
| **2** | Battery level | Low battery changes motor response and can ruin test consistency. |
| **3** | Sensor positions | Color, ultrasonic, and camera placement affect all readings. |
| **4** | Color sensor detection | Curve counting depends on reliable blue/orange detection. |
| **5** | Curve counter | Parking depends on reaching the correct curve count. |
| **6** | PID and wall protection | The robot must complete laps before final parking can be trusted. |
| **7** | Front reverse | Safety behavior must work before full-speed testing. |
| **8** | Curve shape | The robot needs centered exits before obstacle tuning. |
| **9** | Parking | Parking should be tuned after curve counting is reliable. |
| **10** | Camera angle | Obstacle reaction depends on early detection. |
| **11** | Obstacle speed and bias | The robot must avoid pillars without carrying them. |
| **12** | Obstacle recovery | The robot must return to stable navigation after avoidance. |
| **13** | Obstacle parking | This should be finalized after avoidance and recovery are stable. |

</div>

This order helps prevent random tuning. Each step depends on the previous one.

Cheese v4 improved through a gradual tuning process that combined mechanical redesign, sensor adjustment, PID calibration, curve-count logic, parking references, and obstacle detection tuning.

Open Challenge is now close to final and works almost consistently when the battery is charged and the setup is stable. Obstacle Challenge is functional but still being calibrated, especially for recovery after avoiding a pillar and for obstacle parking.
