A failure is useful when it shows what needs to change. In engineering, a failed test is not just something that went wrong. It is evidence.

For Cheese, the most important failures were connected to excess weight, difficult PID calibration, unstable curves, line-counting errors, sunlight affecting the color sensor, camera delay, obstacle avoidance calibration, and some v3 structural stress.

This section explains what failed, why it mattered, what we changed, and what we learned.

<p align="center">
  <strong>A failure was useful when it helped us identify what needed to change in the next version.</strong>
</p>

## ❀ 4.2.1 Failure Analysis Method ────୨ৎ────────୨ৎ────

When Cheese failed, we tried to connect the visible problem to a cause. A robot can crash for many reasons, and the first explanation is not always correct.

For example, a wall crash can look like a software problem, but it may also involve ultrasonic sensor height, PID values, steering geometry, wheel grip, robot mass, or low battery voltage.

For each failure, we asked:

<div align="center">

| Question | Purpose |
| :--- | :--- |
| **What failed?** | Identifies the visible issue. |
| **Why did it matter?** | Explains the effect on performance. |
| **What probably caused it?** | Connects the failure to a subsystem. |
| **What risk did it create?** | Shows why the problem had to be fixed. |
| **What did we change?** | Shows the design or tuning response. |
| **What improved or still needs work?** | Keeps the documentation honest. |

</div>

This helped us turn failures into engineering decisions instead of random fixes.

## ❀ 4.2.3 Failure Overview ────୨ৎ────────୨ৎ────

The failures that shaped v4 were not isolated. Many of them affected more than one subsystem.

<div align="center">

| What Did Not Work | Why It Mattered | Response |
| :--- | :--- | :--- |
| **Excess weight** | Made curves, steering, and calibration harder. | Reduce mass from 888 g to 666 g. |
| **Difficult PID calibration** | Caused unstable corrections and wall crashes. | Continue tuning with lower sensors and lighter structure. |
| **Unstable curves** | Robot could enter or exit curves badly. | Tune curve behavior and improve mechanical response. |
| **Line-counting errors** | Robot sometimes counted too many or too few curves. | Improve color sensor protection and detection logic. |
| **Sunlight affecting color sensor** | Blue line detection could fail. | Cover/protect the sensor from direct light. |
| **Camera delay** | Obstacle avoidance could happen too late. | Continue HuskyLens calibration and angle testing. |
| **Obstacle parking pending** | Obstacle path changes final timing and position. | Keep Open parking working while obstacle parking is developed. |
| **v3 pin stress** | Small parts became mechanical failure points. | Reduce structural stress in v4. |
| **Large camera mount** | Added unnecessary structure and height. | Replace with simpler camera support. |
| **Nano cable clutter** | Camera/Nano area was harder to inspect. | Shorten only the Nano USB cable. |

</div>

These failures led to one major conclusion:

<p align="center">
  <strong>Cheese needed a lighter, cleaner, lower, and easier-to-calibrate v4 structure.</strong>
</p>

## ❀ 4.2.4 Excess Weight Did Not Work ────୨ৎ────────୨ৎ────

The v3 robot weighed **888.8 g**, documented as **888 g** for calculations. This weight made the robot harder to calibrate and control, especially during curves.

The problem was not only that the robot was heavy. The deeper problem was that weight affected other systems.

<div align="center">

| Weight-Related Problem | Why It Mattered |
| :--- | :--- |
| **Harder to turn** | More mass resisted direction changes during curves. |
| **Harder to stop or recover** | The robot needed more control after a curve or correction. |
| **More stress on steering** | Steering had to move the robot’s front direction against more inertia. |
| **More stress on structure** | Pins, axles, and supports carried more load. |
| **Harder PID tuning** | Corrections had to fight more physical resistance. |

</div>

The v4 response was to remove unnecessary structure and reduce the robot to **666 g**.

<p align="center">
  <strong>Result:</strong><br>
  The v4 robot became more fluid, faster in its movement, easier to handle, and better balanced through a lower center of gravity.
</p>

This did not automatically solve every calibration problem, but it gave the software and sensors a better physical base to work with.

---

## ❀ 4.2.5 The Large Camera Mount Did Not Work ────୨ৎ────────୨ৎ────

The v3 camera structure was too large for the function it needed to perform. The camera needed a clear forward view, but the mount added extra pieces, extra height, and extra mass.

This created several problems:

<div align="center">

| Camera Mount Problem | System Effect |
| :--- | :--- |
| **Added extra mass** | Made the robot heavier and harder to calibrate. |
| **Raised the structure** | Affected center of gravity and stability. |
| **Made the front area crowded** | Made camera and sensor adjustments harder. |
| **Created more places for tight pieces** | Some parts became harder to assemble or inspect. |
| **Required more visibility support in v3** | The camera setup depended more on lighting and structure. |

</div>

In v4, the camera stayed because obstacle detection still matters. What changed was the structure around it.

The camera was lowered and kept forward, with the angle still being optimized so it focuses on the obstacles clearly.

<p align="center">
  <strong>What failed was not the camera. What failed was the oversized support structure.</strong>
</p>

---

## ❀ 4.2.6 Unnecessary Structural Pieces Did Not Work ────୨ৎ────────୨ৎ────

Earlier versions used more pins, axles, liftarms, and supports because the robot’s layout required them. The EV3 Brick orientation, motor placement, camera mount, and taller structure created a need for more support pieces.

However, after testing, we realized that some of these pieces were not improving performance. They were mainly supporting an older structure that was no longer the best option.

<div align="center">

| Problem With Extra Pieces | Why It Was Bad |
| :--- | :--- |
| **Added weight** | Made movement and calibration harder. |
| **Created tight spaces** | Made repair and inspection slower. |
| **Increased part stress** | Pins and connectors could be placed under pressure. |
| **Made the robot harder to understand** | More pieces made it harder to identify what was actually necessary. |
| **Supported outdated design choices** | Some pieces existed only because of the old camera mount or layout. |

</div>

The v4 decision was to remove unnecessary pieces, but not to make the robot weak. The goal was to keep the structure strong enough while reducing the amount of useless mass.

<p align="center">
  <strong>The lesson was not “use fewer pieces always.” The lesson was “use only the pieces that have a purpose.”</strong>
</p>

---

## ❀ 4.2.7 Pin Stress Happened in v3 ────୨ৎ────────୨ৎ────

Some pieces and pins were under stress in v3. This did not become a current v4 problem, but it was still an important lesson.

In LEGO Technic robots, pins and connectors are small, but they hold the entire structure together. If they are forced, overloaded, or placed under too much pressure, the structure can loosen or fail.

<div align="center">

| Pin / Connection Issue | Why It Matters |
| :--- | :--- |
| **Broken pin** | Weakens the structure. |
| **Tight connection** | Makes repair and adjustment difficult. |
| **Repeated stress** | Can create failure after several tests. |
| **Small alignment shift** | Can affect steering or sensor position. |

</div>

<p align="center">
  <img src="../../img/broken_pin.jpeg" alt="Broken Technic pin from Cheese testing" width="55%">
</p>

<p align="center">
  <em>Broken Technic pin caused by force, pressure, or repeated structural stress during v3 testing.</em>
</p>

This failure helped us be more careful in v4. Since the v4 structure is lighter and cleaner, we have not had the same pin-stress problem so far.

<p align="center">
  <strong>What we learned:</strong><br>
  A small connection failure can affect the reliability of the whole robot.
</p>

---

## ❀ 4.2.8 Ultrasonic Sensor Placement Did Not Fully Work ────୨ৎ────────୨ৎ────

The ultrasonic sensors are used for wall distance. If they are not placed well, the PID receives weaker information.

One issue was that the ultrasonic sensors were too high or not positioned to use their full potential. This matters because the WRO field walls are not infinitely tall. If the sensor is too high, the ultrasonic beam may not hit the most useful part of the wall.

<div align="center">

| Ultrasonic Failure | Cause | Fix | Result |
| :--- | :--- | :--- | :--- |
| **Wall readings were not ideal** | Sensors were too high or not perfectly aligned. | Lower ultrasonic sensors in v4. | Better physical reading conditions. |
| **PID had unstable information** | Wall-distance readings affected correction behavior. | Continue PID tuning with improved placement. | Calibration is improving. |
| **Robot sometimes crashed near walls** | Sensor data and steering response were not fully balanced. | Tune PID, thresholds, and recovery. | Fewer severe errors, but tuning continues. |

</div>

This failure showed that a software problem can begin as a physical placement problem.

<p align="center">
  <strong>If the sensor placement is weak, the code has to fight bad information.</strong>
</p>

---

## ❀ 4.2.9 Color Sensor and Sunlight Did Not Work Well Together ────୨ৎ────────୨ৎ────

The color sensor became one of the most important parts of Cheese because it helps with line and curve counting. However, it had a problem when sunlight entered the sensor area.

Direct light affected the color reading and made the sensor miss the blue line in some tests. This caused curve-counting problems, especially when the robot counted too many or too few curves.

<div align="center">

| Color Sensor Failure | Cause | Fix | Result |
| :--- | :--- | :--- | :--- |
| **Blue line was missed** | Sunlight interfered with the reading. | Covered/protected the sensor from direct light. | Line detection improved. |
| **Curve count was sometimes wrong** | The sensor missed a line or counted too many detections. | Continue tuning detection timing and cooldown. | Improved, but still a main calibration area. |
| **Lighting conditions changed between tests** | Field lighting was not always identical. | Test in real conditions and protect sensor area. | More stable color behavior. |

</div>

The fix was not to remove the color sensor. The fix was to protect it and keep improving detection logic.

<p align="center">
  <strong>The color sensor became more reliable after we reduced the effect of sunlight.</strong>
</p>

---

## ❀ 4.2.10 PID and Curve Stability Are Still Calibration Challenges ────୨ৎ────────୨ৎ────

PID calibration has been one of the hardest parts of Cheese. The robot can complete the Open Challenge overall, but the PID still needs refinement to make the run smoother and more consistent.

The main issues are curve behavior, wall correction, and recovery after turns.

<div align="center">

| Movement Failure | Why It Happens | Why It Matters | Response |
| :--- | :--- | :--- | :--- |
| **PID difficult to calibrate** | Wall readings, steering response, and speed must match. | Bad PID can cause oscillation or wall crashes. | Continue tuning after v4 structure improvement. |
| **Unstable curves** | Steering angle, timing, or recovery may not be balanced. | Robot may exit curves in a bad position. | Adjust curve and recovery behavior. |
| **Counts too many curves** | Sensor detection may trigger more than once. | Robot may think it completed more than it did. | Tune cooldown and confirmation logic. |
| **Counts too few curves** | Sensor may miss a line because of speed or lighting. | Robot may not know when to finish. | Protect color sensor and tune detection. |
| **Outer wall crashes** | Curve or correction can be late. | Robot loses time and stability. | Use reverse recovery and continue tuning. |
| **Inner wall crashes** | Correction or recovery may be too strong. | Robot exits poorly after a turn. | Balance PID and steering response. |

</div>

This shows that movement problems are not only code problems. They involve mechanics, sensors, weight, wheels, battery, and field conditions.

<p align="center">
  <strong>Open Challenge status:</strong><br>
  Cheese can complete three laps and Open parking is mostly well calibrated, but PID, curve counting, and consistency are still being improved.
</p>

---

## ❀ 4.2.11 Camera Delay and Obstacle Avoidance Are Still in Progress ────୨ৎ────────୨ৎ────

The HuskyLens is already detecting the obstacle colors, but obstacle avoidance is still being calibrated.

Current detection setup:

<div align="center">

| Obstacle Color | HuskyLens ID | Required Rule |
| :--- | :---: | :--- |
| **Red pillar** | **ID 1** | Pass on the right. |
| **Green pillar** | **ID 2** | Pass on the left. |

</div>

The problem is that detecting the object is not enough. The robot must detect it early, decide correctly, steer around it, recover, and continue driving without crashing or missing the next event.

<div align="center">

| Obstacle Issue | Why It Matters | Current Response |
| :--- | :--- | :--- |
| **Camera has delay** | The robot has less time to avoid the pillar. | Continue tuning camera angle and detection timing. |
| **Lighting can affect recognition** | Red/green colors may appear less clear. | Test with real pillars and real lighting. |
| **Camera angle is not final** | The camera must focus mainly on obstacles. | Adjust the camera angle until the obstacle area is clear. |
| **Avoidance is not fully calibrated** | The robot may detect the color but not avoid correctly. | Continue connecting ID detection to left/right movement. |
| **Recovery after obstacle is difficult** | Robot must return to normal navigation after avoidance. | Treat obstacle avoidance and recovery as separate phases. |

</div>

This part is documented honestly:

<p align="center">
  <strong>The HuskyLens has positive progress because it detects red and green, but the complete avoidance behavior is still under calibration.</strong>
</p>

---

## ❀ 4.2.12 Parking Did Not Always Work as a Separate Problem ────୨ৎ────────୨ৎ────

Parking depends on the whole run. It is not only a stop command.

For the **Open Challenge**, parking is already mostly well calibrated. If the rest of the code behaves correctly, the Open parking works. However, parking has still caused problems during testing because it depends on curve counting, timing, alignment, and final position.

For the **Obstacle Challenge**, parking is still not fully adapted because obstacle avoidance changes the robot’s path and timing.

<div align="center">

| Parking Area | Status | Why It Matters |
| :--- | :--- | :--- |
| **Open parking** | Mostly well calibrated. | Works when the run logic behaves correctly. |
| **Open parking issues** | Still happened in some tests. | Bad line counting or alignment can affect final stop. |
| **Obstacle parking** | Not fully adapted yet. | Obstacle avoidance changes final position and timing. |

</div>

The lesson is:

<p align="center">
  <strong>Parking is not the end of the system. It is the result of the full system.</strong>
</p>

---

## ❀ 4.2.13 Second Regional Testing Pressure ────୨ৎ────────୨ৎ────

One of the biggest reasons we moved toward v4 came from testing pressure around the second regional.

Some codes that seemed to work did not perform reliably during practice before evaluation. Because of this, we had to depend on an older code version that was more trustworthy at that moment.

This showed us that a robot cannot only work once. It must be understandable and repeatable under pressure.

<div align="center">

| What Happened | Why It Mattered | What It Changed |
| :--- | :--- | :--- |
| Newer code versions were not always reliable. | We could not trust them under evaluation pressure. | Simpler, clearer logic became more important. |
| Older code had to be used. | Reliability mattered more than having the newest version. | We focused on reducing unknown variables. |
| Calibration time was limited. | We could not spend all practice time fighting structure and code. | v4 was redesigned to be easier to test. |
| The robot had too many possible failure points. | It was hard to know what caused each failure. | v4 reduced unnecessary structure and clutter. |

</div>

This failure helped us understand that good engineering is not only about building the most advanced version. It is about building a version that can be tested, repaired, understood, and trusted.

## ❀ 4.2.14 Failure → Cause → Fix → Result ────୨ৎ────────୨ৎ────

<div align="center">

| Failure | Likely Cause | Fix / Response | Result |

| **Robot was hard to calibrate in curves** | Excess weight and higher structure. | Rebuild lighter v4 chassis. | Better fluency, speed, and center of gravity. |
| **Large camera mount created problems** | Too many pieces and too much height. | Simplify and lower camera support. | Cleaner front structure and easier testing. |
| **Ultrasonic readings were not ideal** | Sensors were too high. | Lower ultrasonic sensors. | Better wall-reading conditions. |
| **Color sensor missed blue line** | Sunlight entered sensor area. | Protect/cover sensor from direct light. | Better line detection. |
| **Curve counter counted extra or missed lines** | Timing, cooldown, lighting, and speed issues. | Continue calibration and detection tuning. | Improved, still a main tuning area. |
| **PID was hard to tune** | Sensor data, steering response, and speed were not fully balanced. | Tune PID with improved v4 structure. | Better overall behavior, still under refinement. |
| **Camera reacted with delay** | Angle and detection timing not fully calibrated. | Continue HuskyLens angle and ID testing. | Positive progress, not final yet. |
| **Obstacle avoidance was incomplete** | Detection and movement logic not fully connected. | Use ID 1 red / ID 2 green and continue avoidance calibration. | In progress. |
| **Obstacle parking was not ready** | Obstacle path changes timing and final position. | Keep Open parking working; adapt obstacle parking later. | Open parking works; obstacle parking pending. |
| **Pin stress happened in v3** | Tight or stressed structural connections. | Reduce unnecessary structure in v4. | No current v4 issue reported. |

</div>

This table shows how failure became design evidence. Each problem created a reason for the next decision.

## ❀ 4.2.15 How These Failures Led to v4 ────୨ৎ────────୨ৎ────

The v4 redesign came from repeated failures and calibration problems. At first, it was tempting to solve problems by adding more pieces, more supports, or more code. Testing showed that this was not always the right answer.

The team changed strategy from:

<p align="center">
  <strong>“Add more to fix every problem”</strong><br>
  to<br>
  <strong>“Simplify the robot so it is easier to calibrate, inspect, and trust.”</strong>
</p>

<div align="center">

| Failure Pattern | v4 Design Response |
| :--- | :--- |
| **Heavy structure made curves harder.** | Reduce mass to 666 g. |
| **Large camera support added complexity.** | Simplify and lower the camera mount. |
| **Ultrasonic placement limited wall reading.** | Lower the ultrasonic sensors. |
| **Color sensor was useful but affected by sunlight.** | Keep placement and protect the sensor area. |
| **One cable added clutter near the camera bridge.** | Shorten the Arduino Nano USB cable. |
| **Extra pieces added stress and confusion.** | Remove unnecessary supports, pins, and axles. |
| **Obstacle behavior was not final.** | Continue HuskyLens calibration honestly. |

</div>

This is the main reason v4 is stronger. It was not redesigned only for appearance. It was redesigned because testing showed which problems were limiting the robot.

---

## ❀ 4.2.16 Final Reflection ────୨ৎ────────୨ৎ────

The most important thing that did not work was the idea that adding more automatically makes a robot better.

More pieces did not automatically mean more stability. More code did not automatically mean better behavior. A larger camera mount did not automatically mean better vision. More sensor data did not automatically mean better decisions.

Testing showed that Cheese needed a cleaner and more intentional design.

The v4 robot is stronger because it was shaped by real failures. It is lighter, more compact, easier to inspect, and better suited for continued calibration.

<p align="center">
  <strong>Final key sentence:</strong><br>
  What did not work became the evidence that shaped what finally improved.
</p>
