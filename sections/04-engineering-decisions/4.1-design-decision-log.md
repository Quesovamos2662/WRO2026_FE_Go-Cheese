A design decision is not only a change. It is a choice made after noticing a problem, comparing options, thinking about trade-offs, and selecting the solution that best supports the robot’s performance.

For Cheese v4, the biggest design decision was to stop adding more structure and instead rebuild the robot around a simpler idea:

<p align="center">
  <strong>Less unnecessary structure, better weight distribution, clearer sensor placement, and easier calibration.</strong>
</p>

The v4 redesign was not made only to make the robot look cleaner. Each change was connected to a real engineering reason: weight, stability, sensor reliability, cable access, calibration time, or competition performance.

---

## ❀ 4.1.1 What This Decision Log Is For ────୨ৎ────────୨ৎ────

The purpose of this design decision log is to document the reasoning behind Cheese’s development. A robot can be improved by changing parts, but an engineering project must explain why those changes were made.

This log focuses on four questions:

<div align="center">

| Question | Why It Matters |
| :--- | :--- |
| **What problem did we observe?** | A decision should begin with a real issue, not a random idea. |
| **What options did we compare?** | Engineering requires choosing between possible solutions. |
| **What trade-off did we accept?** | Every improvement usually creates a cost or risk somewhere else. |
| **How did the decision affect the rest of the robot?** | One subsystem can change how another subsystem behaves. |

</div>

This section is especially important because Cheese is not a robot made from one perfect idea. It is the result of testing, failing, redesigning, and adapting.

---

## ❀ 4.1.2 Beginner Explanation: What Is a Design Decision? ────୨ৎ────────୨ৎ────

A design decision is the answer to a problem.

For example, saying “we lowered the ultrasonic sensors” is only a change. The engineering decision is the full explanation:

<p align="center">
  <strong>Problem:</strong> wall readings were not always reliable.<br>
  <strong>Reason:</strong> the sensors could be too high for the side walls.<br>
  <strong>Decision:</strong> lower the ultrasonic sensors.<br>
  <strong>Expected result:</strong> better wall detection and easier PID calibration.
</p>

That is the difference between documenting a robot and documenting engineering.

The subsystem interaction map is included here because Cheese does not work as separate isolated parts. The chassis affects sensor height. Sensor readings affect PID. PID affects steering behavior. Steering behavior affects crashes. Crashes affect structural strength. Battery voltage affects motor response and camera reliability.

In simple terms:

<p align="center">
  <strong>When one subsystem changes, the rest of the robot feels it.</strong>
</p>

<div align="center">

| Subsystem | It Affects | Example on Cheese |
| :--- | :--- | :--- |
| **Mechanical structure** | Steering, sensors, wiring, center of gravity | A heavy or tall structure makes calibration harder. |
| **Sensor placement** | Software decisions and PID response | Lower ultrasonic sensors can improve wall detection. |
| **Power system** | Motors, Arduino Nano, HuskyLens, testing consistency | Low battery voltage can slow steering and weaken camera reliability. |
| **Software logic** | Movement, curve counting, obstacle behavior | PID values decide how aggressively the robot corrects. |
| **Wiring layout** | Debugging and reliability | Cleaner cables make it easier to find loose or wrong connections. |
| **Testing process** | All design decisions | Failures reveal what needs to change next. |

</div>

This is why the v4 redesign was not only a mechanical update. It changed the conditions for calibration, software tuning, obstacle integration, and inspection.

## ❀ 4.1.4 Main v3 to v4 Decision Summary ────୨ৎ────────୨ৎ────

The v4 redesign was a response to problems found during v3 testing. In v3, Cheese worked, but the structure became too bulky and calibration became harder than necessary. The camera support structure, extra pieces, tall layout, and heavier build created more points of adjustment.

In v4, the team changed the engineering strategy. Instead of adding more supports, we rebuilt the robot to be smaller, lighter, lower, and easier to inspect.

<div align="center">

| Design Area | v3 Situation | v4 Decision | Engineering Reason |
| :--- | :--- | :--- | :--- |
| **Overall structure** | Larger and heavier, with more extra support pieces. | Rebuilt into a more compressed layout. | Reduce weight, reduce calibration difficulty, and improve handling. |
| **Robot mass** | About **888 g**. | Reduced to about **666 g**. | Less mass improves acceleration, response, and stress on the structure. |
| **Camera structure** | Large mount and extra pieces mainly supporting the camera. | Removed the large mount and simplified the camera support. | Keep camera function while reducing unnecessary height and mass. |
| **Camera position** | Higher and more dependent on lighting support. | Placed forward, lower, and closer to the sensor area. | Improve visibility and reduce the need for the old v3 lighting setup. |
| **Ultrasonic sensors** | Needed better alignment with wall height. | Lowered and supported with smaller structures. | Improve wall detection and PID reliability. |
| **Color sensor** | Already placed correctly for floor reading. | Kept in the same working position. | Avoid unnecessary recalibration of a sensor that was already reliable. |
| **Front wheels** | Previous front wheel setup was less optimized for the new structure. | Changed to SPIKE-style front wheels. | Improve grip, smoothness, and stability during steering. |
| **USB cable to Arduino Nano** | Longer USB connection added cable clutter. | Replaced with a shorter USB Type-A to Nano cable. | Improve cable organization and reduce loose cable interference. |
| **Extra pieces** | Some pieces supported old structure instead of active function. | Removed unnecessary pins, axles, and structural supports. | Reduce clutter and keep only pieces that serve a clear purpose. |

</div>

The main idea behind v4 was not “remove as much as possible.” The real idea was:

<p align="center">
  <strong>Remove what does not help performance, keep what supports the robot’s function, and make every part easier to test.</strong>
</p>

---

## ❀ 4.1.5 Why We Reduced Weight ────୨ৎ────────୨ৎ────

One of the most important changes from v3 to v4 was reducing the robot’s mass from about **888 g** to about **666 g**.

This decision was made because the heavier v3 structure made calibration harder. A heavier robot needs more effort to accelerate, slow down, and change direction. It also places more stress on the steering system, chassis connections, and motor response.

For a beginner, this can be understood through a simple idea from physics:

<p align="center">
  <strong>With the same motor force, a lighter robot can respond more easily than a heavier robot.</strong>
</p>

The relationship is:

<p align="center">
  <strong>F = m · a</strong>
</p>

This means that if the mass is lower, the same force can produce more acceleration. For Cheese, reducing weight was useful because the motors did not change, but the robot became easier for those motors to move.

<div align="center">

| Why Lower Weight Helps | Effect on Cheese |
| :--- | :--- |
| **Less inertia** | The robot can change movement more easily. |
| **Less stress on steering** | The steering structure does not fight as much mass during turns. |
| **Less stress on connections** | Pins, axles, and liftarms carry less load. |
| **Better calibration conditions** | PID and steering values are easier to tune when the robot behaves more consistently. |
| **Faster response** | The robot can react more fluently to corrections and curves. |

</div>

This decision also saved time. Since the team has limited testing time, a simpler and lighter robot is easier to tune than a heavy robot with many unnecessary variables.

---

## ❀ 4.1.6 Why We Removed the Large Camera Structure ────୨ৎ────────୨ৎ────

In v3, the camera structure was bigger than necessary. Its main job was to hold the HuskyLens in a usable position, but the amount of structure around it added extra weight, extra height, and more calibration complexity.

During testing, we realized that the camera did not need a large mount to perform its function. What the camera needed was a stable forward-facing position with a clear view.

So in v4, we removed the large camera mount and replaced it with a simpler support.

<div align="center">

| Previous Approach | Problem | v4 Decision | Result |
| :--- | :--- | :--- | :--- |
| **Large camera mount** | Added weight and height. | Simplify the camera support. | Cleaner and lighter front structure. |
| **Extra pieces holding the camera** | Increased complexity without improving every function. | Keep only necessary support. | Easier inspection and less mass. |
| **Higher camera position** | Needed more tuning and visibility support. | Move the camera lower and forward. | Better physical position for obstacle detection. |

</div>

This was a systems decision. Removing the mount did not only affect the camera. It affected weight, center of gravity, wiring, calibration, and access to the front structure.

<p align="center">
  <strong>We did not remove the camera function. We removed the unnecessary structure around it.</strong>
</p>

---

## ❀ 4.1.7 Why We Lowered the Ultrasonic Sensors ────୨ৎ────────୨ৎ────

The ultrasonic sensors are responsible for reading wall distance. Their placement is important because ultrasonic sensing depends on sound bouncing back from a surface.

If the sensors are too high, the ultrasonic signal can miss the side wall or hit a less useful part of the field. If the sensors are better aligned with the wall height, the sound has a better chance of bouncing back clearly.

That is why v4 lowered the ultrasonic sensors.

<div align="center">

| Problem | v4 Decision | Expected Improvement |
| :--- | :--- | :--- |
| Sensor beam could miss useful wall surface. | Lower ultrasonic sensors. | Better wall-distance readings. |
| Readings could become less reliable during movement. | Improve physical alignment with the wall. | Better PID input. |
| Wall detection could react late or inconsistently. | Reduce height and simplify support. | More stable correction behavior. |

</div>

This decision connects directly to software. If ultrasonic readings improve, PID tuning becomes easier. If ultrasonic readings are unstable, the code may react too late, overcorrect, or steer based on bad data.

<p align="center">
  <strong>Better sensor placement gives the software better information.</strong>
</p>

---

## ❀ 4.1.8 Why We Kept the Color Sensor Placement ────୨ৎ────────୨ৎ────

Not every part of v4 needed to move. The color sensor stayed in the same general position because it was already doing its job.

The color sensor faces the floor, and its job is to detect the colored track lines used for progress and curve counting. Since the sensor was already placed correctly for that purpose, moving it would have created unnecessary risk.

<div align="center">

| Reason to Keep It | Why It Was a Good Decision |
| :--- | :--- |
| **It already faced the floor correctly.** | The useful information is on the mat. |
| **It supported line and curve counting.** | It helped the robot know where it was in the run. |
| **Its position was already tested.** | Keeping it reduced the need for new calibration. |
| **Moving it could create new problems.** | A different height or angle could change color readings. |

</div>

This decision is important because engineering is not only about changing weak areas. It is also about protecting what already works.

<p align="center">
  <strong>The color sensor stayed because its placement matched its job.</strong>
</p>

---

## ❀ 4.1.9 Why We Changed the Front Wheels ────୨ৎ────────୨ৎ────

In v4, the front wheels were changed to SPIKE-style wheels. This decision was connected to steering stability, grip, and smoother motion.

The front wheels are part of the steering system. Even though the rear motor provides the main drive force, the front wheels decide how the robot enters and follows a turn. If the front wheels slip, bounce, or vibrate too much, the steering angle may not translate cleanly into the robot’s path.

<div align="center">

| Front Wheel Reason | Why It Matters |
| :--- | :--- |
| **Better grip on smooth surfaces** | Helps reduce slipping during starts, braking, and turns. |
| **Wider, smoother contact area** | Helps reduce small vibrations and unstable movement. |
| **More predictable steering response** | The robot follows steering commands more consistently. |
| **Useful for trajectory planning** | Wheel diameter and circumference can help when encoder-based distance calculations are used. |

</div>

For Cheese, the main reason for the front wheel change was not only appearance. It was part of the attempt to make the front steering behavior more stable and easier to tune.

> **Important note:** Distance calculations should only use the wheel connected to the drive encoder. Since Cheese’s drive motor is in the rear, encoder-based distance calculations should be based mainly on the rear drive wheel setup, not only the front wheels.

This front wheel update should also be documented in other repo sections because it affects multiple parts of the robot.

<div align="center">

| Repo Section | Why the Wheel Change Belongs There |
| :--- | :--- |
| **1.1 Mechanical Design** | The front wheel choice affects movement, grip, and stability. |
| **1.3 Steering and Drive** | The front wheels directly affect steering response. |
| **1.4 Chassis Explanation** | The wheel layout affects the final chassis footprint and support. |
| **5.1 Bill of Materials** | The new front wheels must appear in the parts list. |
| **5.2 Build Instructions** | A builder needs to know which wheels to install in front. |
| **v-photos/v4 README** | The v4 photos should identify the front wheel change as part of the redesign. |

</div>

## ❀ 4.1.10 Why We Changed the USB Cable to the Arduino Nano ────୨ৎ────────୨ৎ────

Most cables stayed the same, but the USB cable connected to the Arduino Nano was changed to a shorter cable of the same type.

This is important to write correctly. The v4 redesign did not shorten every cable. The specific cable change was the USB Type-A cable used for the Arduino Nano connection.

<div align="center">

| Cable Decision | What Actually Changed | Why It Helped |
| :--- | :--- | :--- |
| **Arduino Nano USB cable** | Replaced with a shorter USB Type-A to Nano cable. | Reduced cable clutter near the EV3, Nano, and camera area. |
| **Other EV3 sensor/motor cables** | Mostly stayed the same. | They were still needed to reach their ports and components. |
| **Cable management** | Improved by layout and positioning, not by replacing every cable. | Easier inspection and less loose cable interference. |

</div>

This decision improved the wiring layout without pretending the entire wiring system was rebuilt. It made the camera/Arduino area cleaner and reduced the chance that a long cable would interfere with sensors, wheels, or inspection.

---

## ❀ 4.1.11 Why We Removed Unnecessary Pieces ────୨ৎ────────୨ৎ────

In v3, some pieces were added to support a taller or larger structure. Once the camera mount was simplified and the robot was redesigned, many of those pieces no longer had a strong purpose.

We removed unnecessary pins, axles, and structural pieces because they added mass and complexity without improving performance.

<div align="center">

| Removed Piece Type | Why It Could Be Removed | Benefit |
| :--- | :--- | :--- |
| **Extra pins** | Some were supporting old structures that were no longer needed. | Less clutter and fewer loose connection points. |
| **Extra axles** | Some were part of unnecessary supports. | Reduced mass and simpler construction. |
| **Extra liftarms / supports** | Some only held the old camera structure or extra height. | Lower, cleaner, more compact robot. |
| **Large camera mount pieces** | The camera could still work with a simpler mount. | Better center of gravity and easier calibration. |

</div>

The lesson was important:

<p align="center">
  <strong>We discovered that Cheese did not need more pieces. It needed fewer, better-used pieces.</strong>
</p>

A simpler structure is not automatically weaker. If the remaining pieces are placed with purpose, the robot can be lighter, cleaner, and still strong enough to support the EV3 Brick, motors, sensors, and camera.

## ❀ 4.1.12 Constraints That Shaped Our Decisions ────୨ৎ────────୨ৎ────

The v4 redesign was shaped by real constraints. A constraint is a limit that affects what solution is possible.

<div align="center">

| Constraint | How It Affected Cheese |
| :--- | :--- |
| **Limited time** | We needed solutions that could be built, tested, and tuned quickly. |
| **Limited materials** | Multiple teams use LEGO and SPIKE parts, so we had to avoid risky or wasteful designs. |
| **Part fragility** | We could not risk breaking rare pieces by adding unnecessary stress. |
| **Weight** | Extra mass made calibration and steering response harder. |
| **Sensor reliability** | Sensor placement had to improve real readings, not just look organized. |
| **Competition rules** | The robot must complete the required challenge behavior and fit the allowed structure limits. |
| **Testing access** | We needed a robot that could be inspected and modified quickly between test runs. |

</div>

These constraints made the v4 decision clearer. A heavier robot with more structure might look stronger, but it would take more time to tune and would create more possible failure points.

---

## ❀ 4.1.13 Trade-Off Analysis ────୨ৎ────────୨ৎ────

Every design decision has a trade-off. A trade-off means gaining something while accepting a possible cost.

<div align="center">

| Decision | Benefit | Trade-Off / Risk | Why We Accepted It |
| :--- | :--- | :--- | :--- |
| **Reduce weight** | Faster response, less stress, easier calibration. | Could make the structure weaker if too much support is removed. | We kept only the supports that were structurally necessary. |
| **Simplify camera mount** | Less height, less mass, cleaner front structure. | Camera still needs stable alignment. | The camera function stayed, but the unnecessary mount was removed. |
| **Lower ultrasonic sensors** | Better wall alignment and stronger chance of useful echoes. | Sensors may be more exposed to bumps. | Wall readings are critical, so better placement was worth the protection risk. |
| **Keep color sensor position** | Avoids recalibrating a working sensor. | It may not be visually “new” in v4. | A working placement should not be changed without reason. |
| **Use simpler structure** | Easier to inspect and tune. | Less redundancy in supports. | The remaining supports were chosen more intentionally. |
| **Shorter Nano USB cable** | Less cable clutter near the camera system. | Must still reach the Nano safely. | It improved organization without changing the electronic function. |
| **Change front wheels** | Better grip and steering smoothness. | Different wheel behavior may need testing. | Steering stability was one of the main goals of v4. |

</div>

This table shows that v4 was not a random rebuild. It was a set of connected decisions that balanced weight, stability, sensor reliability, and testing practicality.

## ❀ 4.1.14 Risk Identification and Mitigation ────୨ৎ────────୨ৎ────

As we calibrated Cheese, we identified several risks. A risk is something that can make the robot fail, even if the design seems correct.

<div align="center">

| Risk | Why It Matters | Mitigation |
| :--- | :--- | :--- |
| **Structure becomes too weak after removing pieces** | A weak chassis can flex and make steering or sensors inconsistent. | Keep essential supports and remove only pieces that do not serve a clear function. |
| **Center of gravity remains too high** | A tall robot can feel unstable during turns. | Lower and compress the layout in v4. |
| **Ultrasonic readings stay unreliable** | Bad wall readings can cause late correction or crashes. | Lower sensors and continue PID calibration. |
| **Color sensor affected by light** | Sunlight can make the robot miss blue or orange markers. | Keep the floor-facing placement and physically protect the sensor from strong outside light. |
| **Camera detection is slow or incomplete** | Obstacle avoidance may happen too late. | Continue HuskyLens calibration with real red and green pillars. |
| **Cables interfere with sensors or movement** | A loose cable can block a sensor, pull a component, or touch moving parts. | Improve cable organization, especially around the Nano and camera area. |
| **Battery voltage drops during testing** | Motors and camera may behave differently when voltage is low. | Use charged EV3 batteries and avoid tuning on a weak battery. |

</div>

Risk mitigation does not mean the risk disappears completely. It means we recognized the problem and changed the design or testing process to reduce the chance of failure.

## ❀ 4.1.15 How One Subsystem Affects Another ────୨ৎ────────୨ৎ────

One of the biggest lessons from Cheese is that robot subsystems are connected. A problem that looks like software can actually come from mechanics. A problem that looks like a sensor issue can actually come from wiring or battery level.

<div align="center">

| If This Changes... | It Can Affect... | Example From Cheese |
| :--- | :--- | :--- |
| **Chassis weight** | Motor response and steering timing | A lighter v4 robot is easier for the motors to move and correct. |
| **Camera mount height** | Center of gravity and visibility | Removing the tall mount made the robot cleaner while keeping the camera forward. |
| **Ultrasonic sensor height** | PID behavior | Lower sensors can give better wall information for correction. |
| **Color sensor placement** | Curve counting reliability | Keeping the working position avoided new calibration problems. |
| **Battery voltage** | Drive speed, steering speed, and camera reliability | Low voltage can make the robot react slower and make testing inconsistent. |
| **Front wheel grip** | Steering path and curve stability | Better grip helps steering commands translate into real movement. |
| **Cable routing** | Debugging and sensor reliability | Cleaner cable placement makes it easier to inspect problems before a run. |
| **Software PID values** | Mechanical stress and wall crashes | Aggressive corrections can make the robot oversteer or hit walls. |

</div>

This is why v4 was designed as a full-system improvement. The goal was not to make one subsystem perfect in isolation. The goal was to make the mechanical structure, sensors, wiring, software, and testing process work better together.

## ❀ 4.1.18 Final Design Decision Summary ────୨ৎ────────୨ৎ────

The v4 redesign was based on a change in engineering strategy. Instead of adding more pieces every time the robot had a problem, we started asking which pieces were actually necessary.

That led to the main v4 decisions:

<div align="center">

| v4 Decision | Main Engineering Purpose |
| :--- | :--- |
| **Reduce weight from about 888 g to 666 g** | Improve response, reduce stress, and make calibration easier. |
| **Simplify camera mount** | Keep vision function while reducing unnecessary structure. |
| **Lower ultrasonic sensors** | Improve physical wall detection conditions. |
| **Keep color sensor placement** | Protect a sensor position that already worked. |
| **Use SPIKE-style front wheels** | Improve steering grip and stability. |
| **Shorten only the Nano USB cable** | Reduce clutter around the camera bridge. |
| **Remove unnecessary pieces** | Reduce mass and make the structure easier to inspect. |

</div>

The strongest lesson from v4 is that a robot does not become better only by adding more. Sometimes the better engineering decision is to remove, simplify, and rebuild around the parts that truly matter.

<p align="center">
  <strong>Final key sentence:</strong><br>
  We did not change Cheese only to make it look cleaner. Each v4 change was connected to weight, stability, sensor reliability, easier inspection, or better calibration.
</p>
