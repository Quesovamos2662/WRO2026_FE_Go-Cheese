A design decision is not only a change. It is a choice made after noticing a problem, comparing possible solutions, thinking about constraints, and selecting the option that best supports the robot’s performance.

For Cheese v4, the biggest engineering decision was to stop solving every problem by adding more parts. Instead, we rebuilt the robot around a simpler idea:

<p align="center">
  <strong>Less unnecessary structure, better weight distribution, clearer sensor placement, and easier calibration.</strong>
</p>

The v4 redesign was not made only to make Cheese look cleaner. Each major change was connected to a real performance reason: weight, stability, sensor reliability, curve behavior, wiring access, camera visibility, or testing time.

---

## ❀ 4.1.1 Purpose of the Design Decision Log ────୨ৎ────────୨ৎ────

The purpose of this decision log is to explain the reasoning behind the robot, not only the final result. A judge or another team should be able to understand why Cheese changed from v3 to v4.

This section answers four engineering questions:

<div align="center">

| Question | Why It Matters |
| :--- | :--- |
| **What problem did we observe?** | A decision should begin with real evidence, not a random idea. |
| **What options did we compare?** | Engineering requires choosing between possible solutions. |
| **What trade-off did we accept?** | Every improvement usually creates a cost or risk somewhere else. |
| **How did it affect the rest of the robot?** | One subsystem can change how another subsystem behaves. |

</div>

This is important because Cheese is not a robot made from one perfect build. It is the result of repeated testing, calibration problems, structural changes, and software tuning.

## ❀ 4.1.2 Subsystem Interaction Map ────୨ৎ────────୨ৎ────

<p align="center">
  <img src="../../img/subsystem_interaction_map.png" alt="Cheese subsystem interaction map" width="85%">
</p>

<p align="center">
  <em>This planned diagram shows how Cheese’s mechanical structure, sensors, power, wiring, software, and testing process affect each other.</em>
</p>

A subsystem interaction map is a diagram that shows that the robot is not made of separate independent parts. The chassis affects sensor height. Sensor height affects readings. Readings affect PID. PID affects steering. Steering affects wall crashes. Battery voltage affects motor response. Camera placement affects obstacle detection.

For Cheese, systems thinking became very important because many problems did not come from only one place.

<div align="center">

| Subsystem | Affects | Example on Cheese |
| :--- | :--- | :--- |
| **Mechanical structure** | Weight, center of gravity, sensor stability | A taller or heavier structure made calibration harder. |
| **Sensor placement** | PID, curve counting, obstacle detection | Lower ultrasonic sensors may improve wall readings. |
| **Power system** | Motor speed, steering response, camera behavior | Low battery voltage can make the robot react slower. |
| **Wiring** | Debugging and reliability | A shorter Nano USB cable reduced clutter near the camera system. |
| **Software** | Movement, wall correction, curve counting | PID values decide how aggressively the robot reacts. |
| **Testing** | Future design decisions | Failures showed which parts needed to change for v4. |

</div>

The main systems-thinking lesson is:

<p align="center">
  <strong>When one subsystem changes, the whole robot can behave differently.</strong>
</p>

---

## ❀ 4.1.3 Main Constraints ────୨ৎ────────୨ৎ────

The v4 redesign was shaped by real constraints. A constraint is a limit that affects what solution is possible.

<div align="center">

| Constraint | How It Affected Our Decisions |
| :--- | :--- |
| **Limited time** | We needed solutions that could be built, tested, and tuned quickly. |
| **Limited materials** | Several teams use LEGO and SPIKE pieces, so we could not waste rare parts. |
| **Part fragility** | We had to avoid over-stressing pins, axles, and connectors. |
| **Weight** | Extra mass made calibration and curve control harder. |
| **Sensor reliability** | Sensor positions had to improve real readings, not just look organized. |
| **Competition rules** | The robot must complete laps, parking, and obstacle behavior correctly. |
| **Testing pressure** | The robot needed to be easy to inspect and repair between runs. |

</div>

These constraints pushed us toward a simpler and more practical v4 design. A more complex robot might look stronger, but it can be harder to repair, harder to tune, and harder to trust during competition preparation.

---

## ❀ 4.1.4 V3 to V4 Decision Summary ────୨ৎ────────୨ৎ────

The v3 robot weighed **888.8 g**, but we rounded this to **888 g** for documentation and calculations. The current v4 robot weighs **666 g**, and we do not expect to add enough extra mass to change this value drastically.

<p align="center">
  <img src="../../v-photos/v4/v3_vs_v4_comparison.jpg" alt="Cheese v3 to v4 comparison" width="85%">
</p>

<p align="center">
  <em>Visual comparison between the previous v3 structure and the current v4 redesign. This supports the decision to reduce unnecessary structure and create a more compact robot.</em>
</p>

<div align="center">

| Design Area | v3 Situation | v4 Decision | Engineering Reason |
| :--- | :--- | :--- | :--- |
| **Overall structure** | Heavier and more complex. | Rebuilt into a compressed layout. | Reduce calibration difficulty and improve handling. |
| **Mass** | 888.8 g, documented as 888 g. | Reduced to 666 g. | Less mass improves response and reduces stress. |
| **Camera mount** | Larger structure holding the HuskyLens. | Removed large mount and simplified support. | Keep camera function without unnecessary structure. |
| **Camera position** | Higher and more dependent on extra visibility support. | Lower and forward, slightly above the front sensor area. | Improve obstacle visibility while reducing height. |
| **Auxiliary lights** | Used in v3 as visibility support. | Removed from v4. | Lower camera placement reduced the need for v3 lighting. |
| **Ultrasonic sensors** | Needed better alignment with the walls. | Lowered sensor placement. | Improve wall-distance readings for PID. |
| **Color sensor** | Already working in its floor-facing position. | Kept in the same placement. | Avoid unnecessary recalibration. |
| **Front wheels** | Previous front setup was less ideal for the new layout. | Changed only the front wheels to SPIKE wheels. | Improve grip, turn quality, and steering response. |
| **Nano USB cable** | Longer cable created clutter around the camera/Nano area. | Replaced with a shorter USB Type-A to Nano cable. | Reduce cable clutter without changing all EV3 cables. |
| **Extra structural pieces** | Some supported old layout choices. | Removed unnecessary pins, axles, and supports. | Reduce mass and simplify inspection. |

</div>

The v4 design was not about removing parts randomly. It was about removing what did not support performance and keeping what was structurally or functionally necessary.

---

## ❀ 4.1.5 Decision: Reduce Weight from 888 g to 666 g ────୨ৎ────────୨ৎ────

Reducing weight was one of the most important v4 decisions. The v3 robot was not impossible to drive, but it was harder to calibrate and control during curves.

For a beginner, the idea is simple:

<p align="center">
  <strong>A lighter robot is easier for the same motors to move, correct, and turn.</strong>
</p>

The physics relationship is:

<p align="center">
  <strong>F = m · a</strong>
</p>

If the motor force stays similar and the mass decreases, the robot can respond more easily. This matters in curves because the robot must change direction quickly and recover without hitting the walls.

<p align="center">
  <img src="../../img/weight_reduction_chart.png" alt="Cheese weight reduction chart" width="75%">
</p>

<p align="center">
  <em>Weight reduction from approximately 888 g in v3 to 666 g in v4. This supports the decision to reduce mass, improve response, and make calibration easier.</em>
</p>

<div align="center">

| Benefit of Lower Weight | Effect on Cheese |
| :--- | :--- |
| **Less inertia** | The robot resists turning and stopping less. |
| **Less stress on steering** | The steering system does not fight as much mass. |
| **Less stress on connections** | Pins, axles, and liftarms carry less load. |
| **Easier PID tuning** | The robot reacts more predictably to corrections. |
| **Better curve response** | The robot can enter and exit curves more smoothly. |

</div>

The trade-off was that removing too many pieces could make the structure weak. To reduce that risk, we removed pieces that did not serve a clear function while keeping supports that protect the motors, sensors, EV3 Brick, and chassis.

---

## ❀ 4.1.6 Decision: Simplify the Camera Structure ────୨ৎ────────୨ৎ────

In v3, the camera mount was larger than necessary. It helped hold the HuskyLens, but it added mass, height, and calibration complexity.

The camera itself was still important. The issue was not the HuskyLens. The issue was the amount of structure used to hold it.

In v4, the camera stayed forward because obstacles appear in front of the robot. However, the support was simplified and lowered. The camera is now being tested from a lower position, slightly above the front sensor area, to find the angle that gives the best obstacle visibility.

<div align="center">

| Camera Decision | Reason |
| :--- | :--- |
| **Keep the camera facing forward** | Obstacles appear ahead of the robot. |
| **Lower the camera compared with v3** | Reduces upper mass and improves the compact layout. |
| **Remove large mount** | The big structure was not necessary for the camera to function. |
| **Continue testing the angle** | The camera must focus on obstacles, not random field areas. |
| **Remove v3 lights from current design** | v4 does not use auxiliary lights as part of the current layout. |

</div>

This was a systems decision because the camera mount affected more than vision. It also affected weight, center of gravity, cable organization, and calibration time.

<p align="center">
  <strong>We did not remove the camera function. We removed the unnecessary structure around it.</strong>
</p>

---

## ❀ 4.1.7 Decision: Lower the Ultrasonic Sensors ────୨ৎ────────୨ৎ────

The ultrasonic sensors are responsible for wall-distance information. Their job is to help Cheese understand where it is relative to the side walls.

In earlier layouts, the ultrasonic sensors were not positioned as effectively as they could be. If they are too high, the ultrasonic beam may not hit the most useful part of the wall. This can make readings weaker or less consistent.

In v4, the ultrasonic sensors were lowered so they could use more of their ultrasonic sensing potential.

<div align="center">

| Problem | v4 Decision | Expected Improvement |
| :--- | :--- | :--- |
| Sensor beam was not optimally aligned with the walls. | Lower ultrasonic sensors. | Better wall-distance readings. |
| PID had to work with imperfect data. | Improve sensor placement first. | Easier PID tuning. |
| Wall correction could become late or unstable. | Improve physical reading conditions. | More predictable correction behavior. |

</div>

This decision shows a key engineering idea:

<p align="center">
  <strong>Before forcing the software to fix bad data, improve the sensor placement that creates the data.</strong>
</p>

---

## ❀ 4.1.8 Decision: Keep the Color Sensor Placement ────୨ৎ────────୨ৎ────

The color sensor stayed in the same general position because it was already working for its job.

The color sensor faces the floor and detects colored lines used for progress and curve counting. Since this placement already supported the robot’s logic, moving it would have created unnecessary calibration risk.

<div align="center">

| Reason to Keep It | Why It Was Better |
| :--- | :--- |
| **It already faced the floor correctly.** | The color markers are on the mat. |
| **It supported line and curve counting.** | The robot uses it to understand progress. |
| **It was already tested.** | Keeping it avoided new unknowns. |
| **Moving it could change readings.** | Height and angle affect color detection. |

</div>

This decision matters because engineering is not only about changing things. It is also about protecting the parts of the design that already work.

<p align="center">
  <strong>The color sensor stayed because its position matched its function.</strong>
</p>

---

## ❀ 4.1.9 Decision: Change Only the Front Wheels to SPIKE Wheels ────୨ৎ────────୨ৎ────

In v4, only the **front wheels** were changed to SPIKE wheels. The rear wheels were not changed.

This decision was connected to steering behavior. The front wheels are the wheels that guide the robot’s direction, so their grip and turning smoothness are important during curves and corrections.

<div align="center">

| Front Wheel Reason | Why It Helps |
| :--- | :--- |
| **Better grip** | Helps the robot avoid slipping on smooth surfaces. |
| **Smoother turning** | Helps the robot follow steering commands more cleanly. |
| **Better curve behavior** | Front wheel grip affects how the robot enters curves. |
| **Less vibration** | A smoother front contact can make movement more stable. |

</div>

This change should also be documented in other repository sections because it affects more than one subsystem:

<div align="center">

| Repo Section | Why It Should Mention the Wheel Change |
| :--- | :--- |
| **1.1 Mechanical Design** | Wheels are part of mobility and motion. |
| **1.3 Steering and Drive** | The front wheels directly affect steering response. |
| **1.4 Chassis Explanation** | The wheel layout affects the physical robot design. |
| **5.1 Bill of Materials** | The SPIKE front wheels must be listed as parts. |
| **5.2 Build Instructions** | Another team needs to know which wheels go in front. |

</div>

> **Important note:** If encoder-based distance calculations are used, they should be based on the drive wheel system. Since the SPIKE wheels were changed only in the front, they mainly affect steering contact and grip, not the rear drive encoder behavior.

---

## ❀ 4.1.10 Decision: Shorten Only the Arduino Nano USB Cable ────୨ৎ────────୨ৎ────

It is important to document this accurately: we did not shorten all cables.

The EV3 motor and sensor cables stayed the same length. The cable that changed was the USB cable connected to the Arduino Nano. We replaced it with a shorter USB Type-A to Nano cable to reduce clutter around the camera/Nano area.

<div align="center">

| Cable Area | What Changed | Why It Helped |
| :--- | :--- | :--- |
| **Arduino Nano USB cable** | Changed to a shorter cable. | Reduced clutter near the Nano and camera. |
| **EV3 motor cables** | Stayed the same. | They still needed to reach the motors. |
| **EV3 sensor cables** | Stayed the same. | They still needed to reach the sensors. |
| **Overall cable organization** | Improved through layout and placement. | Easier to inspect before testing. |

</div>

This decision shows that wiring improvement does not always mean replacing every cable. Sometimes the better solution is to change the one cable that creates the most clutter and redesign the structure around it.

---

## ❀ 4.1.11 Trade-Off Analysis ────୨ৎ────────୨ৎ────

Every major v4 decision involved a trade-off. A trade-off means gaining something while accepting a possible risk.

<div align="center">

| Decision | Benefit | Trade-Off / Risk | Why We Accepted It |
| :--- | :--- | :--- | :--- |
| **Reduce weight** | Better response and easier calibration. | Removing too much could weaken the structure. | We kept essential supports and removed only unnecessary pieces. |
| **Simplify camera mount** | Lower mass and cleaner front layout. | Camera angle still needs careful testing. | The large mount was not necessary for the camera’s function. |
| **Lower ultrasonic sensors** | Better alignment with side walls. | Sensors may be more exposed to bumps. | Wall readings are critical for PID. |
| **Keep color sensor position** | Avoids recalibrating a working sensor. | It may not look like a visible v4 change. | A working placement should not be changed without reason. |
| **Use SPIKE wheels in front** | Better steering grip and smoother turns. | Different wheel behavior needs testing. | Front grip is important for curve stability. |
| **Shorten Nano USB cable** | Less clutter near camera bridge. | Cable still must reach safely. | It improved organization without changing the full wiring system. |
| **Remove extra pieces** | Less mass and less clutter. | Less redundant support. | The remaining structure was chosen more intentionally. |

</div>

This table shows that v4 was not random. Each change came from a problem and each solution was selected because its benefits were more important than its risk.

---

## ❀ 4.1.12 Risk Identification and Mitigation ────୨ৎ────────୨ৎ────

A risk is something that can make the robot fail even if the design seems correct. In v4, we tried to reduce the risks that were most connected to calibration and reliability.

<div align="center">

| Risk | Why It Matters | Mitigation |
| :--- | :--- | :--- |
| **Robot becomes structurally weak after removing pieces** | Weak structure can flex and change sensor or steering alignment. | Keep essential support and remove only nonfunctional pieces. |
| **PID remains difficult to tune** | Bad PID can cause wall crashes or unstable curves. | Lower sensors, reduce weight, and continue calibration. |
| **Color sensor misses lines** | Missed line detection causes extra or missing curve counts. | Keep working placement and protect from sunlight. |
| **Camera detects obstacles late** | Late detection gives less time to avoid pillars. | Continue calibrating HuskyLens angle and detection timing. |
| **Obstacle parking remains incomplete** | Obstacle path changes final position and timing. | Keep Open parking working and adapt obstacle parking later. |
| **Low battery voltage affects behavior** | Motors and camera can behave differently when power is weak. | Test with charged batteries and avoid tuning on weak voltage. |
| **Cable clutter affects inspection** | Hard-to-see wiring slows debugging. | Shorten the Nano USB cable and organize the layout. |

</div>

Risk mitigation does not mean every risk disappears. It means the team recognized the risk and made a design choice to reduce it.

## ❀ 4.1.13 Current System Status After v4 Decisions ────୨ৎ────────୨ৎ────

The v4 redesign improved the robot, but it did not mean every subsystem became finished at the same time. Some parts are working, while others still need calibration.

<div align="center">

| System | Current Status | Notes |
| :--- | :--- | :--- |
| **Open Challenge driving** | Working overall. | Cheese can complete three laps, but calibration is still being improved. |
| **Open Challenge parking** | Mostly well calibrated. | Parking works when the rest of the code behaves correctly, but it has had issues during testing. |
| **PID** | In progress. | Still needs tuning for smoother wall following and fewer crashes. |
| **Curve counting** | In progress. | Sometimes counts extra or misses lines, so calibration continues. |
| **HuskyLens detection** | Positive progress. | Red is ID 1 and green is ID 2. |
| **Obstacle avoidance** | Still being calibrated. | The robot still needs reliable left/right avoidance without delay. |
| **Obstacle parking** | Pending. | It is not fully adapted to the final obstacle behavior yet. |
| **v4 structure** | Improved. | Lighter, cleaner, lower, and easier to inspect. |

</div>

This status is important because the robot is being documented honestly. v4 is an improvement, not a claim that every subsystem is already perfect.

---

## ❀ 4.1.14 Final Design Decision Summary ────୨ৎ────────୨ৎ────

The strongest v4 lesson was that a robot does not always improve by adding more. Sometimes the best engineering decision is to remove, simplify, and rebuild around the parts that truly matter.

<div align="center">

| v4 Decision | Main Engineering Purpose |
| :--- | :--- |
| **Reduce mass from 888 g to 666 g** | Improve response, reduce stress, and make calibration easier. |
| **Simplify camera mount** | Keep vision function while reducing unnecessary structure. |
| **Lower ultrasonic sensors** | Improve physical wall-detection conditions. |
| **Keep color sensor placement** | Protect a working floor-detection position. |
| **Use SPIKE wheels only in front** | Improve steering grip and curve response. |
| **Shorten Nano USB cable only** | Reduce clutter around the camera bridge. |
| **Remove unnecessary pieces** | Reduce weight and make the robot easier to inspect. |
| **Continue honest obstacle calibration** | Avoid claiming finished behavior before testing proves it. |

</div>

<p align="center">
  <strong>Final key sentence:</strong><br>
  We did not change Cheese only to make it look cleaner. Each v4 change was connected to weight, stability, sensor reliability, easier inspection, or better calibration.
</p>
