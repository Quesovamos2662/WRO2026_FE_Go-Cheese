A design decision is more than a physical modification.

For Go!Cheese, a decision becomes an engineering decision when it can be connected to:

<p align="center">
  <strong>
    Observation → Problem → Decision → Trade-Off → Test → Result → Learning
  </strong>
</p>

The transition from Cheese v3 to Cheese v4 followed this process repeatedly.

Instead of solving every problem by adding another support, sensor mount, cable holder, or structural piece, we began asking a different question:

<p align="center">
  <strong>
    Does this component directly improve the function of the robot?
  </strong>
</p>

This question became one of the main principles behind Cheese v4.

---

# ❀ 4.1.1 Purpose of the Design Decision Log ────୨ৎ────────୨ৎ────

The purpose of this section is to explain **why Cheese looks and behaves the way it does today**.

The final robot alone does not show the complete engineering process.

A judge can see the finished chassis, sensors and wiring, but those elements do not automatically explain:

- why the robot became lighter,
- why the EV3 Brick was lowered,
- why the camera structure changed,
- why the ultrasonic sensors were repositioned,
- why the front wheels changed,
- why auxiliary lighting disappeared,
- or why some working components were intentionally left almost unchanged.

This section therefore documents four important questions.

<div align="center">

| Engineering Question | Purpose |
| :--- | :--- |
| **What problem did we observe?** | Connect the decision to real testing |
| **What did we change?** | Identify the engineering response |
| **What trade-off did we accept?** | Show that every decision has consequences |
| **How did it affect the complete robot?** | Demonstrate systems thinking |

</div>

The objective is not to present v4 as a perfect robot.

The objective is to show how testing progressively produced a better one.

---

# ❀ 4.1.2 Our Systems-Thinking Approach ────୨ৎ────────୨ৎ────

One of the biggest lessons during development was that Cheese cannot be divided into completely independent systems.

A mechanical modification can affect software.

A sensor modification can affect steering.

A battery condition can change how the same software behaves physically.

A camera position can change how much reaction time the obstacle algorithm receives.

For Cheese, the interaction can be summarized as:

<p align="center">
  <strong>
    Structure → Sensor Geometry → Sensor Data → Software Decision → Motor Response → Robot Motion → New Sensor Data
  </strong>
</p>

This creates a continuous feedback system.

<div align="center">

| Subsystem | Can Affect | Example on Cheese |
| :--- | :--- | :--- |
| **Mechanical structure** | Mass, rigidity, sensor alignment | Excess structure increased mass and complexity |
| **Sensor placement** | Measurement quality | Ultrasonic position changes wall readings |
| **Vision placement** | Detection timing | HuskyLens angle changes when a pillar enters view |
| **Power** | Motor response | Battery condition changes physical reaction |
| **Steering geometry** | Curve behavior | Ackermann geometry determines the physical turn |
| **Software** | Corrections and recovery | PID determines when and how strongly Cheese reacts |
| **Testing** | Future decisions | Failures reveal which subsystem needs modification |

</div>

The central lesson became:

<p align="center">
  <strong>
    When one subsystem changes, the behavior of the complete robot can change with it.
  </strong>
</p>

# ❀ 4.1.3 Main Design Constraints ────୨ৎ────────୨ৎ────

Cheese v4 was developed under real engineering constraints.

<div align="center">

| Constraint | Effect on the Design |
| :--- | :--- |
| **Competition rules** | The design must support autonomous navigation, obstacle behavior and parking |
| **Available LEGO components** | Solutions must use parts that are actually available to the team |
| **Limited testing time** | Changes must be practical to build and validate |
| **Robot mass** | Unnecessary structure increases inertia and motor load |
| **Mechanical rigidity** | Removing too much structure can create flex |
| **Sensor reliability** | Sensors must be positioned for useful measurements |
| **Camera visibility** | HuskyLens must see pillars early enough to react |
| **Wiring access** | Components must remain inspectable and repairable |
| **Battery condition** | Physical response can change as available power changes |
| **Calibration time** | Every unnecessary redesign can introduce new variables |

</div>

These constraints pushed v4 toward a simpler philosophy:

<p align="center">
  <strong>
    Keep what works → Remove what does not help → Improve what limits reliability
  </strong>
</p>

# ❀ 4.1.4 From Cheese v3 to Cheese v4 ────୨ৎ────────୨ৎ────

The redesign from v3 to v4 was substantial.

The previous v3 robot had a measured mass of **888.8 g**, commonly rounded to approximately **888 g** in the documentation.

Cheese v4 has a measured mass of **666 g**.

This represents a reduction of approximately:

<p align="center">
  <strong>
    888.8 g → 666 g = 222.8 g removed
  </strong>
</p>

That is approximately **25% of the v3 mass**.

But the redesign involved much more than weight.

  <img src="../../v-photos/v4/removed_structural_parts_from_v3_to_v4.jpg"
       alt="Structural components removed during Cheese v3 to v4 redesign"
       width="72%">
</p>

<p align="center">
  <em>
    Structural components removed while simplifying Cheese from v3 to v4.
    Parts were removed selectively rather than randomly.
  </em>
</p>

<p align="center">
  <img src="../../v-photos/v4/removed_lighting_system_from_v3_to_v4.jpg"
       alt="Lighting system removed during Cheese v3 to v4 redesign"
       width="72%">
</p>

<p align="center">
  <em>
    Auxiliary lighting hardware from the previous configuration was also removed
    as the vision system and physical layout evolved.
  </em>
</p>

The main redesign decisions were:

<div align="center">

| Design Area | v3 | v4 | Main Reason |
| :--- | :--- | :--- | :--- |
| **Mass** | 888.8 g | 666 g | Reduce unnecessary load |
| **Overall structure** | Taller and more complex | Lower and more compact | Improve accessibility and reduce excess structure |
| **EV3 position** | More integrated into upper structure | Lower and flatter | Lower mass distribution and improve access |
| **Large Motor** | Previous mounting layout | Horizontal mounting | Fit compact architecture |
| **Camera support** | Larger upper structure | Simplified | Remove unnecessary mass |
| **HuskyLens position** | Higher | Lower and forward | Improve compactness and field view |
| **Auxiliary lights** | Present | Removed | No longer part of current v4 architecture |
| **Ultrasonic layout** | Earlier placement | Three-sensor layout | Improve wall and forward awareness |
| **Front wheels** | Previous LEGO wheel setup | SPIKE front wheels | Improve front contact during steering |
| **Nano USB** | Longer cable | Shorter cable | Reduce wiring clutter |

</div>

This redesign established the physical foundation for the current software calibration.

# ❀ 4.1.5 Decision 01 — Reduce Robot Mass ────୨ৎ────────୨ৎ────

### Problem

Cheese v3 contained structural elements that had accumulated during earlier development.

Some were necessary when they were introduced, but later versions no longer depended on all of them.

The result was additional mass and complexity.

### Decision

Remove components that no longer served a clear structural, sensing, wiring, or protective purpose.

<p align="center">
  <strong>
    v3: 888.8 g → v4: 666 g
  </strong>
</p>

<div align="center">

| Measurement | Value |
| :--- | :---: |
| **Cheese v3** | **888.8 g** |
| **Cheese v4** | **666 g** |
| **Mass removed** | **222.8 g** |
| **Approximate reduction** | **25%** |

</div>

### Engineering reasoning

For the same propulsion system, reducing unnecessary mass reduces the inertia that must be accelerated, redirected and stopped.

This is especially relevant when Cheese:

- enters a corner,
- changes steering direction,
- performs a PID correction,
- reverses during recovery,
- or slows during parking.

### Trade-off

Removing structure can reduce rigidity.

The goal was therefore **not minimum possible weight**.

The goal was:

<p align="center">
  <strong>
    Minimum unnecessary weight while preserving sufficient structural rigidity.
  </strong>
</p>

### Result

The final v4 structure became substantially lighter and easier to inspect while maintaining the components required for competition operation.

# ❀ 4.1.6 Decision 02 — Lower and Simplify the Main Structure ────୨ৎ────────୨ৎ────

Weight was not the only reason for rebuilding the chassis.

The location of that weight also mattered.

The EV3 Brick was positioned lower and flatter, with the screen facing upward.

The Large Motor was also integrated horizontally into the current layout.

These decisions helped create a robot that is:

- more compact,
- easier to access,
- easier to inspect,
- and less dependent on a tall upper structure.

<p align="center">
  <img src="../../v-photos/v4/ev3_low_position_v4.jpg"

</p>

### Trade-off

A compact structure provides less unused internal space.

This means component placement must be planned more carefully.

### Why we accepted it

The team preferred a deliberate compact layout over keeping empty structure only because it made mounting easier.

# ❀ 4.1.7 Decision 03 — Simplify the HuskyLens Structure ────୨ৎ────────୨ৎ────

The HuskyLens remained necessary for the Obstacle Challenge.

The large structure previously surrounding it did not.

### Problem

The v3 camera arrangement contributed:

- upper mass,
- additional supports,
- wiring complexity,
- and a taller robot profile.

### Decision

Keep the HuskyLens facing forward while simplifying its surrounding structure and lowering its position.

<p align="center">
  <img src="../../v-photos/v4/sensor_placement_cam_v4.jpg"
       alt="Current HuskyLens position on Cheese v4"
       width="65%">
</p>

<p align="center">
  <em>
    Current forward HuskyLens position in Cheese v4.
  </em>
</p>

<p align="center">
  <img src="../../v-photos/v4/huskylens_angle_side_v4.jpg"
       alt="Side view of Cheese v4 HuskyLens angle"
       width="65%">
</p>

<p align="center">
  <em>
    Side view used to evaluate the current HuskyLens height and viewing angle.
  </em>
</p>

### System effect

Camera placement affects much more than image quality.

<p align="center">
  <strong>
    Camera Height + Camera Angle → Detection Timing → Available Reaction Distance → Obstacle Avoidance
  </strong>
</p>

A pillar detected correctly but too late can still produce a failed maneuver.

### Trade-off

A lower camera requires careful angle calibration so that the field of view remains useful.

### Current result

The current HuskyLens configuration can recognize the competition pillar colors.

Current training uses:

<div align="center">

| Pillar | HuskyLens ID | Required Passing Side |
| :--- | :---: | :---: |
| 🟢 **Green** | **Color ID 1** | **Left** |
| 🔴 **Red** | **Color ID 2** | **Right** |

</div>

The remaining Obstacle Challenge problem is therefore not simply color recognition.

It is reliably converting detection into avoidance and recovery.

# ❀ 4.1.8 Decision 04 — Remove the Auxiliary Lighting System ────୨ৎ────────୨ৎ────

Cheese v3 used additional lighting hardware around the sensing area.

The current v4 architecture does **not** use those auxiliary lights.

### Decision

Remove:

- the lights,
- their structural supports,
- associated mounting pieces,
- and the additional power-support structure that was no longer required.

### Why

The v4 camera position and sensing configuration changed enough that maintaining the previous lighting structure was no longer justified by its cost in mass and complexity.

### Trade-off

Removing controlled lighting means ambient conditions must still be considered during testing.

### Result

The front structure became simpler and lighter.

This is a good example of a component being useful in one version but unnecessary in the next.

<p align="center">
  <strong>
    A previous solution does not need to remain forever if the original problem changes.
  </strong>
</p>

---

# ❀ 4.1.9 Decision 05 — Improve Ultrasonic Sensor Placement ────୨ৎ────────୨ৎ────

The Open Challenge depends heavily on ultrasonic measurements.

Cheese v4 uses:

- a left ultrasonic sensor,
- a right ultrasonic sensor,
- and a front ultrasonic sensor.

<p align="center">
  <img src="../../v-photos/v4/side_sensor_layout_v4.jpg"
       alt="Cheese v4 lateral ultrasonic sensor layout"
       width="72%">
</p>

<p align="center">
  <em>
    Current side-sensor layout used for wall-distance information.
  </em>
</p>

### Problem

Software cannot produce reliable wall correction if the physical measurements entering the controller are unreliable.

### Decision

Position the lateral ultrasonic sensors lower and directly toward the side walls while maintaining a front ultrasonic for forward safety.

<div align="center">

| Sensor | Main Function |
| :--- | :--- |
| **Left Ultrasonic** | Left-side distance |
| **Right Ultrasonic** | Right-side distance |
| **Front Ultrasonic** | Forward clearance and recovery support |

</div>

### Engineering reasoning

The order of improvement should be:

<p align="center">
  <strong>
    Better Sensor Geometry → Better Measurements → Better PID Input → Better Steering Decision
  </strong>
</p>

not:

<p align="center">
  <strong>
    Poor Measurement → More Aggressive Software → More Instability
  </strong>
</p>

### Trade-off

Lower sensors can be physically more exposed.

### Why we accepted it

Wall-distance quality is fundamental to Open navigation, so measurement quality was prioritized.

# ❀ 4.1.10 Decision 06 — Preserve the Working Color-Sensor Architecture ────୨ৎ────────୨ৎ────

Not every v4 decision involved replacing something.

The color sensor already had a useful floor-facing structural position.

<p align="center">
  <img src="../../v-photos/v4/color_sensor_front_layout_v4.jpg"
       alt="Cheese v4 color sensor position"
       width="58%">
</p>

<p align="center">
  <img src="../../v-photos/v4/color_sensor_floor_gap_v4.jpg"
       alt="Cheese v4 color sensor floor gap"
       width="58%">
</p>

In v4, the sensor remained in the same **general structural location**, while its floor gap was adjusted slightly lower to improve detection.

### Earlier problem

Ambient lighting affected floor-color recognition during earlier testing.

An improvised light-blocking cover was tested.

However, the cover could drag against the field and created a new mechanical problem.

### Decision

Remove the dragging cover and improve the sensor's physical floor distance instead.

### Result

The current sensor position provides sufficiently improved detection that an external light-blocking cover is not part of normal v4 operation.

This produced an important lesson:

<p align="center">
  <strong>
    A fix that solves one problem but creates another is not automatically a good engineering solution.
  </strong>
</p>

# ❀ 4.1.11 Decision 07 — Change Only the Front Wheels ────୨ৎ────────୨ৎ────

Cheese v4 changed the **front wheels** to LEGO SPIKE wheel assemblies.

The rear drive wheels remained part of the EV3/Technic drive system.

<p align="center">
  <img src="../../v-photos/v4/front_spike_wheels_v4.jpg"
       alt="Cheese v4 SPIKE front wheel assemblies"
       width="68%">
</p>

<p align="center">
  <em>
    Current SPIKE front-wheel configuration used with the Ackermann steering system.
  </em>
</p>

### Why only the front?

The front wheels determine the direction commanded by the Ackermann steering mechanism.

The rear wheels provide propulsion.

Changing only the front therefore allowed us to modify the steering contact without unnecessarily redesigning the rear drive system.

### Expected advantages

- improved front contact,
- cleaner steering response,
- reduced unwanted sliding during turns,
- and better compatibility with the current steering geometry.

### Trade-off

Different front-wheel behavior changes how the robot physically responds to steering commands.

This required real-track testing.

### Systems-thinking connection

<p align="center">
  <strong>
    Front Wheel Contact → Physical Steering Response → Curve Shape → PID Recovery
  </strong>
</p>

# ❀ 4.1.12 Decision 08 — Shorten Only the Nano USB Cable ────୨ৎ────────୨ৎ────

It is important to document this decision accurately.

We did **not** replace or shorten every EV3 cable.

The main cable changed was the USB connection between the Arduino Nano and the EV3.

<p align="center">
  <img src="../../v-photos/v4/ev3_usb_to_nano_v4.jpg"
       alt="Cheese v4 EV3 USB to Arduino Nano connection"
       width="68%">
</p>

### Problem

The previous longer USB cable created unnecessary clutter around the Nano and vision-system area.

### Decision

Use a shorter USB Type-A to Mini-B connection for the Arduino Nano.

<div align="center">

| Cable | v4 Decision |
| :--- | :--- |
| **Nano USB** | Shorter cable |
| **EV3 motor cables** | Retained |
| **EV3 sensor cables** | Retained |

</div>

### Result

The communication architecture remained the same:

<p align="center">
  <strong>
    HuskyLens → I²C → Arduino Nano → USB Serial → EV3
  </strong>
</p>

but the physical wiring became easier to manage.

<p align="center">
  <img src="../../v-photos/v4/wiring_overview_v4.jpg"
       alt="Cheese v4 wiring overview"
       width="72%">
</p>

This demonstrates another important principle:

<p align="center">
  <strong>
    Improve the part creating the problem instead of redesigning everything around it.
  </strong>
</p>

# ❀ 4.1.13 Decision 09 — Keep the Arduino Nano Flexible ────୨ৎ────────୨ৎ────

The Arduino Nano serves as the communication bridge between the HuskyLens and EV3.

However, v4 does not use a large permanent LEGO mounting structure dedicated only to holding the Nano.

<p align="center">
  <img src="../../v-photos/v4/arduino_nano_position_v4.jpg"
       alt="Current Arduino Nano position on Cheese v4"
       width="62%">
</p>

The Nano is positioned so that:

- it remains connected,
- its cable does not interfere with moving parts,
- it can be inspected,
- and it does not require another heavy structural tower.

### Trade-off

A less rigidly mounted electronic component requires careful cable positioning.

### Why we accepted it

The Nano is lightweight and does not need the same structural support as a motor, EV3 Brick, or steering assembly.

Adding a large dedicated mount would recreate the same structural complexity that v4 was designed to remove.

# ❀ 4.1.14 Decision 10 — Prioritize Accessibility and Inspection ────୨ৎ────────୨ৎ────

Competition robots are repeatedly:

- programmed,
- tested,
- charged,
- repaired,
- recalibrated,
- and inspected.

A component that is impossible to reach creates unnecessary testing time.

The v4 architecture therefore considers access as an engineering requirement.

<p align="center">
  <img src="../../v-photos/v4/ev3_battery_access_v4.jpg"
       alt="Cheese v4 EV3 battery access"
       width="62%">
</p>

<p align="center">
  <em>
    Battery accessibility was preserved so the robot can be prepared efficiently between tests.
  </em>
</p>

Accessibility affects reliability because:

<p align="center">
  <strong>
    Easier Inspection → Faster Diagnosis → Faster Repair → More Testing Time
  </strong>
</p>

This does not directly make Cheese drive faster.

It makes the engineering process around Cheese more effective.

# ❀ 4.1.15 Major Trade-Off Analysis ────୨ৎ────────୨ৎ────

Every major v4 decision involved a compromise.

<div align="center">

| Decision | Benefit | Risk / Trade-Off | Why Accepted |
| :--- | :--- | :--- | :--- |
| **Reduce mass** | Less unnecessary load | Too much removal could weaken chassis | Essential supports were retained |
| **Lower EV3** | More compact mass distribution | Less unused internal space | Compactness was more valuable |
| **Simplify camera mount** | Less upper structure | Camera angle becomes critical | Large mount was unnecessary |
| **Remove auxiliary lights** | Less mass and complexity | Greater dependence on ambient conditions | Current layout no longer justified them |
| **Lower ultrasonics** | Better wall geometry | Greater physical exposure | Reliable wall readings are essential |
| **Lower color-sensor gap** | Better floor detection | Too low could contact mat | Height was adjusted through testing |
| **Remove sensor cover** | No dragging structure | Less physical light shielding | Current sensor position performs sufficiently |
| **SPIKE front wheels** | Improved steering contact | Different physical response | Front steering behavior benefited |
| **Shorter Nano USB** | Less clutter | Cable must still reach safely | Same architecture with cleaner wiring |
| **Flexible Nano placement** | Less dedicated structure | Requires careful cable management | Nano does not require heavy support |

</div>

This table represents the core of the v4 redesign:

<p align="center">
  <strong>
    No decision was completely free.
    Each improvement was accepted because its benefit was more valuable than its remaining risk.
  </strong>
</p>

# ❀ 4.1.16 Failure → Decision → Result Log ────୨ৎ────────୨ৎ────

The strongest design decisions came from failures or limitations observed during testing.

<div align="center">

| Observation / Failure | Engineering Cause | Decision | Result / Learning |
| :--- | :--- | :--- | :--- |
| **Robot accumulated unnecessary structure** | Old solutions remained after design changed | Remove nonessential parts | v4 mass reduced to 666 g |
| **Upper structure became complex** | Camera and lighting supports accumulated | Simplify front/top structure | Cleaner and lower architecture |
| **Wall data limited control quality** | Sensor geometry affects measurements | Improve ultrasonic placement | Better physical conditions for PID |
| **Color detection affected by ambient light** | Floor sensing is sensitive to environment | Tested physical cover | Light was blocked, but cover created drag |
| **Cover dragged on mat** | Mechanical fix introduced new failure | Remove cover and lower sensor slightly | Simpler current color architecture |
| **Vision structure added mass** | Camera function and camera support were treated together | Keep camera, reduce support | Vision retained with less structure |
| **Long Nano cable created clutter** | Excess cable near electronics | Shorten only Nano USB | Cleaner wiring |
| **Steering contact needed improvement** | Front-wheel behavior affects turns | Use SPIKE front wheels | New steering contact tested |
| **Battery condition changed behavior** | Motors respond physically to available power | Consider battery during calibration | Avoid unnecessary software retuning |

</div>

This process can be summarized as:

<p align="center">
  <strong>
    Failure → Identify Cause → Change the Correct Subsystem → Test Again
  </strong>
</p>

# ❀ 4.1.17 Risk Identification and Mitigation ────୨ৎ────────୨ৎ────

A design can improve while still containing risks.

Recognizing those risks is part of engineering.

<div align="center">

| Current Risk | System Effect | Mitigation |
| :--- | :--- | :--- |
| **Structure becomes too flexible** | Sensor or steering alignment can change | Retain essential structural supports |
| **Ultrasonic reading fluctuates** | PID may request incorrect correction | Physical placement + software filtering |
| **Color line is missed** | Curve count can become incorrect | Improved floor gap + software validation |
| **Camera sees pillar too late** | Avoidance time decreases | Continue HuskyLens angle/timing calibration |
| **Obstacle avoidance is weak** | Cheese may contact/carry pillar | Continue avoidance-strength tuning |
| **Poor post-obstacle recovery** | Next pillar may enter view from bad heading | Recovery remains current obstacle priority |
| **Parking count is wrong** | Parking activates early or late | Validate curve-count logic |
| **Battery becomes weak** | Motor response changes | Test with appropriate battery condition |
| **Cable interferes with mechanism** | Mechanical or communication failure | Keep wiring short, visible and secured |

</div>

Risk mitigation does not mean that every risk has disappeared.

It means the team knows **what can fail, why it matters, and what is being done about it**.

# ❀ 4.1.18 Decisions We Intentionally Did NOT Make ────୨ৎ────────୨ৎ────

An engineering log should also explain changes that were avoided.

<div align="center">

| Possible Change | Why We Did Not Do It |
| :--- | :--- |
| **Replace every cable** | Only the Nano USB was creating significant clutter |
| **Remove every structural support** | Low weight is useless if the chassis becomes flexible |
| **Redesign the rear wheels** | The front steering contact was the area being changed |
| **Add the auxiliary lights back** | Current v4 architecture does not require them for normal operation |
| **Create a large Nano mount** | It would add structure without enough functional benefit |
| **Move the color sensor to a completely new location** | Its general floor-facing placement already worked |
| **Solve poor sensor data only through software** | Physical sensor geometry should be corrected first |

</div>

This was an important change in our engineering process.

<p align="center">
  <strong>
    Not changing something can also be a design decision.
  </strong>
</p>

# ❀ 4.1.20 V4 Decision Priority Map ────୨ৎ────────୨ৎ────

The decisions made during the redesign can be grouped by their main purpose.

<div align="center">

| Priority | Decisions |
| :--- | :--- |
| ⚖️ **Reduce unnecessary mass** | Remove excess structure, remove lighting supports, simplify camera structure |
| 📡 **Improve sensor information** | Lower ultrasonics, optimize color-sensor floor gap, calibrate camera angle |
| 🛞 **Improve physical motion** | SPIKE front wheels, compact structure, Ackermann integration |
| 🔌 **Improve accessibility** | Shorter Nano USB, cleaner wiring, accessible EV3/battery |
| 💻 **Support software reliability** | Better physical sensor inputs before increasing software correction |
| 🧪 **Improve testing efficiency** | Fewer unnecessary parts, easier inspection and faster diagnosis |

</div>

The priorities are connected.

For example:

<p align="center">
  <strong>
    Less Structure → Lower Mass → Easier Motion → Cleaner Sensor Response → Easier Calibration
  </strong>
</p>

and:

<p align="center">
  <strong>
    Better Sensor Placement → Better Data → Better Software Decisions → Better Physical Navigation
  </strong>
</p>

# ❀ 4.1.21 Final Design Decision Summary ────୨ৎ────────୨ৎ────

Cheese v4 was developed by simplifying the robot around the systems that matter most.

<div align="center">

| v4 Decision | Main Engineering Purpose |
| :--- | :--- |
| **Reduce 888.8 g to 666 g** | Remove unnecessary load and simplify calibration |
| **Lower and compact the chassis** | Improve layout and accessibility |
| **Lower the EV3 Brick** | Reduce upper structure and improve access |
| **Simplify HuskyLens support** | Preserve vision with less structure |
| **Remove auxiliary lighting** | Eliminate hardware no longer justified by current layout |
| **Use three ultrasonic sensors** | Improve lateral and forward awareness |
| **Improve ultrasonic placement** | Improve the data entering navigation control |
| **Keep color sensor in same general area** | Preserve a proven sensing architecture |
| **Adjust color-sensor floor gap** | Improve detection without a dragging cover |
| **Use SPIKE front wheels** | Improve steering contact |
| **Shorten only Nano USB** | Reduce clutter without unnecessary rewiring |
| **Keep Nano mounting lightweight** | Avoid rebuilding unnecessary structural complexity |
| **Preserve battery access** | Make repeated testing easier |
| **Continue obstacle calibration honestly** | Do not claim reliability before testing proves it |

</div>

The strongest lesson from the v3 → v4 redesign was not that lighter is always better or that fewer parts are always better.

It was this:

<p align="center">
  <strong>
    Every component should justify the complexity it adds to the complete system.
  </strong>
</p>

Cheese v4 became lighter, cleaner and easier to calibrate because the team began evaluating components according to their **function and system effect**, rather than simply keeping every solution introduced during earlier prototypes.

The resulting engineering philosophy is:

<p align="center">
  <strong>
    Observe → Understand → Simplify → Test → Keep What Works
  </strong>
</p>
