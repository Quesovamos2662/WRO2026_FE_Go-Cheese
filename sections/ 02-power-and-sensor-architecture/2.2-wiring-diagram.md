The sensor architecture of Cheese v4 was designed around one main idea:

> **Each sensor should observe a specific part of the environment and provide information that the software can convert into a driving decision.**

The current robot combines:

- **three ultrasonic sensors** for distance measurement,
- **one EV3 Color Sensor** for floor detection,
- **one HuskyLens camera** for obstacle recognition,
- and an **Arduino Nano** that transfers vision information to the EV3.

The position of each sensor is important because sensor readings are only useful when the sensor can reliably observe the area needed by the navigation algorithm.

---

## ❀ 2.2.1 Current Sensor Configuration ────୨ৎ────────୨ৎ────

The current Cheese v4 sensing system is divided into three layers.

| Sensor Layer | Hardware | Main Function |
| :--- | :--- | :--- |
| **Distance** | Left Ultrasonic Sensor | Measures distance from the left side |
| **Distance** | Right Ultrasonic Sensor | Measures distance from the right side |
| **Distance** | Front Ultrasonic Sensor | Detects objects or walls in front of Cheese |
| **Floor** | EV3 Color Sensor | Detects the colored track markings |
| **Vision** | HuskyLens | Detects red and green obstacles |

These sensors do not all perform the same type of navigation.

Instead, the software combines their information depending on the situation.

<p align="center">
  <strong>
    Environment → Sensors → EV3 Logic → Steering / Drive Response
  </strong>
</p>

## ❀ 2.2.3 Left & Right Ultrasonic Sensors ────୨ৎ────────୨ৎ────

The two lateral ultrasonic sensors provide the robot with information about the walls beside it.

<p align="center">
  <img src="../../v-photos/v4/side_sensor_layout_v4.jpg"
       alt="Cheese v4 lateral ultrasonic sensor configuration"
       width="72%">
</p>

<p align="center">
  <em>
    Side sensor layout showing the lateral ultrasonic sensing configuration.
  </em>
</p>

Unlike a camera, the ultrasonic sensors do not identify what an object is.

Their job is simpler:

> **Measure how far away the nearest surface is.**

This information is especially useful for maintaining a controlled position relative to the track walls.

| Reading Situation | Software Interpretation |
| :--- | :--- |
| Distance is near target | Maintain current path |
| Robot approaches wall | Apply steering correction |
| Distance becomes dangerously small | Increase wall avoidance |
| Side readings change during a curve | Use the change as navigation information |

The side ultrasonic sensors therefore form an important part of the wall-following and PID control architecture.

---

## ❀ 2.2.4 Front Ultrasonic Sensor ────୨ৎ────────୨ৎ────

The front ultrasonic sensor provides a different type of information.

Instead of measuring the lateral relationship with the walls, it observes the space directly in front of Cheese.

<p align="center">
  <img src="../../v-photos/v4/huskylens_front_ultrasonic_stack_v4.jpg"
       alt="HuskyLens and front ultrasonic sensor stack on Cheese v4"
       width="62%">
</p>

<p align="center">
  <em>
    Front sensing stack showing the relationship between the HuskyLens and
    the front ultrasonic sensor.
  </em>
</p>

The front ultrasonic sensor is used primarily as a **safety and distance sensor**.

In the current Open Challenge software, it supports:

- front-wall detection,
- emergency reverse behavior,
- distance awareness,
- and parking alignment.

This creates an additional safety layer.

```text
Normal Driving
      │
      ▼
Front Distance Checked
      │
      ├── Safe ─────────────→ Continue
      │
      └── Too Close
              │
              ▼
        Reverse / Recover
```

The front ultrasonic sensor does **not** count curves.

Curve counting is handled by the color sensor.

## ❀ 2.2.6 HuskyLens Position & Field of View ────୨ৎ────────୨ৎ────

The position and angle of the HuskyLens directly affect obstacle detection.

<p align="center">
  <img src="../../v-photos/v4/huskylens_angle_side_v4.jpg"
       alt="Side view of HuskyLens angle in Cheese v4"
       width="62%">
</p>

<p align="center">
  <em>
    Side view showing the current HuskyLens height and viewing angle.
  </em>
</p>

This became particularly important during obstacle testing.

A camera can be functioning correctly and still fail to provide useful information if:

- the obstacle is outside its field of view,
- the robot exits a curve at an unfavorable angle,
- the obstacle enters the image too late,
- or Cheese is not sufficiently aligned with the straight.

Therefore, camera placement is part of the navigation system itself.

The engineering relationship is:

<p align="center">
  <strong>
    Camera Position → Field of View → Detection Time → Avoidance Time
  </strong>
</p>

This is one reason the v4 HuskyLens position was kept relatively low and directed toward the useful obstacle-detection region.

## ❀ 2.2.7 Color Sensor Placement ────୨ৎ────────୨ৎ────

The EV3 Color Sensor is mounted near the front-bottom area of Cheese and points toward the floor.

<p align="center">
  <img src="../../v-photos/v4/color_sensor_front_layout_v4.jpg"
       alt="Front layout of Cheese v4 color sensor"
       width="47%">
  &nbsp;
  <img src="../../v-photos/v4/color_sensor_floor_gap_v4.jpg"
       alt="Cheese v4 color sensor distance from floor"
       width="47%">
</p>

<p align="center">
  <em>
    Current color-sensor position and its physical relationship with the track surface.
  </em>
</p>

The color sensor is responsible for detecting the colored floor markings used by the Open Challenge navigation logic.

In the current software, the relevant floor classifications are simplified into:

| Detected Color | Software Classification |
| :--- | :--- |
| Blue | **BLUE** |
| Red / Yellow / Brown range | **ORANGE** |
| Other floor | No curve color |

A curve is not accepted simply because one color appears.

The software checks a valid color transition together with steering behavior.

Examples of valid transitions include:

```text
BLUE → ORANGE
```

or

```text
ORANGE → BLUE
```

This makes the color sensor part of the robot's **curve-counting system**, not just a basic color detector.

---

## ❀ 2.2.8 Why the Color Sensor Was Lowered ────୨ৎ────────୨ৎ────

Earlier versions experienced problems with environmental light.

Sunlight and changing illumination could affect the reliability of floor-color detection.

An improvised physical light-blocking solution was tested, but it created another mechanical problem: the structure could drag against the track.

The final v4 solution was simpler.

The color sensor remained in the same general structural area but was positioned **slightly lower and closer to the floor**.

This improved the practical readings enough that the temporary light-blocking structure was no longer required during normal operation.

The development process can be summarized as:

```text
Unstable color readings
        ↓
Environmental light identified as a factor
        ↓
Physical cover tested
        ↓
Cover created mechanical interference
        ↓
Sensor position adjusted
        ↓
Sensor moved slightly lower
        ↓
More reliable floor detection
```

This was an important engineering lesson because the final solution was not additional software.

It was a **mechanical change to improve sensor data quality before the software processed it**.

## ❀ 2.2.9 HuskyLens Vision System ────୨ৎ────────୨ৎ────

The HuskyLens is used during the Obstacle Challenge to identify colored pillars.

The current recognition configuration distinguishes:

| HuskyLens ID | Obstacle | Required Navigation |
| :---: | :---: | :--- |
| **ID 1** | Red | Pass on the **right** |
| **ID 2** | Green | Pass on the **left** |

The camera does not directly control the motors.

Instead, its information travels through the external vision interface:

```text
HuskyLens
    │
   I2C
    │
    ▼
Arduino Nano
    │
 USB Serial
    │
    ▼
EV3
    │
Navigation Logic
    │
    ▼
Steering + Drive
```

The Arduino Nano receives the camera information and sends simplified data to the EV3.

The current communication concept includes:

```text
R, xCenter, width
G, xCenter, width
N, 0, 0
```

Where:

- `R` represents a detected red obstacle,
- `G` represents a detected green obstacle,
- `N` represents no valid obstacle,
- `xCenter` describes the horizontal position in the camera image,
- and `width` provides information about the detected block size.

The obstacle-navigation software can then convert this information into a steering bias.

## ❀ 2.2.11 Sensor Validation ────୨ৎ────────୨ৎ────

Sensor information is not automatically assumed to be perfect.

Real sensors can produce:

- temporary detection loss,
- sudden distance changes,
- reflections,
- lighting-related color changes,
- or detections that disappear between control cycles.

For this reason, Cheese uses software validation and filtering where necessary.

The general strategy is:

```text
Raw Sensor Reading
        ↓
Validation / Filtering
        ↓
Navigation Interpretation
        ↓
Steering Decision
        ↓
Motor Command
```

For example, the Open Challenge code filters ultrasonic readings before using them in the PID controller.

Color detection also uses additional conditions such as:

- valid color sequence,
- steering confirmation,
- time window,
- and curve cooldown.

This prevents a single raw reading from automatically becoming a major navigation event.

## ❀ 2.2.12 Sensor Roles by Challenge ────୨ৎ────────୨ৎ────

Not every sensor has the same importance in both WRO rounds.

### Open Challenge

| Sensor | Main Role |
| :--- | :--- |
| Left Ultrasonic | Wall-distance control |
| Right Ultrasonic | Wall-distance control |
| Front Ultrasonic | Safety, recovery and parking |
| Color Sensor | Curve detection and counting |
| HuskyLens | Not required for Open navigation |

### Obstacle Challenge

| Sensor / Device | Main Role |
| :--- | :--- |
| Left Ultrasonic | Wall protection |
| Right Ultrasonic | Wall protection |
| Front Ultrasonic | Front-distance protection/recovery |
| Color Sensor | Track/curve information |
| HuskyLens | Red/green obstacle recognition |
| Arduino Nano | Transfers camera information to EV3 |

This distinction is important.

The robot contains multiple sensing systems, but the software decides which information has priority depending on the current navigation situation.

---

## ❀ 2.2.13 Sensor Placement as an Engineering Variable ────୨ৎ────────୨ৎ────

During development, we learned that changing the software is not always the correct response to a sensor problem.

A sensor can produce poor information because of:

| Problem | Possible Cause |
| :--- | :--- |
| Color reading unstable | Sensor height / external lighting |
| Obstacle detected too late | Camera position or angle |
| Wall correction inconsistent | Ultrasonic geometry / filtering |
| False or temporary reading | Sensor noise |
| Obstacle lost after curve | Robot position relative to camera FOV |

This produced an important development rule:

<p align="center">
  <strong>
    Improve the physical measurement before compensating for bad measurements in software.
  </strong>
</p>

This principle influenced both the color-sensor adjustment and HuskyLens testing.

## ❀ 2.2.14 Current Sensor Strengths & Limitations ────୨ৎ────────୨ৎ────

| System | Current Strength | Remaining Limitation |
| :--- | :--- | :--- |
| **Side ultrasonics** | Useful for continuous wall-distance control | Readings still depend on robot angle |
| **Front ultrasonic** | Provides an independent safety layer | Must be calibrated with recovery behavior |
| **Color sensor** | Current lower position provides reliable Open detection | A missed count can still affect parking |
| **HuskyLens** | Can distinguish red and green obstacles | Detection timing/FOV can still affect avoidance |
| **Nano interface** | Allows external vision data to reach EV3 | Adds another communication layer |
| **Combined system** | Multiple sensors provide complementary information | Requires careful software priority management |

The current Open sensing architecture is close to final.

The obstacle sensing architecture is still being calibrated because camera detection, obstacle avoidance, and post-obstacle recovery must work together reliably.

## ✦ Engineering Decisions & Lessons ─── ⋆⋅☆⋅⋆ ───

### 1. More sensors do not automatically produce better navigation

Each sensor must have a clearly defined responsibility.

Adding information that the software cannot interpret reliably can make the controller more complicated rather than more accurate.

### 2. Sensor placement is part of software performance

The color sensor became more reliable after changing its physical height.

The HuskyLens detection behavior also depends heavily on its position and field of view.

Therefore, sensor performance is a combined **mechanical + electrical + software** problem.

### 3. Different sensors should complement each other

The HuskyLens identifies obstacle color.

The ultrasonic sensors measure distance.

The color sensor reads the track.

None of these sensors completely replaces the others.

### 4. Raw detections should be validated

Sensor noise and temporary detections can create incorrect navigation decisions.

Filtering, confirmations, cooldowns, and safety conditions help convert raw measurements into more reliable actions.

### 5. The most difficult problem is not always detection

During obstacle development, Cheese has been able to detect obstacles, but reliable avoidance also depends on:

> **Detection → Reaction → Passing the obstacle → Recovery → Alignment for the next obstacle**

This is why post-obstacle recovery remains one of the main areas being calibrated.

---

## ✦ 2.2 Final Sensor Architecture Summary ─── ⋆⋅☆⋅⋆ ───

Cheese v4 uses a multi-sensor architecture designed around complementary information.

The **three ultrasonic sensors** provide distance awareness.

The **EV3 Color Sensor** detects floor markings and supports curve counting.

The **HuskyLens** identifies red and green obstacles.

The **Arduino Nano** provides the communication bridge required to transfer vision information to the EV3.

Together, the sensing chain becomes:

<p align="center">
  <strong>
    Physical Environment
    → Sensor Measurement
    → Validation
    → EV3 Navigation Logic
    → Motor Response
  </strong>
</p>

The development of v4 demonstrated that reliable sensing depends not only on code, but also on sensor height, orientation, field of view, mechanical stability, and the way multiple sensors are combined.
