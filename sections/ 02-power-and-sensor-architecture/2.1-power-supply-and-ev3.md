The power architecture of Cheese v4 was designed around two requirements:

> **Provide enough power for repeatable testing while keeping the EV3 Brick accessible, mechanically stable, and easy to inspect.**

The EV3 Brick is the center of the robot's control system. It executes the navigation software, reads the LEGO sensors, controls the motors, and provides the main interface between software and the physical robot.

Detailed electrical connections are intentionally separated into **Section 2.2 — Wiring Diagram**.

---

## ❀ 2.1.1 Main Power Source ────୨ৎ────────୨ৎ────

The primary energy source of Cheese v4 is the **LEGO MINDSTORMS EV3 rechargeable battery**.

The battery is installed directly in the EV3 Brick, which then supplies the LEGO devices connected to the robot.

## ❀ 2.1.2 EV3 Brick: Central Controller ────୨ৎ────────୨ৎ────

The EV3 Brick is not only the battery carrier.

It is the **central processing and control unit** of Cheese.

Its main responsibilities are:

| EV3 Responsibility | Function |
| :--- | :--- |
| **Program execution** | Runs the navigation software |
| **Motor control** | Commands propulsion and steering |
| **Sensor acquisition** | Receives LEGO sensor measurements |
| **Power distribution** | Supplies connected LEGO electronics |
| **Communication** | Provides the interface to the external vision subsystem |
| **Testing interface** | Allows programs and robot behavior to be inspected |

This creates the basic control relationship:

<p align="center">
  <strong>
    Battery → EV3 Controller → Sensor Processing → Motor Commands → Robot Movement
  </strong>
</p>

The exact physical connections and port assignments are documented separately in **2.2 Wiring Diagram**.

## ❀ 2.1.4 Accessibility as a Design Requirement ────୨ৎ────────୨ৎ────

A controller that is difficult to access creates problems during rapid testing.

During development, the team frequently needs to:

1. turn Cheese on and off,
2. select or start programs,
3. inspect the EV3,
4. connect development equipment,
5. charge or exchange the battery,
6. and troubleshoot the robot.

For this reason, accessibility was considered during the v4 redesign.

<p align="center">
  <strong>
    Compact design ≠ inaccessible electronics
  </strong>
</p>

The goal was to make Cheese smaller and cleaner **without burying the EV3 inside the chassis**.

---

## ❀ 2.1.5 Power Consistency During Testing ────୨ৎ────────୨ৎ────

Battery condition became an important experimental variable.

Cheese can still operate when the battery is partially discharged, but the physical response of the motors may begin to differ from the behavior observed with a well-charged battery.

This matters because autonomous navigation follows a chain:

<p align="center">
  <strong>
    Sensor Detection → Software Decision → Motor Response → Physical Movement
  </strong>
</p>

Even when the software command remains identical, a change in motor response can alter the final path.

| Battery Condition | Observed Engineering Concern |
| :--- | :--- |
| **Charged** | More consistent response during testing |
| **Partially discharged** | Behavior may begin to differ from previous tuning |
| **Weak** | Steering and propulsion comparisons become less reliable |
| **Different charge between tests** | Can make software changes difficult to evaluate |

---

## ❀ 2.1.6 Why Battery Condition Matters to Navigation ────୨ৎ────────୨ৎ────

Cheese relies on closed-loop corrections, steering response, curve behavior, reverse recovery, and controlled driving speed.

The software calculates what Cheese should do, but the **motors physically execute those commands**.

Therefore:

> **A correct software command does not guarantee the same physical result if the power condition changes significantly.**

For example, a curve becoming wider does not automatically prove that the curve or PID parameters are wrong.

Possible variables include:

- battery condition,
- mechanical friction,
- wheel grip,
- sensor measurements,
- steering response,
- and software parameters.

Changing software to compensate for a weak battery could create the opposite problem when a charged battery is installed again.

---

## ❀ 2.1.7 Battery Rotation as a Testing Control ────୨ৎ────────୨ৎ────

Using two rechargeable batteries became part of the team's testing procedure.

Consider two autonomous tests:

| Variable | Test A | Test B |
| :--- | :---: | :---: |
| Software | Same | Same |
| Robot structure | Same | Same |
| Sensor configuration | Same | Same |
| Battery condition | Charged | Weak |
| Robot behavior | Stable | Different |

Without considering battery condition, the team could incorrectly attribute the difference to software.

Our testing principle therefore became:

<p align="center">
  <strong>
    Control the power condition before changing another system.
  </strong>
</p>

This is especially important when comparing:

- PID values,
- steering corrections,
- curve parameters,
- driving speed,
- reverse behavior,
- and parking performance.

---

## ❀ 2.1.8 v3 → v4 Electrical Simplification ────୨ৎ────────୨ৎ────

Cheese v3 experimented with an auxiliary lighting system intended to improve sensing conditions.

However, this system also required additional:

- wiring,
- mounting hardware,
- supporting structure,
- and electrical components.

During the v4 redesign, the sensor arrangement and overall structure were simplified.

The permanent auxiliary lighting system was removed.

  <img src="../../v-photos/v4/removed_lighting_system_from_v3_to_v4.jpg"
       alt="Lighting system removed from Cheese v3 to Cheese v4"
       width="68%">
</p>

<p align="center">
  <em>
    Components associated with the previous auxiliary lighting architecture
    that were removed during the v4 redesign.
  </em>
</p>

| Cheese v3 | Cheese v4 |
| :--- | :--- |
| Auxiliary lighting tested | No permanent auxiliary lighting |
| Additional electrical hardware | Reduced electrical hardware |
| Additional supporting structure | Simplified upper structure |
| More system complexity | Cleaner architecture |

This produced an important engineering rule:

> **A component should remain only when its practical benefit justifies its weight, wiring, structural support, and complexity.**

## ✦ Engineering Decisions & Lessons ─── ⋆⋅☆⋅⋆ ───

### 1. Power is an experimental variable

Battery condition can change motor response and therefore affect the physical path even when the software is unchanged.

### 2. Accessibility matters

The EV3 must remain accessible because Cheese is repeatedly programmed, inspected, charged, and tested.

### 3. Electrical and mechanical design are connected

Moving the EV3 lower affected not only accessibility but also the physical organization of the robot.

### 4. Repeatability matters more than one successful run

A configuration is more useful when Cheese can reproduce its behavior under controlled conditions.

### 5. Simplification can improve the complete system

Removing hardware that no longer provided enough benefit reduced wiring and structural complexity.

---

## ✦ 2.1 Final Power & EV3 Summary ─── ⋆⋅☆⋅⋆ ───

Cheese v4 uses the **EV3 rechargeable battery** as its primary power source and the **EV3 Brick** as its central controller.

The v4 redesign keeps the EV3 lower, flatter, and accessible while reducing unnecessary upper structure.

Battery condition is also treated as an engineering variable during testing because changes in available power can affect the physical response of the motors and make navigation comparisons less reliable.
