Cheese v4 uses the **LEGO MINDSTORMS EV3 rechargeable battery** as its main energy source and the **EV3 Brick** as the central controller of the robot.

The EV3 controls the propulsion and steering motors, reads the LEGO sensors, executes the navigation software, and communicates with the Arduino Nano through USB.

For the obstacle challenge, the Arduino Nano works as the communication bridge between the EV3 and the HuskyLens camera.

The resulting architecture connects four major systems:

<p align="center">
  <strong>Power → Control → Sensors & Actuators → Vision</strong>
</p>

---

## ❀ 2.1.1 Complete Power & Control Architecture ────୨ৎ────────୨ৎ────

At the center of Cheese is the EV3 Brick.

The overall system can be summarized as:

```text
EV3 Rechargeable Battery
          │
          ▼
       EV3 Brick
     ┌────┼─────────────┐
     │    │             │
     ▼    ▼             ▼
  Motors Sensors    Arduino Nano
                        │
                       I2C
                        │
                        ▼
                    HuskyLens
```

The robot therefore combines the standard LEGO EV3 ecosystem with an external vision subsystem.

| System | Main Components | Purpose |
| :--- | :--- | :--- |
| **Power** | EV3 rechargeable battery | Supplies the robot |
| **Control** | EV3 Brick | Executes the main navigation software |
| **Propulsion** | EV3 Large Motor | Drives the robot |
| **Steering** | EV3 Medium Motor | Controls the front steering linkage |
| **Distance sensing** | 3 ultrasonic sensors | Detects walls and distances |
| **Floor sensing** | EV3 Color Sensor | Detects track colors |
| **Vision** | HuskyLens | Detects obstacle colors |
| **Vision bridge** | Arduino Nano | Transfers camera information to the EV3 |
| **Communication** | USB + I2C | Connects EV3, Nano, and HuskyLens |

## ❀ 2.1.2 Main Power Source ────୨ৎ────────୨ৎ────

The main electrical energy source of Cheese v4 is the **LEGO MINDSTORMS EV3 rechargeable battery**.

The battery is installed directly into the EV3 Brick.

From there, the EV3 distributes power to the LEGO motors and sensors connected to its ports.

## ❀ 2.1.9 Arduino Nano ↔ HuskyLens Wiring ────୨ৎ────────୨ৎ────

The Arduino Nano communicates with the HuskyLens through **I2C**.

The essential connection is:

| HuskyLens | Arduino Nano | Function |
| :--- | :--- | :--- |
| **VCC** | **5V** | Power |
| **GND** | **GND** | Common ground |
| **SDA** | **A4 / SDA** | I2C data |
| **SCL** | **A5 / SCL** | I2C clock |

The resulting data path is:

<p align="center">
  <strong>HuskyLens → Arduino Nano → EV3 → Navigation Logic</strong>

## ❀ 2.1.10 Power Consistency During Testing ────୨ৎ────────୨ৎ────

Battery condition became an important variable during development.

Cheese can still operate when the battery is partially discharged, but motor behavior may no longer match the behavior observed with a freshly charged battery.

This matters because the robot depends heavily on timing.

For example:

<p align="center">
  <strong>Sensor detection → Software decision → Motor response → Physical movement</strong>
</p>

If the motor response changes, the final physical path can change even when the software remains identical.

| Battery Condition | Observed Engineering Concern |
| :--- | :--- |
| **Charged** | More consistent motor response |
| **Partially discharged** | Behavior may begin to differ from previous tuning |
| **Weak** | Steering and propulsion become less reliable for comparison |
| **Different charge between tests** | Can make software changes difficult to evaluate |

Because of this, battery condition is considered before changing important tuning values.

---

## ❀ 2.1.11 Why Battery Condition Matters to PID ────୨ৎ────────୨ৎ────

The PID controller determines how Cheese corrects its path, but the controller does not physically move the robot.

The motors execute those commands.

Therefore:

<p align="center">
  <strong>
    Correct software command + inconsistent motor response
    = different physical result
  </strong>
</p>

A curve that suddenly becomes wider does not automatically mean that the PID values are wrong.

Possible causes include:

- battery condition,
- mechanical friction,
- wheel grip,
- sensor readings,
- steering response,
- or software parameters.

This distinction became important during testing because changing software to compensate for a weak battery could make the robot behave incorrectly again once a charged battery was installed.

---

## ❀ 2.1.12 Battery Rotation as a Testing Control ────୨ৎ────────୨ৎ────

Using two rechargeable batteries became part of our testing procedure.

Consider two tests:

| Variable | Test A | Test B |
| :--- | :---: | :---: |
| Code | Same | Same |
| Robot structure | Same | Same |
| Sensor configuration | Same | Same |
| Battery | Charged | Weak |
| Result | Stable | Different |

Without controlling the battery condition, the team could incorrectly conclude that the code or mechanical design caused the difference.

Our testing principle therefore became:

<p align="center">
  <strong>
    Control the power condition before changing another system.
  </strong>
</p>

This improves the reliability of comparisons between different PID, curve, speed, and steering configurations.

## ❀ 2.1.13 v3 → v4 Electrical Simplification ────୨ৎ────────୨ৎ────

Cheese v3 included an auxiliary lighting system that was tested to improve sensing conditions.

However, this system also required additional:

- wiring,
- structural support,
- mounting components,
- and power hardware.

During the v4 redesign, the team simplified the upper structure and changed the sensor arrangement.

The permanent auxiliary lighting system was therefore removed.

## ✦ Engineering Decisions & Lessons ─── ⋆⋅☆⋅⋆ ───

The development of Cheese showed that the electrical system cannot be treated independently from software and mechanical design.

### Lesson 1 — Power affects repeatability

Battery condition can change motor response and therefore change the physical behavior of the robot.

### Lesson 2 — The EV3 is more than a processor

It is simultaneously the robot's controller, LEGO sensor interface, motor interface, power-distribution center, and communication point.

### Lesson 3 — External electronics need clear interfaces

The Arduino Nano and HuskyLens architecture is documented separately because it introduces a non-LEGO subsystem into the robot.

### Lesson 4 — Diagrams and photographs serve different purposes

A wiring diagram explains **how the system is supposed to connect**.

A photograph proves **how the system was actually implemented**.

Both are necessary for reproducibility.

### Lesson 5 — Simpler can be better

Removing the previous auxiliary lighting system reduced hardware, wiring, and structural complexity.

The goal of v4 was not simply to remove components, but to keep only the systems that provided enough value to justify their complexity.

## ✦ 2.1 Final Architecture Summary ─── ⋆⋅☆⋅⋆ ───

Cheese v4 uses the EV3 rechargeable battery as its primary energy source and the EV3 Brick as the center of its electrical and control architecture.

The EV3 controls the Large drive motor and Medium steering motor, receives information from the LEGO sensors, and communicates with the Arduino Nano through USB.

The Arduino Nano forms the bridge between the EV3 and HuskyLens. The camera communicates with the Nano through I2C, allowing obstacle information to become part of the EV3 navigation system.

The complete architecture is documented at multiple levels:

<p align="center">
  <strong>
    Complete System → Technical Wiring → EV3 Brick → Nano/HuskyLens → Physical Robot
  </strong>
</p>

This documentation approach makes the robot easier to inspect, debug, explain, and reproduce while also recording the engineering decisions that produced the current Cheese v4 architecture.
