Calibration means checking that the sensors are reading the real environment correctly before expecting the robot to drive reliably. A sensor can be connected correctly and still give poor information if its height, angle, lighting, distance, movement, or cable routing is not stable.

For Cheese, calibration is especially important because the robot depends on different types of sensors at the same time:

<div align="center">

| Sensor Type | What It Reads | Why Calibration Matters |
| :--- | :--- | :--- |
| **Color sensor** | Floor colors and track markers | The robot uses color readings to detect progress and count curves. |
| **Ultrasonic sensors** | Wall distance | The robot uses distance readings for wall following and PID correction. |
| **HuskyLens camera** | Obstacles / visual targets | The robot will use camera recognition to identify obstacle colors and react correctly. |

</div>

The most important lesson is that sensor calibration is not only about numbers. It is about making sure the physical placement, code logic, testing conditions, and sensor behavior all match each other.

---

## ❀ 2.4.1 Calibration Philosophy ────୨ৎ────────୨ৎ────

Cheese does not use one single calibration method for every sensor because each sensor reads a different part of the field. The color sensor reads the floor, the ultrasonic sensors read walls, and the HuskyLens reads obstacles in front of the robot.

For that reason, each sensor needs a different type of testing.

<div align="center">

| Sensor | Calibration Style | Why This Style Fits |
| :--- | :--- | :--- |
| **Color sensor** | Real-track testing and color grouping | The floor colors depend on the actual mat, lighting, and sensor height. |
| **Ultrasonic sensors** | Repeated distance tests, PID tuning, and placement adjustment | Wall readings depend on angle, height, movement, and distance. |
| **HuskyLens** | Planned training on real pillars | Camera recognition depends on real obstacle appearance and lighting. |

</div>

This means calibration on Cheese is not a one-time action. It is an iterative process:

<p align="center">
  <strong>Test → observe readings → identify failure → adjust placement or code → test again</strong>
</p>

That repeated process is slower, but it is more realistic. A robot can behave correctly once by luck, but reliable calibration means the same sensor decision works across repeated runs.

## ❀ 2.4.4 What a Threshold Means ────୨ৎ────────୨ৎ────

A threshold is a limit used by the code to decide when a sensor reading should count as meaningful.

For a beginner, a threshold is like a rule that says:

<p align="center">
  <strong>“If the sensor reading reaches this condition, the robot should react.”</strong>
</p>

Thresholds are necessary because real sensors do not always give perfect readings. A sensor might briefly read a color, see a reflection, detect noise, or measure a strange distance. Without thresholds or confirmation logic, the robot could react to every tiny mistake.

<div align="center">

| Sensor | Example of Threshold / Rule | Why It Matters |
| :--- | :--- | :--- |
| **Color sensor** | Accept only specific color categories as useful markers. | Prevents the robot from counting random floor readings as track markers. |
| **Ultrasonic sensors** | React when wall distance becomes too close, too far, or unbalanced. | Helps PID and wall correction decide when to steer. |
| **HuskyLens** | React only when a trained object or ID is detected. | Prevents random visual information from triggering obstacle behavior. |

</div>

Thresholds are not magic values. They must be tested because the best threshold depends on the robot’s speed, sensor placement, lighting, surface, and movement.

## ❀ 2.4.5 How the Color Sensor Was Tested ────୨ৎ────────୨ৎ────

The color sensor was tested directly on the real track. This was important because Cheese does not drive on a theoretical surface. It drives on the real mat, under real lighting, with real colored lines, at real speed.

The color sensor did not give as many problems as the ultrasonic sensors. However, using it as part of the navigation strategy was still an important engineering decision.

At first, it could seem possible to let the ultrasonic sensors do almost everything: detect walls, regulate PID, help with curves, and guide the robot around the field. But that would put too much responsibility on the ultrasonic sensors. If they already have to manage wall distance, they should not also be the only source of progress information.

For that reason, the color sensor became part of the curve and progress strategy. It helps the robot know when it passes important floor markers.

<div align="center">

| Color Sensor Test Focus | Why It Mattered |
| :--- | :--- |
| **Testing on real colored lines** | The sensor needed to recognize the actual colors on our mat. |
| **Repeated passes over the same line** | Helped check whether the same marker produced similar useful readings. |
| **Testing while moving** | The robot reads the line quickly, not while perfectly still. |
| **Using it for curve / line counting** | Helped Cheese know where it was in the run. |
| **Reducing ultrasonic workload** | Allowed ultrasonic sensors to focus more on wall distance and PID correction. |

</div>

The color sensor gave Cheese a different type of information from the ultrasonic sensors:

<p align="center">
  <strong>Ultrasonic sensors:</strong> “How close am I to the wall?”<br>
  <strong>Color sensor:</strong> “What floor marker did I pass?”
</p>

That separation made the robot’s logic more reliable because each sensor had a clearer job.

---

## ❀ 2.4.6 Color Sensor Mode: COL-COLOR ────୨ৎ────────୨ৎ────

The color sensor runs in **COL-COLOR mode**. This is the EV3 color sensor’s built-in color classification mode.

In this mode, the sensor emits its own light, reads the light that reflects back from the floor, and classifies the result as a built-in color category. Instead of giving the code raw RGB values every time, the sensor gives a simpler answer, such as blue, red, yellow, brown, or another recognized color.

We chose this mode because it kept the program simpler and it worked well enough for our track markers.

<div align="center">

| Option | What It Means | Why We Did / Did Not Use It |
| :--- | :--- | :--- |
| **COL-COLOR mode** | Sensor classifies the color internally. | Used because it is simpler and reliable enough for our markers. |
| **Raw RGB values** | Code reads red, green, and blue intensity values directly. | More flexible, but requires more math, thresholds, and tuning. |

</div>

Using COL-COLOR matched the principle of minimum sufficient logic. If the sensor can classify the track colors well enough, the code does not need to add unnecessary complexity.

---

## ❀ 2.4.7 The Orange Color Group ────୨ৎ────────୨ৎ────

The orange line was the most subtle part of color calibration.

A real sensor does not always read a real orange surface as one perfect category. Depending on lighting, sensor height, surface reflection, and movement, the EV3 color sensor may classify the orange line as different warm colors.

During testing, the orange line could appear as:

<div align="center">

| Real Track Marker | Possible Sensor Reading | Code Meaning |
| :--- | :--- | :--- |
| **Orange line** | Red | Orange marker detected. |
| **Orange line** | Yellow | Orange marker detected. |
| **Orange line** | Brown | Orange marker detected. |
| **Blue line** | Blue | Blue marker detected. |

</div>

Instead of fighting the sensor and trying to force it to report only one exact color, we accepted the readings it naturally produced on the real mat.

The code groups the warm readings together:

<p align="center">
  <strong>ORANGE_COLOR_GROUP = red + yellow + brown</strong>
</p>

This is a practical calibration decision. The robot does not need the sensor to perfectly name the color “orange.” It only needs to know that the orange marker has been detected.

---

## ❀ 2.4.8 Why Color Grouping Improved Reliability ────୨ৎ────────୨ৎ────

Color grouping improved reliability because it made the code match the real behavior of the sensor.

If the orange line is sometimes read as red, sometimes yellow, and sometimes brown, then accepting only one of those categories would make the robot miss real markers. By accepting the full group, the robot is more tolerant to small changes in lighting, reflection, or motion.

<div align="center">

| Strategy | Problem | Result |
| :--- | :--- | :--- |
| **Accept only one orange-like reading** | The robot may miss the line if the sensor reports a different warm color. | Less reliable. |
| **Accept red + yellow + brown as orange group** | The robot accepts the real range of readings produced by the sensor. | More reliable. |
| **Switch to raw RGB immediately** | More control, but more calibration math and thresholds. | More complex than needed at this stage. |

</div>

This decision shows that calibration does not always mean making readings perfectly clean. Sometimes calibration means designing the code to handle the sensor’s real-world behavior.

---

## ❀ 2.4.9 Why the Color Sensor Was Calibrated on the Real Track ────୨ৎ────────୨ৎ────

We did not choose the color behavior only from theory, a datasheet, or another team’s robot. We tested it on the real mat.

This matters because a color sensor reading depends on several physical conditions:

<div align="center">

| Condition | How It Can Affect the Reading |
| :--- | :--- |
| **Paint color** | The real orange or blue may not match a perfect digital color. |
| **Surface finish** | A shiny or matte surface reflects light differently. |
| **Ambient lighting** | Room light can slightly change what the sensor sees. |
| **Sensor height** | A higher or lower sensor can receive different reflected light. |
| **Robot speed** | Fast movement reduces the time the sensor spends over a line. |
| **Sensor angle** | If the sensor is tilted, reflected light changes. |

</div>

Calibrating on the real surface made the color sensor more reliable because the code was based on what Cheese actually saw during testing.

<p align="center">
  <strong>Real track testing → real sensor behavior → better color decisions</strong>
</p>

This is also why the color sensor stayed in the same position in v4. It was already matching its job: reading the floor markers.

## ❀ 2.4.10 How Ultrasonic Readings Were Checked ────୨ৎ────────୨ৎ────

The ultrasonic sensors were checked through repeated driving tests and distance-reading observations. Unlike the color sensor, they were not calibrated with a formal startup routine. Instead, their behavior was improved by testing how the robot reacted to wall readings.

The ultrasonic sensors are used for wall distance, which affects PID and wall following. When the robot drifted, overcorrected, corrected too late, or crashed, the team checked whether the problem could be coming from sensor readings, PID values, steering behavior, or physical placement.

<div align="center">

| Ultrasonic Testing Method | Purpose |
| :--- | :--- |
| **Repeated runs near walls** | Checked whether the robot could follow the wall consistently. |
| **Distance value observation** | Helped identify readings that looked too high, too low, or unstable. |
| **PID tuning** | Adjusted how strongly the robot reacted to wall-distance errors. |
| **Threshold adjustment** | Changed when the robot considered a wall distance safe, risky, or severe. |
| **Placement changes** | Improved the physical direction and height of the readings. |
| **v4 sensor lowering** | Improved alignment between the ultrasonic beam and the side walls. |

</div>

This is closer to iterative validation than formal calibration. The sensors were checked by how they behaved during real driving, not by a single calibration screen.

---

## ❀ 2.4.11 Programmatic Validation for Ultrasonic Sensors ────୨ৎ────────୨ৎ────

For autonomous robots, ultrasonic readings should not be trusted blindly. A program can use logic rules to decide whether a reading looks useful or suspicious.

Programmatic validation can include:

<div align="center">

| Validation Method | Beginner Explanation | Why It Helps |
| :--- | :--- | :--- |
| **Range check** | Ignore values that are impossible or clearly wrong. | Prevents extreme spikes from controlling the robot. |
| **Threshold zones** | Treat distances as safe, warning, or dangerous. | Helps the robot decide how strongly to correct. |
| **Repeated readings** | Check if values stay similar across multiple loops. | Reduces reaction to one random bad reading. |
| **Sensor comparison** | Compare left and right wall distances. | Helps detect when one sensor seems unrealistic. |
| **Behavior check** | Watch if sensor values match robot movement. | Helps separate sensor error from mechanical error. |

</div>

Cheese’s ultrasonic process has improved through testing, but this is still an area where stronger validation could help. The current system reacts to readings during the run, but a future version could add a short startup check to verify that both sensors are reading reasonable values before the robot starts driving.

---

## ❀ 2.4.12 Ultrasonic Sensor Issues and Adjustments ────୨ৎ────────୨ৎ────

The ultrasonic sensors gave more problems than the color sensor. This is because ultrasonic distance readings depend on how sound reflects from the wall. If the height, angle, distance, movement, or wall contact changes, the reading can change.

<div align="center">

| Issue | Why It Happened | Adjustment / Response | Result |
| :--- | :--- | :--- | :--- |
| **Wall readings were inconsistent** | The sensor angle or height could affect the echo. | Repeated wall-distance tests and PID adjustments. | More controlled correction behavior. |
| **Robot corrected too late** | The reading or threshold did not trigger correction early enough. | Adjusted distance thresholds and steering response values. | Better reaction near walls. |
| **Robot overcorrected** | PID or steering response was too aggressive. | Reduced or tuned correction strength. | Smoother movement after testing. |
| **Sensor beam could miss wall surface** | Sensors were too high or not aligned well enough with the wall. | Lowered ultrasonic sensors in v4. | Better physical alignment with the side walls. |
| **Bad readings wasted runs** | No formal startup validation routine existed. | Used run results to diagnose readings after failure. | Identified need for better pre-run checks in the future. |
| **Different failures looked similar** | Battery, steering, PID, and sensor issues can all cause crashes. | Compared behavior across repeated tests. | Helped separate sensor issues from other subsystems. |

</div>

The main lesson from the ultrasonic sensors is that calibration is not only about the sensor. It also depends on the robot’s structure, sensor height, sensor angle, and the code that reacts to the readings.

---

## ❀ 2.4.13 Why There Is No Full Startup Calibration Routine Yet ────୨ৎ────────୨ৎ────

Cheese does not currently perform a full calibration routine at the beginning of a run. It does not stop to measure a known wall distance, compare both ultrasonic sensors, test the color sensor, or validate the camera before starting.

Instead, the robot starts driving and corrects while moving.

This has one advantage:

<div align="center">

| Advantage | Why It Helps |
| :--- | :--- |
| **Fast start** | The robot does not waste time before beginning the run. |
| **Simpler code** | Fewer startup states and fewer pre-run steps. |

</div>

But it also has a weakness:

<div align="center">

| Weakness | Why It Matters |
| :--- | :--- |
| **No baseline reading** | The robot cannot compare current readings against known-good values. |
| **Bad sensor state may go unnoticed** | Problems may only appear after the robot starts moving. |
| **Failures cost a full run** | A simple issue may not be caught until the robot crashes. |

</div>

A future improvement would be a short pre-run validation routine. For example, Cheese could check whether both ultrasonic sensors are reading within a reasonable range before starting, or whether the color sensor is giving a stable floor reading.

This is not implemented yet, but documenting the gap is important because it shows where reliability can still improve.

## ❀ 2.4.15 Problems Caused by Shadows, Height, Angle, Distance, and Movement ────୨ৎ────────୨ৎ────

Sensor readings are affected by physical conditions. A sensor can be good, but still produce poor results if it is placed badly or tested under inconsistent conditions.

<div align="center">

| Condition | Sensor Most Affected | Possible Problem |
| :--- | :--- | :--- |
| **Shadows / lighting changes** | HuskyLens, color sensor | Objects or colors may look darker or less clear. |
| **Height** | Ultrasonic sensor, color sensor, HuskyLens | Sensor may look above the wall, too far from the floor, or at the wrong obstacle area. |
| **Angle** | Ultrasonic sensor, HuskyLens | Signal or view may not point toward the correct target. |
| **Distance** | Ultrasonic sensor, HuskyLens | Target may be too close, too far, or not centered. |
| **Movement** | All sensors | Fast movement can reduce the time available to detect and react. |
| **Cable interference** | All sensors | A cable can block a view, pull a sensor, or create inspection problems. |
| **Battery level** | Motors, camera system, sensor timing | Lower voltage can change robot behavior and make sensor issues harder to diagnose. |

</div>

This is why sensor calibration connects to the entire robot. Sensors are not independent from mechanical design, power, wiring, and software.

## ❀ 2.4.16 How v4 Changes May Improve Reliability ────୨ৎ────────୨ৎ────

The v4 redesign improved the physical conditions around the sensors. The robot became more stable, lighter, cleaner, and easier to inspect. This can improve reliability because sensors and motors are held in more stable positions, with fewer structural and wiring problems around them.

<div align="center">

| v4 Change | Why It Helps Calibration / Reliability |
| :--- | :--- |
| **Lower ultrasonic sensors** | Better alignment with the side walls. |
| **Simpler camera structure** | Easier camera inspection and less unnecessary upper mass. |
| **Shorter cables** | Less chance of cables blocking sensors or movement. |
| **Color sensor kept in working position** | Avoided unnecessary recalibration. |
| **Cleaner layout** | Easier to inspect sensors before testing. |
| **More stable motor placement** | Reduces structural movement that can affect sensor-based behavior. |
| **Lower center of gravity** | Helps make movement less chaotic during sensor-based corrections. |

</div>

The v4 redesign did not magically solve every sensor issue, but it made testing easier and reduced some physical sources of error.

<p align="center">
  <strong>v4 reliability idea:</strong><br>
  Better structure does not replace calibration, but it makes calibration more repeatable.
</p>

## ❀ 2.4.17 Calibration Is Repeated, Not One Single Step ────୨ৎ────────୨ৎ────

Calibration is a slow process. For us, it takes many repeated tests, similar conditions, and small adjustments. It is difficult to find the exact point that works because Cheese uses more than one sensor, and each sensor behaves differently.

A single test is not enough because one good run can happen by luck. A better calibration process needs repeated evidence.

<p align="center">
  <strong>Test → observe → adjust → repeat → compare results</strong>
</p>

<div align="center">

| Calibration Step | What We Do | Why It Matters |
| :--- | :--- | :--- |
| **Test** | Run the robot or sensor under real conditions. | Shows how the sensor behaves outside theory. |
| **Observe** | Watch what fails or what readings look unstable. | Identifies the real problem. |
| **Adjust** | Change placement, thresholds, PID values, or code response. | Tests a possible solution. |
| **Repeat** | Run the same test again. | Checks whether the change actually helped. |
| **Compare** | Decide if the result is better, worse, or unchanged. | Prevents guessing from one lucky run. |

</div>

This repeated process is important because sensor behavior changes with height, angle, lighting, distance, movement, battery level, and structure. Calibration is not just “setting a value.” It is finding values and placements that survive real testing.

## ✦ Final Sensor Calibration Summary ─── ⋆⋅☆⋅⋆ ───

Calibration was necessary because sensor readings can change depending on height, angle, lighting, distance, movement, battery level, wiring, and structure.

The color sensor was tested on the real track and became reliable for floor marker detection and curve counting. The ultrasonic sensors were checked through repeated distance tests, wall-following behavior, PID tuning, threshold adjustment, and v4 placement changes, but they still need a stronger pre-run validation process. The HuskyLens calibration is still pending and will need to be trained using real obstacle pillars.

<p align="center">
  <strong>Final calibration lesson:</strong><br>
  A sensor is not reliable only because it is connected. It becomes reliable when its readings are tested, understood, repeated, and improved under real conditions.
</p>
