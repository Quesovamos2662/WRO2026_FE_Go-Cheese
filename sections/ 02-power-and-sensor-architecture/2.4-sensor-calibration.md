A sensor being connected correctly does not automatically make its information reliable.

Its readings can change because of:

- height,
- angle,
- distance,
- lighting,
- robot speed,
- field geometry,
- battery condition,
- and the way the software interprets the measurement.

For this reason, Cheese v4 was calibrated primarily through **real-track testing and repeated iteration**.

<p align="center">
  <strong>
    Test → Observe → Adjust → Repeat → Compare
  </strong>
</p>

## ❀ 2.4.1 Calibration Strategy ────୨ৎ────────୨ৎ────

Cheese uses several sensor types, so there is no single calibration procedure that works for the entire robot.

| Sensor | Calibration Focus | Why |
| :--- | :--- | :--- |
| **Left Ultrasonic** | Wall distance and PID response | Controls lateral wall awareness |
| **Right Ultrasonic** | Wall distance and PID response | Controls lateral wall awareness |
| **Front Ultrasonic** | Safety and recovery distance | Detects dangerous forward proximity |
| **EV3 Color Sensor** | Real floor-marker recognition | Supports curve counting and run progress |
| **HuskyLens** | Pillar recognition and visibility | Supports obstacle avoidance |

The calibration process therefore connects:

```text
PHYSICAL PLACEMENT
        ↓
SENSOR READING
        ↓
SOFTWARE INTERPRETATION
        ↓
ROBOT RESPONSE
        ↓
REAL-TRACK RESULT
```

A problem at any stage can affect the final behavior.

The color sensor is calibrated through the **real competition surface**, rather than relying only on theoretical color values.

This matters because the reading depends on:

| Variable | Possible Effect |
| :--- | :--- |
| Ambient lighting | Changes reflected light |
| Surface finish | Changes reflection |
| Sensor height | Changes the amount of reflected light received |
| Robot speed | Changes how long the sensor remains over a marker |
| Sensor angle | Changes the geometry of reflected light |

## ❀ 2.4.4 COL-COLOR Mode ────୨ৎ────────୨ৎ────

The current Open code uses the EV3 Color Sensor in:

```python
COL-COLOR
```

Instead of processing raw RGB values, the program uses the EV3 sensor's built-in color classification.

This keeps the logic simpler and proved sufficient for the current track.

The important software interpretation is:

```text
BLUE
  ↓
Blue marker

RED
YELLOW  ─────→ ORANGE marker
BROWN
```

Therefore:

```text
BLUE = BLUE

RED + YELLOW + BROWN = ORANGE
```

The robot does not need to perfectly identify the physical orange paint as the word **orange**.

It only needs to reliably recognize:

> **“This reading belongs to the orange track-marker group.”**

---

# ❀ 2.4.5 Why Orange Uses a Color Group ────୨ৎ────────୨ৎ────

During real-track testing, the orange region was not always classified by the EV3 sensor as one identical built-in color.

Depending on conditions, warm readings could appear as:

| Physical Marker | EV3 Reading | Software Meaning |
| :--- | :--- | :--- |
| Orange | Red | ORANGE |
| Orange | Yellow | ORANGE |
| Orange | Brown | ORANGE |
| Blue | Blue | BLUE |

Instead of forcing the physical sensor to behave like a perfect digital color detector, the software was adapted to the real readings.

This is an important calibration principle:

> **Calibration should make the software understand the real sensor, not pretend the real sensor behaves perfectly.**

---

# ❀ 2.4.6 Color Sensor Physical Improvement ────୨ৎ────────୨ৎ────

Early testing showed an important environmental problem:

**ambient light could affect floor-color detection.**

At one stage, a physical cover was tested around the color sensor to reduce external light.

However, the cover introduced another problem:

> It could interfere physically with the track.

Therefore, it was not retained as part of the normal v4 design.

Instead, the sensor was positioned **slightly lower while remaining in the same general structural region**.

<p align="center">
  <img src="../../v-photos/v4/color_sensor_floor_gap_v4.jpg"
       alt="Current Cheese v4 color sensor height"
       width="62%">
</p>

The lower position improved the reading conditions enough that the additional light-blocking structure was no longer necessary during normal operation.

### Engineering chain

```text
Ambient light affected readings
            ↓
Physical cover tested
            ↓
Cover created mechanical interference
            ↓
Sensor position reconsidered
            ↓
Sensor lowered slightly
            ↓
More reliable floor detection
            ↓
Cover removed
```

This is a good example of solving a sensing problem through **mechanical calibration instead of additional software complexity**.

# ❀ 2.4.7 Curve Validation ────୨ৎ────────୨ৎ────

Detecting a color does not automatically mean Cheese completed a curve.

This distinction became important during development.

The current curve-counting system recognizes valid transitions:

```text
BLUE → ORANGE

or

ORANGE → BLUE
```

However, additional validation is used because the sensor can encounter a color even when the physical turn has not been completed correctly.

The current system therefore combines:

- color sequence,
- steering confirmation,
- timing window,
- and cooldown logic.

This reduces false curve counts.

---

## ❀ 2.4.8 Current Curve-Counting Calibration Values ────୨ৎ────────୨ৎ────

Current Open calibration includes:

| Parameter | Current Value |
| :--- | :---: |
| Total curve count | **12** |
| Color-change window | **3.0 s** |
| Curve cooldown | **1.5 s** |
| Minimum steering angle confirmation | **0.1°** |
| Minimum steering time | **0.03 s** |
| Post-color steering window | **0.9 s** |

For a three-lap Open run:

```text
4 corners / lap × 3 laps = 12 validated curves
```

The curve counter is directly connected to the finish and parking logic.

Therefore:

```text
Correct sensor detection
        ↓
Correct curve count
        ↓
Correct run progress
        ↓
Correct parking activation
```

A missed or incorrect count can make parking activate too early or too late.

# ❀ 2.4.9 Ultrasonic Calibration ────୨ৎ────────୨ৎ────

Cheese v4 uses **three ultrasonic sensors**.

The lateral sensors support navigation and PID correction.

The front sensor provides forward-distance safety information.

<p align="center">
  <img src="../../v-photos/v4/side_sensor_layout_v4.jpg"
       alt="Cheese v4 ultrasonic sensor layout"
       width="68%">
</p>

Ultrasonic calibration was performed mainly through repeated driving tests.

The team observed:

- wall distance,
- robot drift,
- correction timing,
- steering strength,
- wall contact,
- and recovery behavior.

---

# ❀ 2.4.10 Why Ultrasonic Placement Matters ────୨ৎ────────୨ৎ────

Ultrasonic sensors measure distance using reflected sound.

Therefore, the physical direction of the sensor matters.

If the sensor is too high or poorly aligned, its sensing region may not interact with the wall as intended.

The v4 layout uses lower lateral ultrasonic positioning.

<p align="center">
  <img src="../../v-photos/v4/side_sensor_layout_v4.jpg"
       alt="Low lateral ultrasonic sensors on Cheese v4"
       width="64%">
</p>

The goal is to improve physical alignment between:

```text
ULTRASONIC BEAM → FIELD WALL
```

This reduces one possible source of unstable distance information.

---

# ❀ 2.4.11 Ultrasonic Filtering ────୨ৎ────────୨ৎ────

Raw ultrasonic measurements can fluctuate.

Reacting aggressively to every individual measurement would make Cheese unstable.

The current Open controller therefore filters sensor information before using it for steering.

Current filtering values include:

| Parameter | Value |
| :--- | :---: |
| Sensor filter alpha | **0.65** |
| Derivative filter | **0.45** |
| Control-loop delay | **0.01 s** |

Filtering helps reduce the effect of short spikes while preserving enough response speed for navigation.

The objective is:

```text
RAW DISTANCE
     ↓
FILTER
     ↓
MORE STABLE ERROR
     ↓
PID
     ↓
STEERING
```

---

# ❀ 2.4.12 PID Calibration ────୨ৎ────────୨ৎ────

Sensor calibration and PID calibration are closely connected.

The ultrasonic sensors provide distance information.

The PID controller determines how strongly Cheese reacts to the resulting error.

Current Open PID values are:

| Constant | Current Value |
| :--- | :---: |
| **KP** | **0.28** |
| **KI** | **0.001** |
| **KD** | **0.08** |
| Integral limit | **20** |
| Center deadband | **1.5** |
| Maximum PID steering angle | **32°** |

The PID controller became one of the most important parts of Open Challenge tuning.

### Too weak

```text
Error detected
     ↓
Small correction
     ↓
Robot continues drifting
```

### Too aggressive

```text
Error detected
     ↓
Large correction
     ↓
Robot crosses target
     ↓
Opposite correction
     ↓
Zig-zag
```

### Desired response

```text
Error detected
     ↓
Proportional correction
     ↓
Smooth return
     ↓
Stable path
```

---

# ❀ 2.4.13 Wall-Distance Thresholds ────୨ৎ────────୨ৎ────

Not every wall distance should produce the same response.

The Open controller therefore uses several distance regions.

| Parameter | Current Value |
| :--- | :---: |
| Gentle wall distance | **28.0 cm** |
| Severe wall distance | **22.0 cm** |
| Full wall-avoidance distance | **15.0 cm** |
| Gentle wall angle | **14°** |
| Severe wall angle | **18°** |

This creates progressive correction.

```text
NORMAL DISTANCE
      ↓
PID navigation

CLOSER
      ↓
Gentle protection

TOO CLOSE
      ↓
Severe protection

VERY CLOSE
      ↓
Maximum wall-avoidance authority
```

This is safer than waiting until Cheese is already touching the wall.

# ❀ 2.4.15 Front Recovery Logic ────୨ৎ────────୨ৎ────

When the front distance becomes dangerously small, Cheese can reverse to create space.

The logic can be simplified as:

```text
Front distance checked
        ↓
Safe?
 ┌──────┴──────┐
YES            NO
 │              │
Continue     Confirm reading
                ↓
          Reverse recovery
                ↓
         Increase distance
                ↓
        Return to navigation
```

This recovery behavior was introduced because a robot that remains pressed against a wall may no longer have enough room for effective steering.

Backing away creates space for the steering system to work again.

# ❀ 2.4.17 Vision Calibration Is More Than Color Recognition ────୨ৎ────────୨ৎ────

Recognizing the correct color is only the first part of obstacle calibration.

The camera must also detect the pillar:

- early enough,
- at a useful angle,
- while the pillar remains inside the field of view,
- and with enough time for Cheese to physically react.

This became especially important after curves.

A pillar can be correctly trained but still be missed if Cheese exits a corner with the camera pointed away from the useful region.

Therefore:

```text
GOOD COLOR TRAINING
        ≠
GUARANTEED AVOIDANCE
```

Successful obstacle behavior requires:

```text
Recognition
     +
Field of View
     +
Robot Position
     +
Detection Timing
     +
Steering Response
     +
Post-Avoidance Recovery
```

# ❀ 2.4.19 Current Obstacle-Sensing Behavior ────୨ৎ────────୨ৎ────

The HuskyLens currently influences Cheese's movement.

The obstacle system is therefore beyond the simple detection stage.

Current behavior can be summarized as:

```text
HuskyLens sees pillar
        ↓
Color / ID recognized
        ↓
Position information sent through Nano
        ↓
EV3 receives camera information
        ↓
Camera steering influence generated
        ↓
Combined with navigation / safety logic
        ↓
Cheese attempts avoidance
```

However, current testing has shown several remaining failure modes.

| Failure | Current Observation |
| :--- | :--- |
| Pillar not visible soon enough | Avoidance can begin late |
| Poor approach angle | Camera may not maintain useful detection |
| Avoidance too weak | Cheese may contact or carry the obstacle |
| Poor recovery | Robot may not return to a useful path afterward |
| Poor post-curve position | Next pillar may enter the FOV too late |

The largest remaining challenge is not simply recognizing red and green.

It is:

> **recovering reliably after the avoidance so Cheese is ready for the next obstacle.**

# ❀ 2.4.20 Speed as a Calibration Variable ────୨ৎ────────୨ৎ────

Sensor reliability is connected to robot speed.

A faster robot covers more distance between sensor updates and gives the steering system less time to respond.

This became especially important in obstacle testing.

Reducing speed can provide:

- more camera observation time,
- more reaction time,
- smoother avoidance,
- more useful ultrasonic corrections,
- and better recovery opportunities.

However, excessive speed reduction also increases run time.

Therefore speed tuning is a trade-off:

```text
HIGH SPEED
    ↓
Fast run
but
less reaction time

LOWER SPEED
    ↓
More reaction time
but
slower run
```

The target is the **fastest speed that remains repeatable**.

---

# ❀ 2.4.21 Battery Condition as a Testing Variable ────୨ৎ────────୨ৎ────

Battery condition also affects calibration results.

A sensor threshold may remain mathematically identical while the robot's physical response changes because the motors do not behave exactly the same under different battery conditions.

For this reason, a test failure should not immediately be blamed on the sensor.

The team must consider:

```text
Sensor?
PID?
Steering?
Mechanical structure?
Battery?
Camera visibility?
Software timing?
```

This systems approach helps prevent changing a correct calibration value to compensate for a completely different problem.

# ❀ 2.4.23 Failure → Adjustment → Result ────୨ৎ────────୨ৎ────

The most important calibration decisions can be summarized through the engineering process.

| Failure / Observation | Adjustment | Result |
| :--- | :--- | :--- |
| Ambient light affected floor readings | Tested cover, then lowered color sensor | More reliable floor detection without permanent cover |
| Orange produced multiple EV3 classifications | Grouped red + yellow + brown | More tolerant orange detection |
| False/incorrect curve counts were possible | Added sequence, steering confirmation and cooldown | More reliable curve counting |
| Wall correction could become unstable | Tuned PID and filtered ultrasonic readings | Smoother Open navigation |
| Ultrasonic wall alignment needed improvement | Lowered lateral sensor placement | Better physical wall alignment |
| Dangerous front proximity | Added front-distance recovery logic | More protection from front-wall crashes |
| Camera detection depended strongly on angle | Adjusted camera position and robot path | Better opportunity for pillar detection |
| Obstacle avoidance could fail despite detection | Continued steering and speed tuning | Improved behavior, still under development |
| Robot could remain poorly positioned after avoidance | Recovery became a major tuning focus | Current obstacle-development priority |

This is more representative of the actual development process than treating calibration as one isolated setup step.

# ✦ Engineering Lessons ─── ⋆⋅☆⋅⋆ ───

### 1. Calibration is not one number

Reliable sensing depends on physical placement, software interpretation, and robot behavior together.

### 2. Real-track testing matters

The competition mat, lighting, walls, speed, and obstacles produce conditions that cannot be reproduced perfectly through theory alone.

### 3. A mechanical adjustment can improve software reliability

Lowering the color sensor and improving sensor placement changed the quality of the information reaching the code.

### 4. Filtering helps, but cannot repair bad geometry

Software can reduce noise, but a sensor still needs to point toward useful information.

### 5. Detection and successful reaction are different problems

This is especially important for HuskyLens.

Recognizing a pillar correctly does not guarantee that the robot will avoid it correctly.

### 6. Reliability requires repetition

One successful run is evidence that the system **can** work.

Repeated successful runs provide evidence that the system is **reliable**.

# ✦ 2.4 Final Calibration Summary ─── ⋆⋅☆⋅⋆ ───

Cheese v4 uses calibration as a continuous engineering process rather than a one-time setup procedure.

The **color sensor** is currently functional for floor-marker detection and curve counting. Its reliability improved through real-track testing, warm-color grouping, validation logic, and a slightly lower physical position.

The **three ultrasonic sensors** provide wall and forward-distance information. Their behavior is supported by filtering, PID tuning, progressive wall thresholds, and front-distance recovery logic.

The **HuskyLens** is already trained and integrated into the obstacle system. It recognizes the competition pillar colors and influences steering through the Nano-to-EV3 vision architecture. The remaining obstacle problem is primarily improving detection timing, avoidance strength, and especially post-obstacle recovery.

The most important calibration lesson from Cheese is:

<p align="center">
  <strong>
    Reliable sensing is created by matching the physical sensor,
    the software interpretation, and the real environment.
  </strong>
</p>
